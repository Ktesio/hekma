- (idea by coach) Tamper-evident run ledger: hash-chained record of every model call, tool call, policy decision and policy change, with retention and export
- (idea by coach) Oversight as a feature: approval gates on high-impact tool calls (pay, email, delete) with a named human approver recorded in the ledger

- (idea by user) Auditor fear 1: agent sends a wrong application approval to a customer
- (idea by user) Auditor fear 2: agent sends letters or emails to customers it should not
- (idea by user) Auditor fear 3 (scariest): cross-process data contamination — a process for customer X gets data from a process for customer Y and leaks it
- (insight by coach) All three fears are about the wire: irreversible customer-facing actions and cross-subject data flow both pass through a point Hekma can sit on
- (idea by coach) Customer-facing outbox: every outbound to a customer (email, letter, decision) goes through a Hekma outbox with policy — hold, sample N% for review, human approve, or a recall window before release
- (idea by coach) Subject-scoped runs: each run declares its data subject (customer id); Hekma blocks and alerts when prompts, tool args or outputs carry another subject's identifiers
- (idea by coach) Contamination canaries: seed a unique fake marker per run; if run A's canary ever appears in run B's traffic, contamination is proven and the runs are frozen
- (idea by coach) Proving the negative: ledger + subject checks let Hekma state, per customer run, that no other customer's identifiers crossed the wire
- (idea by user) Leak paths: vector store, shared memory and many more
- (idea by user) Hardest risk: bad input — a CrewAI/LangGraph flow starts with incorrect data, or agents call tools with the wrong request params
- (insight by coach) Hekma cannot judge whether data is correct, but it can judge whether it is consistent with what the run declared; consistency is checkable at the wire, correctness is not
- (idea by coach) Run binding: at start a run declares its binding (customer_id, application_id); every tool call and outbound must reference the same binding or be held — one mechanism for wrong params and contamination
- (idea by coach) Tool-argument contracts at the wire: per-tool rules (send_email.to must belong to the bound customer; approve_application.id must equal the bound application; amount within range)
- (idea by coach) Intake preflight: flow declares an input schema; Hekma validates the starting payload before the first model call and refuses bad starts
- (idea by coach) Quarantine and resume: on a binding or contract violation, freeze the run, hold its outbox, let a human fix the input and resume from the last checkpoint without touching other runs
