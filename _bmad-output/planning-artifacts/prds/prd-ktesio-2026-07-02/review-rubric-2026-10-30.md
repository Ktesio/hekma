# PRD Quality Review — Hekma: the Control Plane for Agent Workloads

- **PRD:** `_bmad-output/planning-artifacts/prds/prd-ktesio-2026-07-02/prd.md` (updated 2026-10-30)
- **Rubric:** `.claude/skills/bmad-prd/assets/prd-validation-checklist.md`
- **Scope of this run:** the 2026-10-30 control-plane amendments (title, §1, §2, §3 glossary, FR-1/19/21/41/43 amendments, §4.14 FR-49..FR-58, NFR-4, §6, §8, §9.3, §12, §13, §14) and the contradictions they create with unchanged text. Out of scope by ruling: "Ktesio" and `kt` remaining outside the title and Vision.

## Overall verdict

The amendment is unusually disciplined for a pivot: every change is dated and sourced, Task is retired in the glossary rather than silently dropped, the four new `[ASSUMPTION]` tags all round-trip to §14 #22, and most new consequences (FR-53 key custody, FR-54 "never reports a Run as clean without having checked", FR-56 client-timeout honesty) are crisp and testable. What is at risk is the new spine itself: Control Depth is defined as a linear order that the FRs contradict, nobody states which verbs each depth honors, `block` is now silently coupled to Scent-Check `shadow`, and the `warn` default is ratified without the PRD admitting what it costs the solo Operator whose JTBD and UJ the product was built on. The pivot also has no journey, no success metric, and a §10/§4.5 positioning that still argues against the proxy-layer product §4.14 now specifies. Grade: **Fair** — buildable after a focused Update, not before.

## Decision-readiness — thin

The big calls are stated as decisions, which is good: the `warn` default is `[FIXED]` in §3 with a date and owner, Q3 and Q5 are closed with supersession notes, and Q9–Q11 are genuinely open with owners and decision points. But the trade-offs behind the two most consequential decisions are not surfaced. The `warn` default (§3 Breach Action, FR-21) gives up the "set a ceiling once and trust it is enforced even when I am not watching" promise (§2.1 JTBD #2) for every Operator who does not opt in, and it changes a shipped default (`epics.md` still records "default `pause` (ratified)" as delivered behaviour). The PRD's only acknowledgement is the parenthetical "the change ships as a documented default change"; UJ-1 was quietly edited to add "with the Breach Action set to `pause`" so the journey still works, which hides rather than names the cost. There is no `[NOTE FOR PM]` at this tension.

The second unacknowledged trade-off is positioning: FR-51 (base-URL proxy), FR-53 (virtual provider keys, real keys in custody) and FR-56 (reroute to another configured model) put Hekma squarely in LLM-gateway territory, while FR-51 asserts "Hekma complements such gateways and does not replace them" and §8 keeps "Not an LLM/model server". A reader pushing back ("you are building LiteLLM") finds the objection dodged, not answered.

### Findings
- **high** `warn` default ratified without its cost or a migration path (§3 Breach Action, FR-21, §2.1 JTBD #2, UJ-1, §4.5 Description, FR-47, §7) — Existing users whose configs rely on the implicit `pause` default will stop being paused on upgrade; §2.1 JTBD #2 still promises enforcement "even when I am not watching"; §4.5 still says "the Engine acts on the Agent Instance's lifecycle when a ceiling is hit"; FR-47 still says "Spend is capped per run" with whatever Breach Action is configured; §7 requires "minimum one minor-version notice window" for CLI-surface breaking changes, and a default flip is a behavioural break. *Fix:* add a `[NOTE FOR PM]` under FR-21 naming what is given up (unattended enforcement for solo Operators) and why it is accepted (prod framework teams); add a consequence: "an Agent Instance whose config predates 2026-10-30 and sets no Breach Action keeps `pause` (or gets a one-release warning naming the change)"; reword §2.1 JTBD #2 to "…trust it is enforced once I choose an enforcing Breach Action"; update §4.5 Description; make FR-47's recipe set `stop` explicitly and say so in a consequence.
- **high** Gateway overlap stated as a non-issue rather than a decision (FR-51, FR-53, FR-56, §8, §10, §4.5 Description) — §10 Why Now and §4.5 still sell runner-level enforcement as "precisely what proxy-layer budget tools do not do", while §4.14 builds a proxy with virtual keys and model reroute. *Fix:* add a §8 non-goal that draws the line explicitly (e.g. "Not a model gateway: Hekma routes only to hold, reject or reroute a governed Run; provider fallback, caching, prompt management and load-balancing stay with gateways"), and add a dated amendment to §10 and the §4.5 Description stating the new differentiator (depth-aware governance of Runs across runner and wire).

## Substance over theater — adequate

Most new text is earned: each §4.14 FR carries specific, falsifiable consequences, and the principles block ("signal, don't kill"; "a caller can never loosen what operator configuration sets") actually drives consequences in FR-49, FR-53 and FR-54. Two places slide into theater. The §4.14 principle "every surface scales to millions of Runs" and the NFR-4 amendment ("targets are measured at 10k, 100k and 1M Runs") name measurement points but no thresholds — scale as adjective. And the Vision now stacks two theses: a control-plane paragraph for "teams" and "prod", followed unchanged by the "personal agent … per-agent tax … solo operator's laptop fleet" paragraphs. Either could be cut without the other noticing.

### Findings
- **medium** Scale principle has no bound (§4.14 Description, NFR-4 amendment, FR-50) — "scales to millions of Runs" and "no read path loads the whole Run set" are not testable without a latency or memory bound at a stated Run count; NFR-4 defers numbers to "after the Epic 24 benchmark" while FR-50 (Epic 21) must be accepted first. *Fix:* give NFR-4 provisional, tagged targets now (e.g. `hekma ps` default view p95 < 1s at 100k Runs; Service Host RSS per idle wire Run ≤ N KB) as `[ASSUMPTION]` placeholders indexed under §14 #17, to be replaced by the benchmark.
- **medium** Vision reads as two products (§1) — paragraph 1 (control plane, teams, prod) and paragraphs 2–4 (personal agents, solo operator) are not reconciled; "consistency itself is the product" vs "control comes in depths". *Fix:* fold paragraphs 2–4 into one paragraph that positions personal agents as one Control Depth (`supervised`) of the broader thesis, or mark them explicitly as the v1 origin story.

## Strategic coherence — thin

The thesis is clear in §1 paragraph 1 and §4.14's description: governance follows the Run, not the process, at an honest depth. Feature order in §12 follows from it (entities → listing → identity → discovery → hold → continuity → federation). But the thesis is unvalidated by the PRD's own instruments. The new JTBD ("As a framework team…") has no User Journey and no named protagonist; no §4.14 FR says "Realizes UJ-…"; §11 Success Metrics measure v1 only and Q10 defers control-plane metrics to "before Epic 21 closes" — i.e. after the first epic has been built. The promise in §1 ("without ever being the reason prod stops") has no metric or counter-metric, and nothing counterbalances the `warn` default (e.g. runaway spend under `warn`).

### Findings
- **high** The pivot's primary audience has no journey and no metric (§2.1 framework-team JTBD, §2.3, §4.14, §11, §13 Q10) — this is a developer product where UJs are load-bearing (shape fit), yet the persona the whole §4.14 serves never appears in a journey. *Fix:* add UJ-4 with a named protagonist (e.g. a platform engineer pointing a CrewAI flow's base URL at Hekma, self-announcing it, holding a runaway call, raising its budget over a Selector, and restarting the Service Host in handoff mode with the flow untouched); cite UJ-4 from FR-49..FR-58; promote Q10's candidates into provisional SM-6/SM-7 plus a counter-metric (e.g. SM-C4: "unattended overspend under the `warn` default"), tagged `[ASSUMPTION]`.

## Done-ness clarity — thin

Many new consequences are exemplary (FR-53 "the real provider key never appears in the agent's environment, arguments or Agent Home"; FR-56 "it never reports the Run as cleanly paused"; FR-54 "never reports a Run as clean without having checked"). The gaps are structural: the core vocabulary of §4.14 cannot be tested because it is not enumerated. FR-49 says "a verb the depth cannot honor fails fast naming the depth" but no FR says which verbs each depth honors. Run status values (`held`, `silent`, "anomalous", "over-budget", "unattributed") appear in FR-50/52/56 but are never enumerated the way Lifecycle State is. And the Control Depth order contradicts the FRs.

### Findings
- **high** Control Depth is defined as a linear order the FRs contradict, and `observed` has no FR that creates it (§3 Control Depth, FR-19 amendment, FR-49, FR-51, FR-52) — §3 orders depths "observed < wire < registered < supervised", implying a `registered` Run can be held on the wire; but FR-52 lets a Run register by "an OTel resource attribute" with no traffic through Hekma, and the FR-19 amendment says "observed and registered Runs are metered on the wire when their traffic passes through Hekma" — an `observed` Run whose traffic passes through Hekma is by definition `wire`. No FR describes how a Run becomes `observed` (no OTLP ingest FR exists; the glossary's OTLP entry is export-only). *Fix:* either redefine Control Depth as two attributes (traffic path: none / wire; process relation: none / registered / supervised) or define the order so each depth strictly includes the one below (registration requires wire routing); add an FR (or FR-52 consequence) for inbound telemetry that creates `observed` Runs; correct the FR-19 amendment to "wire, registered and supervised Runs whose traffic passes through Hekma".
- **high** No verb × Control Depth matrix (FR-49, FR-50, FR-56, FR-57) — `pause`, `resume`, `stop`, `hold`, `release`, `reroute`, `reject`, budget raise and each Breach Action are not mapped to depths; e.g. what does `stop` do to a `registered` Run Hekma does not own, and is `pause` on a `wire` Run a hold? FR-49's fail-fast rule is untestable without it. *Fix:* add a table to FR-49 (rows = verbs and Breach Actions, columns = depths, cells = honored / best-effort with qualifier / fails fast) and a consequence that every cell is covered by a conformance test.
- **high** `block` is coupled to Scent-Check `shadow`, weakening FR-43's own consequence (FR-43 amendment, FR-53, §13 Q9) — "block … obeys the Scent-Check Mode and policy mode: in `shadow` it records what it would refuse" conflates identity checking (Scent-Check) with budget enforcement (Breach Action). With Q9's proposed Service Host default of `shadow`, an Operator who explicitly sets `block` gets record-only behaviour, contradicting FR-43's unchanged consequence "refuses further model calls through the proxy … until the ceiling is raised or reset" (story 19-2 is still backlog, so this lands before code). *Fix:* decouple: `block` always refuses once configured; Scent-Check Mode governs only calls lacking a valid Run Key. If a dry-run mode for `block` is wanted, give it its own name (e.g. a policy-level `shadow` for enforcement) and define it in §3.
- **medium** Run status values undefined (FR-49, FR-50, FR-52, FR-54, FR-56) — "status", `held`, `silent`, "anomalous", "over-budget", "unattributed", "unscented", "stale" are used but not enumerated; "anomaly" has no definition, so FR-50's exception-first view cannot be tested. *Fix:* add a glossary entry **Run Status** with the full set and transitions (and how it relates to Lifecycle State for supervised Runs), and a glossary entry **Anomaly** listing the conditions that raise one (unscented call, bypass, breach under `warn`, expired Lease, client-ended hold).
- **medium** FR-55 is implementation-shaped and one consequence is likely unachievable (FR-55, §3 Shim, FR-41 amendment, NFR-1) — "owned by a Shim" and "journaled durably" prescribe mechanism; "a `kill -9` of the Service Host while a call is held recovers that hold" assumes the held client connection survives the process that holds it. It is also unclear whether supervised Runs survive a crash when handoff mode is off (title says they survive crashing; the opt-in bullet covers only SIGTERM). *Fix:* restate as capabilities ("a supervised Run's process outlives the Service Host"); change the kill -9 consequence to "the hold record, Run state and spend are recovered, and a client connection lost with the host is recorded on the Run as hold-ended-by-host-crash"; add a consequence stating crash behaviour with handoff mode off.
- **medium** Deferrals written as testable consequences (FR-53 last bullet, FR-58 bullets 4–5) — "Default Scent-Check Mode per environment is decided in the story spec", "Topology … is decided when the epic is detailed" and "Ships only with a dated §6 privacy amendment" are decisions or gates, not verifiable outcomes. *Fix:* move them out of the Consequences lists into a "Gate:"/"Open:" line (Q9 already carries the first); keep the `[ASSUMPTION]` tags.
- **medium** Lease and Run Key lifetimes unbounded and untagged (§3 Lease, Run Key, FR-52, FR-53) — "expires", "short-lived", "an expired Lease" have no default; FR-52's `silent` transition is untestable without one. *Fix:* add placeholder defaults (e.g. Lease 60s, Run Key 15 min) as `[ASSUMPTION]`s and index them in §14 #22.
- **low** FR-49 "deprioritized" is vague and the per-run scope resets on restart (FR-49, FR-18, §3 Run) — if each supervised process span is a new Run, a crash-looping instance gets a fresh per-run budget on each Restart Policy relaunch. *Fix:* drop "deprioritized" or define it; add a consequence that a Restart Policy relaunch either continues the same Run or is bounded by the cumulative budget, stated explicitly.

## Scope honesty — adequate

The scope work is mostly honest: §8 is re-confirmed and closes Q5, "Org governance … is later, not v-next" is explicit, Hub federation and trace export are gated on dated §6 amendments, and all four new inline `[ASSUMPTION]` tags are indexed. Three omissions are silent rather than explicit. Key custody (FR-53) is a security promise made against NFR-6's unchanged "not a security sandbox … v1 must not imply it" and its `[NOTE FOR PM]` that sandboxing needs "real security review"; §8 frames key custody and bypass detection as the *exception* to "No security sandboxing claim", which invites reading them as one. FR-51 adds identity headers to forwarded calls — run ids and possibly labels leaving the machine to a provider or gateway — with no §6 note. And the Control API is now reachable remotely (FR-51 non-loopback, FR-57 remote Service Host, FR-58 Hub) while §3 still defines it as "local".

### Findings
- **high** Key custody makes a security claim the PRD elsewhere disclaims (FR-53, §8 last bullet, NFR-6) — "the real provider key never appears in the agent's environment, arguments or Agent Home" holds only against an agent that does not read the Service Host's state directory as the same OS user; FR-2 isolation is explicitly not a sandbox. *Fix:* reword §8 to "No security sandboxing claim (NFR-6). Key custody (FR-53) and bypass detection (FR-54) reduce accidental key exposure and detect bypass; they are not isolation boundaries"; add an FR-53 consequence stating the threat model (protects against key leakage via env/args/logs, not against a same-user process reading Hekma's secret store) and add a `[NOTE FOR PM]` on whether key custody needs the security review NFR-6 reserves for sandboxing.
- **medium** Identity headers are a new outbound data flow with no §6 coverage (FR-51 bullet 4, §6 Privacy) — §6's default is "no telemetry leaves the machine"; adding Run identity (and possibly labels, which may carry customer names) to calls sent to a provider or gateway is data leaving the machine. *Fix:* add a dated §6 note and an FR-51 consequence: identity headers are off by default (or carry only the opaque run id), labels are never forwarded unless an allow-list is configured, and secrets/Run Keys never are.
- **low** Stale scope statements (§2.2 heading, §9.2 last bullet) — §2.2 is titled "Non-Users (v1)" but its first bullet now describes v-next; §9.2 still lists "team governance" as a §8 non-goal while §8 now says "later". *Fix:* retitle §2.2 "Non-Users" with a horizon per bullet; change §9.2 to "Hosted/web anything, org governance (later, §8), sandboxing".

## Downstream usability — thin

This PRD is chain-top (architecture spine, epics.md and sprint-status already consume it), so glossary precision matters. The new terms are well-formed, but the old governance terms were not widened to match FR-49's "budgets apply per Run at every depth": Token Budget, Usage Ledger, Metering Source, Fleet and Adapter are all still scoped to "an Agent Instance", while wire and registered Runs have no Agent Instance and no Adapter. "Policy" is load-bearing across §4.14 (Description, FR-49, FR-53, FR-43 amendment's "policy mode", Q11) and has no definition. Task is retired in §3, but FR-43's and FR-45's testable consequences still say Task — story extraction will pick up the stale lines and miss the blockquote.

### Findings
- **high** Task absorbed into Run without defining Run nesting (§3 Run, FR-43 body + amendment, FR-49) — FR-43 promised per-Task budgets "alongside the per-Run and cumulative ones"; the amendment makes a Host unit of work a Run, and §3 makes a supervised process span a Run too, so one process now holds a process-span Run and Host-created Runs with no stated relationship. It is undefined whether usage counts against both, which budget breaches first, and what `stop` on the inner Run does. *Fix:* add a `parent run id` to the Run definition (a Host- or self-announced Run inside a supervised process is a child Run); add FR-49 consequences: usage attributes to the child and rolls up to the parent; every ancestor's budgets apply; a verb on a child never affects its parent's process.
- **medium** Governance glossary terms still scoped to Agent Instance (§3 Token Budget, Cost Cap, Usage Ledger, Metering Source, Adapter, Fleet; FR-49, FR-50) — "a ceiling on tokens an Agent Instance may consume", "the Engine's per-Agent-Instance record", "declared by its Adapter", "all Agent Instances". *Fix:* amend each to "an Agent Instance or Run"; state that a Run without an Adapter has Metering Source `engine-observed`; redefine Fleet (or add a term) as the set of Runs a Service Host or Hub governs, and say whether `hekma ps` is the Fleet listing of FR-4 and NFR-4.
- **medium** "Policy" undefined (§4.14 Description, FR-43 amendment "policy mode", FR-49, FR-53, Q11) — Scent-Check Mode is "per policy", Runs are acted on only by "a configured policy", and Q11 asks how policies version; the noun has no scope, owner or shape. *Fix:* add a glossary entry **Policy** (operator-set configuration bound to a Selector, carrying Scent-Check Mode, Breach Actions and budgets) and remove "policy mode" or define it.
- **medium** Task still in testable consequences (FR-43 bullets 1 and 4, FR-45 statement) — the blockquote says "FR-45's 'Run or Task' reads 'Run'" but the FR text is unedited. *Fix:* strike Task in the consequence lines themselves (keep the blockquote as provenance), so a story citing FR-43 bullet 1 gets the current rule.
- **medium** "Caller" undefined in the loosen-limits rule (§4.14 Description, FR-53 bullet 4) — under the §4 Actor note a Host has every Operator capability through the Control API, so it is unclear whether a Host is a "caller" that cannot lower Scent-Check Mode. *Fix:* define caller as "an agent process or framework acting through request headers, OTel attributes or self-announce", and state that the Operator and Host set limits through configuration or the authenticated Control API.
- **medium** Control API and Service Host still defined as local (§3 Service Host, Control API; FR-51, FR-57, FR-58) — FR-57 points at "a remote Service Host or Hub"; FR-51 serves non-loopback. *Fix:* amend both glossary entries: "local by default; remote binding requires authentication (FR-41, FR-51)".
- **low** `block` configurable where it cannot act (FR-21, FR-43) — FR-21 lets any Agent Instance choose `block`, but `block` acts only at the proxy; a self-reported Instance has no proxy path. *Fix:* add a consequence: choosing `block` for an Agent Instance or Run with no wire path fails at configuration time, naming the Metering Source or Control Depth.

## Shape fit — adequate

A developer product with an embeddable engine: capability-spec FRs plus a few named-protagonist UJs is the right shape, and §4.14 follows it. Two drifts. FR-55 and FR-58 specify architecture (Shim ownership, journaling, Node roll-up, "the Hub never needs per-call records") inside FRs — acceptable as constraints only if the PRD says why the product needs them; otherwise they belong in the architecture spine. And the new audience lacks the UJ the shape calls for (covered under Strategic coherence).

### Findings
- **medium** Architecture inside FR-58 (FR-58 bullets 1–2) — "a Hub merges Node summaries" and "Nodes roll up locally and the Hub never needs per-call records" are design choices. *Fix:* restate as capabilities ("one listing and one verb surface across machines; listing never depends on per-call data leaving a Node") and move the roll-up design to the architecture spine.
- **low** Undefined epic and theme references inside requirements (NFR-4 "Epic 24 benchmark", §6 "Epic 24" trace export, §8/§2.2 "themes D/F", §3 Run "AD-7", Q10 "Epic 21") — "themes D/F" appears nowhere else in the PRD; Epic 24 is cited both as the scale benchmark and the trace-export epic, while §12 puts scale near the end of the order. *Fix:* replace epic/theme numbers with FR or horizon names, or add a one-line horizon map in §9.3 (Epics 21–25 → FR sets; themes D/F → org governance and audit).

## Mechanical notes

- **ID continuity.** FR-49..FR-58 are contiguous and unique; no gaps after FR-48. Q9–Q11 continue §13 numbering. Cross-references resolve: FR-41 → FR-55, FR-43 → FR-49/53/54, FR-56 → FR-43/50, FR-57 → FR-50, FR-53 → FR-14 and §13 Q9.
- **Assumptions Index roundtrip.** All four new inline tags (FR-52 frameworks, FR-53 Scent-Check defaults, FR-57 2s refresh, FR-58 Hub-first) are indexed in §14 #22. Gaps: §14 #12 still describes FR-19 as "metering mandatory" without noting the 2026-10-30 amendment for wire/registered Runs; the new NFR-4 Run counts sit after #17's tag and are only implicitly covered; Lease and Run Key lifetimes have neither a value nor a tag; §14 #7 is correctly superseded.
- **Glossary drift.** "run" lowercase in §1 ("observe a run", "every run shows") and "fleet" lowercase vs §3 Run/Fleet; "OpenCode" (§1, FR-48) vs "opencode" (§3, §13 Q1). Terms used but not in §3: virtual provider key, key custody, handoff mode, identity header, unscented, unattributed, anomaly, held, stale, policy / policy mode, caller. Three names for one interception point: "metering proxy" (FR-43), "Hekma proxy endpoint" (FR-51), "interception point" (FR-19) — pick one and define it.
- **Shim cardinality.** §3 says "per-Run process owner" while §3 Run says "one process may host many Runs"; a Shim owns a process, not a Run. Fix to "per supervised process".
- **Lease scope.** §3 Control Depth attaches a Lease only to `registered`; §3 Lease and FR-52 give one to `wire` Runs too. Align the Control Depth entry.
- **Wire discovery vs enforce.** FR-51 "traffic with no identity is listed as unattributed rather than dropped" should add "unless Scent-Check Mode is `enforce`" (FR-53).
- **Confirmation over the Control API.** FR-50's multi-match confirmation (`--yes`) has no stated Control API equivalent, and FR-34 forbids prompts in the Engine; say the API requires an explicit match-count or `dry_run` token instead.
- **Required sections.** All present; §11 has no metrics for the FR-49..FR-58 horizon (tracked as Q10, raised above).
- **UJ protagonists.** UJ-1..UJ-3 are named; the new framework-team JTBD has none.
