## Intent

**Problem:** The three Scent-Check Modes exist only as data. Since 21-3 every Policy row carries `scent_check`, the one pure resolver resolves it through the tie order (`off` < `shadow` < `enforce`), and the stored per-Run resolution and the published snapshot carry it — but create/change refuses `shadow`/`enforce` with `scent-unavailable`, so no Operator can set a mode, nothing on the data path reads the resolved value, and PRD §13 Q9 (the default mode per environment) is undecided. The shared proxy (23-1) serves every call that has an upstream, whether or not it carries an identity; it refuses unknown and revoked Run Keys unconditionally, and nothing reconciles that with `shadow`'s "serve a call with no valid identity and record it as an unscented Anomaly". There is no unscented Anomaly, no OTLP counter, no typed `enforce` refusal, and a Caller has no way to tighten its Run's mode (FR-53: "A Caller cannot lower the Scent-Check Mode" — implies it can raise it; the Caller limits layer drops the field today).

**Approach:** Lift the `scent-unavailable` refusal and make the resolved mode act at the proxy, per call, reading only the snapshot. **Scented** := the call's attribution came from a valid Run Key Hekma issued (23-1's `x-hekma-run-key`, or the API-key slot under 22-2's custody swap); **unscented** := the call was attributed without one — a labelled binding's Run, a split, the unattributed Run, or an engine-made Run route — exactly the paths the PRD Glossary already says are "not a Scent-Check identity". The **effective mode is the strictest over the attribution Run's ancestor chain** (the `disposition_over` pattern, ≤ 8 levels), so a Caller-opened child under an `enforce` parent is `enforce` (T9.2). `off` serves (today's behaviour, byte for byte). `shadow` serves and raises the `unscented` Anomaly on the attributed Run — set once by the store writer's close job, one `anomalies-changed` event, cleared when a re-resolution moves the Run off `shadow` — plus per-call counting. `enforce` refuses with the new typed `401 hekma_unscented_call` (a `proxy-wire v1` row: static body naming how to obtain an identity, `x-should-retry: false`), never forwarded, the request body drained without buffering, a per-call record with disposition `enforce`. **Unknown and revoked Run Keys keep 23-1's typed 401s under every mode** (the O6 reconciliation, Ask First O4): a presented-but-invalid credential is a failed authentication with a more useful answer than "unscented", and refusing it is tighter than the review's literal serve-under-`shadow` row while satisfying its intent — R3.8's "never with the custodied key" holds because the call is never forwarded at all, under every mode, preserving 22-2's "under every Scent-Check Mode" P4 rule. The mode governs identity only: Breach Actions, the 402 fence and its safe-method exemption are untouched, and the fence is checked first (R3.3). A Caller tightens its Run's mode through the limits route (`scent_check` in the Caller layer, applied only where tighter; a lower attempt is refused; Operator/Host set modes on Policies — the limits route refuses the field for them with a remediation). **Q9 is decided as `off` everywhere** (Ask First O1): one environment-independent default, recorded in the default Policy's seed — which 21-3 already seeded `off`, so the upgrade writes nothing and an Operator-edited default Policy is untouched by construction (R3.6); "environment" is retired — differences live in the Operator's own Policies, not in code. The unscented OTLP counter lands with `otlp-metrics v2` (24-5), per 22-1's precedent that no new event family gains a v1 counter. No schema step; hekma-engine stays 0.12.0.

## Design Notes

- **What this story owns, and the rulings it builds on.** FR-53 (ruled 2026-10-30) fixes the modes and their semantics; AD-25 fixes the resolution (the default Policy seeded `off` "until story 22-3 decides PRD Q9 — 22-3 never overwrites a default Policy the Operator has edited"); AD-26 fixes that binding-Run and unattributed calls "are refused under `enforce`" and that the wire contract is versioned. The security review is draft for ruling (AI-58): this spec copies its §9 R3.1–R3.8 and builds on P4's rule (custody only for issued credentials — mode-independent, already honoured because an unscented call is never custody-eligible). Where this spec departs from a literal reading, it is an Ask First O-item (O4, O6, O7) and the matching criterion follows a different ruling.
- **Scented vs unscented, precisely.** A call is **scented** iff a valid Run Key identified it (23-1's `x-hekma-run-key`, or the API-key slot — which 22-2 turns into the custody swap; both are "the supervised Run's Scent-Check identity" per the spine's rubric line, so a custodied Run is never unscented). Everything else the proxy serves today is **unscented**: a labelled binding's Run, a split beneath it, the unattributed Run, and an engine-made Run route (`/_hekma/runs/<id>`) reached with no key — the Glossary already says a binding "is not a Scent-Check identity", and the Run route is the same class of engine-chosen attribution (any local process can present either). Hints do not change scent: beneath a key the child is scented; beneath a binding or the unattributed Run the split stays unscented. A proxy-access credential is not a Scent-Check identity (R5.4 — its row is reserved for 22-5); a credentialed announce will be scented and an uncredentialed announce-header Run unscented (23.2 — reserved rows, tested when they exist).
- **The O6 reconciliation (O4).** 23-1's O6 accepted "refuse unknown and revoked Run Keys now", noting 22-3 reconciles them with `shadow`; the review's R3.1 lists them among the mode-governed caller states and R3.8 says under `shadow` such a call is "forwarded with the client's own header". This spec keeps the refusals under **every** mode: a presented-but-invalid credential is failed authentication, not missing identity — the client's useful answer is "your key is unknown/revoked" (the recently-revoked set exists precisely to say stop retrying), not an unscented refusal; and refusing is tighter than serving, so custody safety is unaffected (R3.8's intent holds trivially: the call is never forwarded, under every mode — 22-2's "under every Scent-Check Mode" wording is preserved with room to spare). Cost: a `shadow` Operator does not see unknown-key traffic as Anomalies — it sees it in the refusal counters, which is the truer signal. If Islam rules the review-literal reading, the two matrix rows change to "served + unscented (forwarded with the client's own header)" and nothing else moves.
- **The effective mode over the chain (T9.2, R3.4).** Policies resolve per Run from its own bound labels; a Caller-opened child resolves Policies its parent's labels never select, so a child could land on a looser default. The enforcement read is therefore the strictest mode over the attribution Run's ancestor chain (`scent_over`, mirroring `disposition_over` — a ≤ 8-level walk over stored resolutions already in the snapshot; `Off` where an entry has none). The stored per-Run resolution is unchanged (the chain rule is a reader rule, like the fence); the limits answer surfaces the Run's own effective value.
- **Where the check sits, and ordering.** After identification, Run resolution, the permit and the fence check — the same place the fence sits — and before the call-start record and any upstream dial. Fence first: a fenced Run's 402 is the Operator's loud, latched signal and wins over the 401 (R3.3's decoupling runs both ways). No safe-method exemption: `block` exempts GET/HEAD/OPTIONS because they carry no billable completion; identity is method-independent, so `enforce` refuses them too (documented beside the fence's exemption). The refusal mirrors the fence's mechanics: body drained (or refused without buffering, honouring `Expect: 100-continue` exactly as the fence does), record written with disposition `enforce`, never forwarded.
- **The unscented Anomaly.** Stored, not derived: the close job of the first unscented call under `shadow` sets `unscented` on the attributed Run in the same transaction as the call's usage row, one `anomalies-changed` event (the existing ownership pattern — `store_changes` owns `DepthFallback`/`UnpricedModel` the same way); repeated calls are no-ops; every re-resolution clears it unless the Run still resolves `shadow`. On the unattributed Run it reads as "traffic on this host is arriving without identities" — the honest reading. It never acts (FR-Glossary: an Anomaly never acts on a Run by itself); `enforce` is the refusal, not the Anomaly.
- **Signals and their bounds (R3.5, T9.5).** The unscented count surfaces on: the Anomaly (per Run), the proxy's atomic counters (`unscented_served`, `unscented_refused` — added to the once-a-minute refusal note, which is already rate-limited), and the per-call record for refusals (disposition `enforce`). No client-supplied string or token is ever a label, key or log value; refusal bodies are static. The **OTLP counter lands with 24-5** (`otlp-metrics v2`): the v1 exporter observes only the event bus, per-call records are not events, and 22-1 set the precedent that no new family gains a v1 counter — a per-call event would be the flood T9.5 warns against. Recorded in deferred-work with the trigger; FR-53's counter exists at the epic level when 24-5 ships.
- **Caller tighten (R3.4, FR-53, FR-60).** The limits route gains `scent_check` as a Caller-scoped field: the resolver's Caller layer (`caller_policy_limits`) now carries it and applies it only where tighter (`scent_tightness`), exactly as it treats ceilings; the route refuses a lower value with the caller-refusal class ("a Caller cannot lower the Scent-Check Mode") — the mirror of 21-6's `raise-forbidden` for ceilings. Operator and Host set modes on Policies (FR-53's "set per Policy"); sending the field under their authority is `422` with the remediation, not a silent second surface. A Caller's tighten is visible in the write's answer (which carries the effective mode) — no new read route, keeping AD-20's "nothing else" (O3). The child chain picks the tighten up through `scent_over`.
- **Q9, decided as `off` (O1/O2), and the environment's retirement.** The PRD's proposal — `off` for a laptop CLI, `shadow` under the Service Host — predates two facts: every CLI write now routes through a local Service Host (FR-41), so "environment" no longer names two distinguishable states; and P4 (custody only for issued credentials) removed shadow-by-default's original purpose, since with P4 **no mode weakens custody** (T9.6 — the review has no security objection to `off` or `shadow`; `enforce` by default would refuse calls nobody asked to refuse, against NFR-9's spirit). `off` everywhere also makes the R3.6 upgrade trivially true: 21-3 already seeded `off`, so this story writes nothing at upgrade and an Operator-edited default is untouched by construction — a `shadow` ruling would need an edited-marker and an upgrade write for seed-shaped defaults, a real cost recorded in O2. "Environment" is retired: differences are the Operator's own Policies (a `shadow` Policy on `env=prod`, an `enforce` Policy on a labelled binding), which is where FR-60 already put standing configuration. The PRD §13 Q9 entry, FR-53's Gates assumption and AD-25's "until story 22-3 decides" clause close with Islam's ruling (his edits, the AI-58 discipline; this spec records the decision).
- **No schema step; version.** `policies.scent_check` (v15), `run_policy.scent_check`, the snapshot's `RunEntry.policy` and the anomalies comma-list all exist; `CallDisposition` has no CHECK in the calls store; the Anomaly and disposition values are data-only. New public surface: `Anomaly::UnscentedCall`, `CallDisposition::Enforce`, `WireError::UnscentedCall` (internal), the limits-route field, the CLI flag; removed: `RunError::ScentUnavailable` and its mappings — breaking within the unreleased 0.12.0, announced in the Unreleased banners (AI-55). hekma-engine stays 0.12.0 (the cycle rule). No new dependency.
- **Threats considered** (review ids in brackets):
  - Scent-Check read as access control [T9.1, R3.7] → the docs carry §10's line: attribution, not authentication; on loopback any process can obtain an identity; custody's protection comes from P4, whatever the mode;
  - a Caller lowering the mode, or escaping it via a child [T9.2, R3.4] → tighten-only at the route, only-where-tighter in the resolver, the strictest-over-the-chain read;
  - a revoked or unknown key gaining custody under `shadow` [T9.3, R3.8] → never forwarded at all under every mode (stricter than the review's serve-with-client-header row);
  - the mode changing a Breach Action [T9.4, R3.3] → no shared code path; the fence is checked first and byte-identical under every mode; proven by the action × mode table;
  - flooded Anomalies, events or counters [T9.5, R3.5] → set-once Anomaly, one event, atomic counters, one diagnostic per minute, static bodies, no client strings as labels;
  - the Q9 default weakening custody [T9.6] → with P4 no mode weakens custody; `off` default refuses nothing new;
  - `enforce` breaking pre-custody supervised metering (engine-observed agents whose base URL is a Run route) [O6] → accepted and documented: the remediation is 22-2 custody or presenting `HEKMA_RUN_KEY` (already delivered to every supervised agent); `off` default means nobody trips it by upgrade;
  - an `enforce` refusal confused with the fence → distinct status/type/body (401 vs 402), both in the wire table;
  - timing or content leaks in the refusal → static body, drained-not-buffered request, `R3.2`'s no-echo rule.
  Out of scope, with the review and the seams: custody's swap and eligibility (22-2), the Host/Origin guard (22-2), announce states (23.2), hold re-validation (23.4), TLS and proxy-access acceptance (22-5), bypass detection (22-4), per-call read surfaces (19.4), proxy metrics (24-5).
- **What 22-3 does NOT do.** No new credential class or mint (22-1); no custody change — the swap, eligibility and the API-key-slot verdict are 22-2's and are untouched (O4 keeps 23-1's slot refusal for the ineligible case); no announce header or endpoint (23.2); no hold/release/reroute/reject (23.4); no non-loopback or proxy-access behaviour (22.5); no OTLP counter before v2 (24-5); no `scented` column or read surface over per-call records (19.4); no Run-level Operator scent limit (Policies are the Operator surface — a Run-level override would extend the resolver chain for no named need); no per-OS work.
- **Deferrals and the deferred-work trigger naming this story.** The 21-3 entry ("Scent-Check behavior does not exist … Trigger: story 22.3") resolves here. New entries: the unscented OTLP counter (trigger 24-5); the `scented` per-call field and unscented filtering on the Host read surface (trigger 19.4); the reserved matrix rows (credentialed/uncredentialed announce, proxy-access) with their triggers (23.2, 22.5).

## I/O Impact Matrix

**The mode matrix (loopback proxy, after 22-2's seam: the API-key-slot verdict is custody's).** "Served" = forwarded under the route/binding's upstream with the client's own credential headers (never a custodied key — P4):

| Credential state on the call (attribution) | `off` | `shadow` | `enforce` |
|---|---|---|---|

## Ask First

Each is a public-contract or product choice; the recommendation is the spec's current text. **O-items are the owner's (Islam's) rulings** — Q9 is his question, the security review's readings are reserved to him, and anything that changes a public contract needs his confirmation; the numbered items are the orchestrator's. Until ruled, the build proceeds on the recommended option and the PR stays unmerged past review.

- **O1. PRD §13 Q9 — the default Scent-Check Mode, and the "environment" it is per.** The PRD proposed `off` for a laptop CLI, `shadow` under the Service Host, `enforce` opt-in, and ruled (interim) that the default Policy seeds `off` until this story decides. Options: (a) `off` everywhere as one environment-independent default, "environment" retired — differences live in the Operator's Policies (recommended: FR-41 made every CLI write ride a Service Host so the two environments are no longer distinguishable; P4 means no mode weakens custody, so shadow-by-default buys little (T9.6); `enforce` by default would refuse calls nobody asked to refuse, against NFR-9; and `off` needs no upgrade write — the seed already says it); (b) `shadow` whenever a long-running host owns the data path, `off` for ephemeral auto-starts (closest to the PRD's proposal, but the mode would flip with host topology and needs an upgrade write for un-edited defaults); (c) `shadow` everywhere (the loudest default; same upgrade-write cost, plus Anomaly noise for every pre-custody call). `enforce` is never a default under every option. Meanwhile: (a).
- **O2. What the decided default means for existing installs.** Options: (a) no upgrade write at all — the seeded `off` already records an `off` ruling, and an Operator-edited default Policy is untouched by construction (recommended with O1(a): R3.6's "never overwrite an edited default" is trivially true); (b) if O1 rules `shadow`/`enforce`: write the new default into every default Policy still in its exact seed shape (needs a recorded edited-marker 21-3 never wrote — an added mechanism and a real overwrite risk the interim ruling warned about). Meanwhile: (a).
- **O3. May an agent (a Caller holding a Run Key) see its own Run's `scent_check` mode?** The decisions record carries it open: AD-20's matrix gives a Run Key "tighten limits — nothing else" (no read route — 22-1 pinned `GET /v0/runs/{id}` refused), yet R3.4's tighten is hard to use blind. Options: (a) no new read route; the limits write's answer carries the effective mode after a tighten (recommended — AD-20's "nothing else" stands, the Caller learns the mode exactly when it acts on it, zero new surface); (b) open `GET /v0/runs/{id}` to a Run Key's own subtree (an AD-20 amendment — a real read surface for one field); (c) nothing at all (the tighten is fully blind). Meanwhile: (a).
- **O4. How 23-1's "refuse unknown and revoked Run Keys" reconciles with `shadow` (its O6).** Options: (a) the mode governs only no-credential attribution; unknown and revoked keys keep their typed 401s under every mode (recommended — 23-1's shipped responses unchanged; the revoked client is told to stop retrying, which the recently-revoked set exists for; refusing is tighter than the review's serve-under-shadow row, so R3.8's never-custody intent holds with room to spare); (b) the review-literal reading (R3.1/R3.8): unknown and revoked keys are unscented — served with the client's own header under `off`/`shadow`, refused with the unscented body under `enforce` (the matrix rows change; nothing else moves). **Public contract either way** — confirm.
- **O5. The `enforce` refusal's wire shape: `401`, `error.type hekma_unscented_call`, `code unscented_call`, a static body naming how to obtain an identity, `x-should-retry: false`** — a `proxy-wire v1` addition (public contract — confirm). Alternative: `403` (policy rather than authentication); 401 is recommended because the client's remediation is to present a credential. Neither is retryable.
- **O6. An engine-made Run route (`/_hekma/runs/<id>`) with no Run Key counts as unscented** — so `enforce` refuses pre-custody engine-observed agents' calls until 22-2 custody or a presented `HEKMA_RUN_KEY`.
