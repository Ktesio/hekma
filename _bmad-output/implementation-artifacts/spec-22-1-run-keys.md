## Intent

**Problem:** A Run has an id, labels, budgets and a status, but no credential of its own. The Control API has one credential class (the operator/Host bearer), so nothing a Run's own process holds can act on that Run — an in-process framework cannot open a child Run beneath itself without the Operator's bearer, and FR-43's child attribution has no carrier. Every later identity story (the shared proxy's identification, key custody, Scent-Check, announce, the proxy beyond loopback) needs one token format, one hash-at-rest rule, one revocation path that the data path sees on the next call, and one authority matrix row per class. None of it exists, and the security review (2026-11-02) found that AD-22 as written cannot re-deliver a hash-only key to a relaunched process.

**Approach:** A credential module in the engine core mints `hk_run_` / `hk_ref_` / `hk_ann_` tokens — 256 bits from the OS CSPRNG (fail closed, no fallback), Crockford base32, held in `SecretString` from mint to delivery — and stores only their SHA-256 in a new `tokens` table (schema v17) with a 12-hex token id as a display label. A supervised launch mints a **Run Key per launch generation** (security review P1): delivered once through the reserved `run.key` leaf to the agent's environment (`HEKMA_RUN_KEY`, Env targets only), committed with the launch record, revoked when that process is confirmed exited and when the Run ends; adoption and reattach change nothing. A Control API child open returns the child's Run Key and a refresh credential once. A refresh is single-use with reuse detection (P3). Operator revocation (`hekma run revoke-keys`) cascades to keys minted under the revoked ones. Every issue, rotation and revocation commits with an outbox event in the writer's transaction and is published in the snapshot's hash → Run index before it is acknowledged. The host's credential resolver gains the Run Key, refresh and announce classes, and the authority matrix becomes per route family: a Run Key may open, close and tighten only within its own Run's subtree, as a Caller. Run Keys never travel in a URL, never land in a file, an argv, a log, an event or a read surface, and the URL rule is enforced on the Control API and on today's per-instance listener. Key custody (the Run Key in the API-key slot), Scent-Check behaviour and the shared proxy's lookup stay with their own stories.

**Acceptance Criteria:**
- Given a mint of each class, then the token is its prefix plus exactly 52 Crockford base32 characters, two mints never collide across 10,000 draws, the stored row holds only the 32-byte hash and the token id (the first 12 hex of the hash), and `Debug` of the minted value, the launch spec, the issued-credentials struct and a parsed presentation shows no token; given the RNG seam failing, then a supervised start is refused with a typed error naming the random source, no process spawns and no row, event or snapshot entry changes.
- Given a supervised start, then the agent's environment carries `HEKMA_RUN_KEY` (and nothing in its argv or Agent Home does), the key authenticates on the Control API as a Run Key of that Run once the launch record has committed, `effective-config.json` and `config get` show no token (the reserved leaf renders as `run-key:<token id>` where it renders at all), and a manifest mapping `run.key` to a `File` or `Flag` target is refused at registration naming the key and the remediation.
- Given two forced Restart Policy relaunches of one Run, then each launch carried a different Run Key, the first two are refused (`credential-revoked`) and the third works, the run id, budgets and labels are unchanged, each launch's key was revoked in the job that recorded its process's exit (cause `process-exited`), and an engine restart that re-adopts the live process leaves its key valid (no credential change).
- Given an Operator stop that ends the Run, then every remaining active token of the Run is revoked in the same job (`run-ended`) and the snapshot no longer holds it; child Runs that outlive the end keep their own keys.
- Given `POST /v0/runs` with the operator bearer, then the 201 carries `credentials {run_key, refresh_credential, token_id}` exactly once (no later read — `GET /v0/runs/{id}`, `GET /v0/runs/{id}/keys`, the listing, SSE, export, CLI `--json` — returns either value); with `issue_credentials: false` none is minted; `hekma run open` without `--print-key` mints none and prints none, and with it prints both once with a stderr note that they are not shown again.
- Given a supervised Run's Run Key as bearer, then it may open a child under its own Run or a descendant (the child's labels are Caller labels; its own Run Key and refresh credential come back once), close a descendant child, and tighten limits on its subtree through the limits route as a Caller; raising a ceiling is refused (`raise-forbidden`); acting on a sibling, a parent or an unrelated Run is `403 run-out-of-scope`; every other route (fleet, instances, config, labels, Policies, listing, run show, events, export, revoke-keys, keys) is `403 forbidden`; a refresh credential is accepted only on `POST /v0/runs/refresh`; an announce credential (minted by a test seam) is refused everywhere — the table-driven class × route-family matrix pins every cell.
- Given a Run Key opening its 1,001st open child beneath one parent, then it is refused `409 too-many-children`; the Operator bearer is not capped.
- Given a refresh with a Run's active refresh credential, then the response returns a new Run Key and a new refresh credential once, the old Run Key is refused on the next request, and the used refresh credential is retired; presenting the retired refresh credential again revokes the Run's current Run Key and refresh credential (`refresh-reuse`), sets the `credential-reuse` Anomaly on the Run (listed by `hekma ps`), emits `reuse-detected`, and answers `401 credential-revoked`; an Operator `revoke-keys` on that Run clears the Anomaly.
- Given `hekma run revoke-keys <RUN>` (cascade default), then the Run's active tokens and every active token minted under them (a child opened with the revoked Run Key, that child's refresh chain) are revoked, the command reports each by run id, class and token id, and a Control API request presenting any of them sent immediately after the command returns — no sleep — is refused; with `--no-cascade` the children's keys stay valid; the revocations survive a `kill -9` of the Service Host and a restart.
- Given a Run-Key-authorized open whose authentication passed but whose token is revoked before its writer job runs (a test barrier), then the job refuses `credential-revoked` and nothing it would have written exists; a job that committed before the revocation stands.
- Given a token in a Control API path or query (`/v0/runs/hk_run_…`, `?key=hk_run_…`, percent-encoded), then the answer is `400 credential-in-url` with a static body and, when it names an active token, that token is revoked (`exposed-in-url`); given the same on the per-instance metering listener, then the upstream fake receives nothing and the agent gets the typed `hekma_credential_in_url` 400; a request carrying `x-hekma-run-key` reaches the upstream fake without that header.
- Given the operator bearer on a Run-Key-only route (`POST /v0/runs/refresh`), then `403 forbidden`; given a supervised Run's Run Key on a non-loopback `--listen` listener, then `401 unauthorized`; given an unknown token, then `401 unauthorized` and given a revoked one `401 credential-revoked`, both with static bodies that echo nothing; 1,000 unresolved presentations produce at most one diagnostic per minute and no token in any log.
- Given the scenario mint → use → refresh → revoke → `kill -9` → restart, then a byte scan of `state.db`, its `-wal` and `-shm`, every log, every Agent Home, `control.json`, `serve.log` and the spawn record finds no sentinel token (before and after a WAL checkpoint), and the no-leak matrix (stdout, stderr, `--json`, engine and instance logs, `breaches.log`, events, outbox, SSE, every Control API response but the one-time ones, OTLP payloads) carries no Run Key, refresh or announce token — only token ids.

## Design Notes

- **The rulings this spec builds on, and who owns them.** AD-22 (ruled by Islam 2026-10-30) fixes the format, the hash, the token id, Env-only delivery, no clock expiry and possession as the binding. The security review is **draft for ruling** (AI-58: Islam picks; nothing in the spine or PRD is edited by this spec): this spec builds on its recommended options P1 (a Run Key per launch), P2 (no refresh credential for a supervised agent unless its Adapter maps one), P3 (single-use refresh with reuse detection), P5 (supervised keys stay local), P8 (the masking mechanism) and P12 (token ids are labels), and records P4's custody-eligibility flag at mint without acting on it. Each is Ask First O1–O7. If Islam rules otherwise the matching AC follows the ruling. P1, P2 and P3 change PRD FR-53 and Glossary wording ("valid for the Run's life", "a refresh from any other process fails") and AD-22's text; those edits are Islam's to make after the ruling, and the spec does not wait on them to be approved.
- **Generation and entropy.** 32 bytes from `getrandom` (already the engine's source for ULIDs). `RunId::mint` falls back to the clock on an RNG error because an id is not a secret; a token never does — the error refuses the start, the open or the refresh before anything is written. Crockford base32 (the `RunId` alphabet, no padding) gives 52 characters; with the prefix a token is 59 bytes. No checksum suffix: AD-22 fixes the format, and the `hk_` prefixes are distinctive enough for secret scanners (registering them with GitHub's secret scanning is a follow-up, not code).
- **Hash, lookup and "the lookup prefix".** The store keeps an unsalted SHA-256 of the whole token (AD-22: a 256-bit random token has no dictionary to salt against, and the data path needs a fast lookup). Lookup is by the full hash — the `tokens` primary key and the snapshot map key. The token id (first 12 hex of the hash) is a display label for records, events, `hekma run keys` and revocation reports, never a lookup, join or uniqueness key (P12: 48 bits collide at Run scale). No part of the secret portion is stored in clear: the only "prefix" anything reads is the class prefix (`hk_run_` …), which is public structure and routes a presentation to its class before hashing. The engine hashes with its std-only SHA-256; the host never hashes a Run Key itself (one implementation on the token path). The host keeps `ring` for its own operator bearer, unchanged.
- **Constant-time comparison.** The operator bearer list keeps today's full-length, no-early-exit loop. Run Keys cannot be scanned linearly at 10M Runs, so they resolve by map lookup on the presented token's hash: the lookup's timing depends only on SHA-256 output of the presented value, which reveals nothing about any stored token (preimage resistance), and the matched entry's 32 bytes are then compared with `ct_eq` (defence in depth). Shape checks (prefix, length, alphabet) reject on public structure only. No code compares token text with `==`.
- **Display once.** The cleartext exists in exactly three places: the agent's spawn environment, the 201 of a child open that asked for credentials, and the 200 of a refresh. It lives in `SecretString` from mint to that delivery; the Control API serializes it through one greppable site (`expose_secret` in the one-time DTO); a presented bearer is wrapped on parse. No read route, event, SSE frame, export row, CLI `--json` document or log line carries it, and nothing can re-show it — a lost Run Key is replaced by a relaunch (supervised) or a refresh, never re-read.
- **The supervised launch (P1).** The Run Key is minted before spawn and delivered through the reserved `run.key` invocation-override leaf (the `metering.base_url` pattern, no Adapter Contract change): the leaf's stored value is the marker `run-key:<token id>`, the cleartext comes only from the per-launch `secrets` map at `apply_config_mapping`, and injected leaves are already kept out of `effective-config.json` (3-4's provenance split — pinned by a test here). The engine adds a default Env target `HEKMA_RUN_KEY` for every kind, so every supervised agent and its in-process helpers can act on their Run; an Adapter may additionally map `run.key` to its own Env variable (22.2 maps it into the API-key slot under custody). The hash commits in the launch-record job with the new launch generation, so a token exists in state.db only if its launch was recorded: an engine crash between spawn and commit leaves a token nobody ever honours (fail closed). The price is a short window — the startup survival window (300 ms) plus the commit — in which the agent's key is not yet recognised; it closes when the Shim commits the spawn record before launch (AD-23), and is documented.
- **Generations, exit and reattach.** The job that records a supervised process's confirmed exit (crash, stop, failure) revokes that launch's active tokens (`process-exited`), so a key lives exactly as long as its process and the previous generation is revoked before any relaunch spawns (R1.9). A Restart Policy relaunch keeps the Run and mints the next generation's key. An engine restart that adopts a live process, and later a Handoff Mode reattach, change no credential: the hash is durable and the process still holds its key.
- **Refresh (P2, P3).** Possession is the binding (AD-22; no OS attestation, and the docs say so). Control-API-opened Runs get a refresh credential paired with their Run Key. A supervised launch gets one only if its Adapter maps `run.refresh_key` to an Env target (none does today): a third-party CLI cannot swap its own API-key variable mid-process, so a refresh credential would be pure exposure, and its rotation is the relaunch. A refresh retires the used credential, revokes the paired Run Key at once, and mints a new pair on the same Run, launch generation and custody flag, `issued_by` = the retired credential. Retired credentials stay in the store so a second presentation is detected: it revokes the Run's current pair, raises `credential-reuse` and answers `credential-revoked` — a silent takeover becomes a visible one. The refresh route lets an `hk_ref_` bearer through to the engine job, which reads the store (refresh credentials are never in the snapshot: refresh is a write, and reuse detection needs retired rows).
- **Revocation and what in-flight work sees.** Every revocation commits in the writer's transaction and is published to the snapshot before the mutation returns (AD-25), so the first request after the acknowledgement is refused (R1.6) and a `kill -9` cannot undo it. Control API authentication runs once at request start against the snapshot; every Caller-authorized job re-reads its token's row inside its own transaction, so a request authenticated before a revocation but executed after it is refused with no effect, and one that committed first stands (it happened before). On demand the Operator revokes a Run's active tokens and, by default, every active token whose `issued_by` chain starts at one of them (R1.6's cascade; the walk is a recursive query over `idx_tokens_issued_by`). Revocation never ends a Run: children opened under a revoked key stay open, with their keys revoked. On the wire nothing reads a Run Key in this story (today's listener attributes by socket); the shared proxy must refuse the next call after revocation while calls already forwarded complete (23.1), and held calls are re-validated at release (23.4) — both deferred with those triggers.
- **Scope: a Run and its children.** A Run Key is a Caller on its own Run's subtree and nothing else (AD-20): open a child beneath its Run or a descendant, close a descendant child (a process-owning Run cannot be closed by anyone, the existing rule), tighten limits through 21-6's limits route as `LimitActor::Caller`. The subtree check walks the parent chain in the snapshot (≤ 8 levels) and again inside the job. Labels it sets are Caller labels through `check_caller_labels`, so they never select a Policy (FR-60). A child opened with a Run Key gets its own Run Key and refresh pair, `issued_by` = the opener, custody flag inherited. Heartbeat has no route until Leases (23.2). Reading a Run (`GET /v0/runs/{id}`) is not in AD-20's Run Key row, so it is refused; a helper reads its child's state from the open response.
- **The authority matrix (route families).** OperatorBearer → `Operator`, `RunOpen`, `RunClose`, `RunLimits`; never `RunRefresh`, never `Proxy`. RunKey → `RunOpen`, `RunClose`, `RunLimits` within its subtree, `Proxy` (no consumer until 23.1). Refresh → `RunRefresh` only. Announce → `Heartbeat`, `OtlpIntake` and creating Runs once those routes exist (23.2, 23.3); refused everywhere in this story. A class refused on a family is `403 forbidden`; a Run Key outside its subtree is `403 run-out-of-scope`. The matrix is one table in `auth.rs`, pinned cell by cell (R1.11).
- **Supervised keys stay local (P5).** A supervised Run's key has no legitimate network use: on a non-loopback `--listen` listener (TLS, since 21-4) it is answered as unrecognised. Run Keys of Control-API-opened Runs are accepted there. The router knows which listener it serves; no per-request peer address is needed.
- **Never in a URL, never in a file or argv.** The Control API scans the raw path and query (and its percent-decoded form) for a token prefix followed by token characters before authentication and answers `400 credential-in-url`; a token so exposed has reached access logs, so if it is active it is revoked (`exposed-in-url`). Today's per-instance listener gets the same rule with a typed `proxy-wire v1` body, and strips `x-hekma-run-key` (AD-26's header) so a helper that already sends it never leaks it upstream. Delivery is Env only: a `File`/`Flag` mapping of `run.key`/`run.refresh_key` is refused at registration, and config writes of either key are refused at every layer.
- **Expiry.** None on a clock (AD-22, ruled 2026-10-30: agents do not refresh an API key mid-run). A key is bounded instead by its process (revoked at exit), its Run (revoked at end), a refresh, an Operator revocation and URL exposure. A supervised Run can last months; the docs say so, and the Run's budgets bound what its key can spend.
- **The snapshot index.** `RunSnapshot.keys` maps hash → `KeyEntry` for active Run Keys and announce credentials of non-ended Runs, published by the store writer only, loaded at open, and carried in the same post-commit hook as the Run entries a job changed. `Engine::authenticate` reads it lock-free with no SQLite (AD-25). `custody_eligible` is recorded at mint (supervised start and Operator/Host opens true; Caller opens inherit) so 22.2's P4 rule needs no backfill; nothing reads it yet. A second engine on the same state dir (an embedder beside `hekma serve`) publishes its own snapshot, so a revocation it commits reaches the host's snapshot only on reload — harmless here because every Run Key action is a write that re-validates in the store, and recorded for 23.1, whose proxy reads only the snapshot.
- **Audit.** One `credential` event per token per change (`issued`, `rotated`, `revoked`, `reuse-detected`), committed with its outbox row in the job that made the change, on the bus and SSE (the Selector filter matches its Run). The OTLP v1 exporter ignores it (no new counter before `otlp-metrics v2`). Unresolved presentations are not events (no outbox flood): the host counts them and emits at most one diagnostic per minute naming counts by class prefix.
- **Breadth.** A Run Key can now create Runs, so T1.9 is live here: Caller opens are capped at 1,000 open children per parent (`MAX_CALLER_OPEN_CHILDREN`, the house set cap); the Operator and Host are not capped. 23.2 revisits the bound with announce.
- **Upgrade.** v16 → v17 is additive DDL, one-way (an older binary refuses it). Nothing is backfilled: a Run live at upgrade cannot be handed a key (its environment is fixed), so it runs without one until its next launch, and `hekma run keys` says it started before Run Keys. Nothing depends on a Run Key yet — Scent-Check stays `off` and refuses other modes until its story (21-3's `scent-unavailable`, untouched; PRD Q9 is not decided here), and custody is not built — so no running agent changes behaviour. If 21-6 or another story lands a schema step first, take the next number; 21-6's spec adds none.
- **Version.** New public types (`TokenClass`, `CredentialMatch`, `IssuedCredentials`, `OpenedRun`, `RunActor`, `CredentialEvent`, `CredentialSummary`, `RevokeOutcome`), new `EngineEvent`, `Anomaly` and `RunError` variants, new facade methods, schema v17: hekma-engine **stays 0.12.0** (the orchestrator's rule for this unreleased cycle; the semver baseline already permits breaking changes at 0.12), announced in the Unreleased banners. No new dependency: `getrandom` and the std-only SHA-256 are in the engine, `ring` in the host.
- **Threats considered.** Each names its mitigation here (review ids in brackets):
  - weak or failed RNG [T1.1] → `getrandom`, fail closed, no fallback;
  - token recovered from state.db, a backup or WAL residue [T1.2] → the cleartext is never written; raw-byte scans after checkpoint and `kill -9`;
  - token-id collision mistaken for identity [T1.3] → ids are labels; the forced-collision test authenticates both independently;
  - disclosure through a read surface or config rendering [T1.4, P8] → display once; the reserved leaf is a marker; overrides never persisted;
  - token in a URL logged by a client, gateway or provider [T1.5] → `400` before auth on the Control API and the listener, plus revocation of the exposed token;
  - revocation not applied, applied late or undone by a crash [T1.6] → commit + publish before ack, in-job re-validation, durability under `kill -9`;
  - a leaked key outliving its need [T1.7] → bounded by process, Run, refresh and Operator revocation; budgets bound spend; documented;
  - a leaked supervised key used from the network [T1.8, P5] → refused on non-loopback listeners;
  - a Run Key exhausting resources with child Runs [T1.9] → the Caller breadth cap and the 8-level nesting cap;
  - a class on a surface it may not use, or on another Run [T1.10] → the route-family matrix and the subtree check, pinned per cell;
  - a revoked key's child Runs still holding live keys [T1.12] → cascade by default;
  - refresh by another process, theft and silent takeover [T2.1, T2.2] → possession stated honestly, single use, reuse detection with a visible Anomaly;
  - a refresh credential handed to a CLI that cannot use it [T2.3] → none unless the Adapter maps one;
  - a relaunch with no deliverable key, or two live generations [T2.4, T2.5] → a key per launch, revoked at confirmed exit;
  - a reattach minting or moving keys [T2.6] → no credential change;
  - the Run Key reaching the provider through a forwarded header [T3.6] → `x-hekma-run-key` stripped (custody's full strip set is 22.2);
  - `Debug`, panic or log leaks [T3.8, T8.3] → `SecretString`, redacting `Debug`, sensitive header values, the no-leak matrix;
  - errors echoing the presented value [T6.5] → static bodies;
  - authentication failures flooding logs or the outbox [T5.6] → counted, one rate-limited diagnostic, no value;
  - the agent's children inheriting `HEKMA_RUN_KEY` [T8.4] → expected and documented;
  - the agent printing its own key to its output log [T6.2] → documented, revoke on demand;
  - same-user processes reading the agent's environment or state.db → Stated limit: state.db holds hashes only, and a same-user process could already act as the Operator;
  - operator-set or spoofed reserved keys → refused at write, stripped at start;
  - file or argv delivery through a manifest [R1.13] → refused at registration;
  - time-of-check vs time-of-use between authentication and the job → re-validation inside the transaction;
  - a stale snapshot in a second engine → writes re-validate in the store, and the proxy half is recorded for 23.1;
  - the pre-record window → fail closed, documented, closes with the Shim;
  - timing side channels → hashed map lookup plus `ct_eq`;
  - downgrade over v17 → refused as too new.
  Out of scope, with the review: custody's own threats (§7.3–§7.5, 22.2/22.5), held calls (23.4), the Shim secret (24.1), Scent-Check (22.3).
- **What 22.1 does NOT do.** No Run Key in the API-key slot, no custodied key, no provider-variable strip (22.2); no Scent-Check behaviour (22.3); no Run Key lookup on the wire, no `X-Hekma-Run-Key` identification, no response headers returning keys (23.1); no announce header, announce endpoint, heartbeat or Leases (23.2); no announce or proxy-access credential issuance (23.1 `hekma binding`, 22.5); no hold re-validation (23.4); no labels bound to a Run Key for base-URL-only clients (23.1's bindings); no Selector form of `revoke-keys` (a later verb pass); no Shim (24.1).
- **Deferrals and the deferred-work trigger naming this story.** New entries at build: the proxy halves of R1.6/R1.8/R1.12 (trigger 23.1) and R1.7 (23.4); the pre-record window (24.1); announce-credential issuance (23.1) and the announce endpoint (23.2); cross-engine revocation propagation (23.1, 24.4); one shared token generator for 21-6's `hkset_` set tokens (the next host-auth change). The 21-9 entry (Caller-label writes through `check_caller_labels` and the Caller upsert, trigger "22.1/23.1"): **partly absorbed** — a Run-Key child open routes its Caller labels through the guard; there is still no Caller label update after creation, so the upsert's first caller stays 23.1/23.2 (re-pointed).
