## Intent

**Problem:** The engine process IS the supervisor: it spawns each agent into a process group / Job Object it holds, owns the stdin/stdout pipes, the raw-log redirects and the `output.log` tailer, and writes the write-ahead spawn record only AFTER exec plus a ~300 ms startup watch (AD-5's recorded orphan window). Whatever happens to the engine therefore happens to every agent — asymmetrically: a crashed engine leaves Unix agents alive to be adopted, while Windows agents die with it through Job kill-on-close; an adopted process loses its stdin pipe and its attributed log goes stale between commands; an adopted Windows process is stopped by a bare `TerminateProcess` that spares the descendants its Job would have killed; and an engine crash between exec and the record commit can leave an unrecorded, unsupervised process. None of this can hold FR-55 (a supervised Run's process must survive the Service Host's exit) without making the engine itself unfallible.

**Approach:** Move process ownership out of the engine process and into one **Shim** per supervised process — `hekma shim`, an internal, hidden subcommand of the same binary whose logic lives in `hekma-engine::shim` (OS parts under `backends/`), spawned detached from the engine's session (`setsid` / `DETACHED_PROCESS` + new process group). The Shim owns what the OS backends own today — the process group (as reaping parent; `PR_SET_CHILD_SUBREAPER` on Linux) or the kill-on-close Job Object, the pipes, the raw-log redirects, the `output.log` tailer — by *running the existing per-OS backend code inside itself* (AD-4's amendment). The engine reaches its Shims through a **third `ProcessBackend` implementation** whose handle is a local-socket client: spawn asks the Shim, stop/pause/poll/stdin are RPCs, exit is pushed by the Shim, and adoption **reconnects** — so a reconnected process keeps its stdin pipe and its attributed log (the pipes never died), and a stop after reconnect terminates the real group/Job on both OSes. Each Shim listens on a Unix domain socket in a `0700` directory under the state directory (short hashed name, under the `sun_path` limit) or a Windows named pipe whose DACL admits only the owning user; every connection presents a per-Shim connection secret (P14: derived as HMAC-SHA-256 of the launch id under a per-state-directory host key, stored only as a hash), and the first message carries the protocol version — the engine accepts its own and the previous minor and *reports, never kills*, a Shim it cannot speak (AD-20). The engine commits the spawn record — now carrying the Shim's endpoint, fingerprint and secret hash — **before** the launch RPC (AD-5's amendment; also closing 22-1's pre-record window), and the adoption owner/lease columns are renamed the **ownership claim** (they must not read as the PRD's Run Lease), keeping the compare-and-set. With no engine connected a Shim keeps its process running and buffers the exit; it never relaunches, never writes state.db, never mints a credential. Handoff Mode itself — releasing Shims on SIGTERM, reattach on the next Host, the service-manager checks — is 24.2's; bypass detection in the Shim is 22.4's; the crash-recovery matrix (cleanup vs adoption by mode) is 24.3's. Handoff Mode stays off in this story: SIGTERM still drains and stops (FR-41), and a crash still leads to adopt-and-continue exactly as today — now uniformly on both OSes.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-23 (ruled by Islam 2026-10-30) fixes: one Shim per supervised process as `hekma shim` (internal, hidden; logic in `hekma-engine::shim`, OS parts in `backends/`, so a Host can point at any binary calling the entry); session detachment; ownership of group/Job, pipes, raw-log redirects, tailer; the third `ProcessBackend` with RPC verbs, pushed exit, reconnecting adopt; socket access control (`0700` dir, peer uid, Windows DACL, per-Shim secret); the protocol version in the first message with report-never-kill; the spawn record committed before launch; the ownership-claim rename keeping the CAS; and the no-engine posture (keep running, buffer, never relaunch/write/mint). AD-4's amendment moves the OS backends INSIDE the Shim and names the drift this story closes; AD-5's amendment fixes commit-before-launch; AD-12's amendment gives adopted processes stdin and an attributed log; AD-19's amendment keeps an ACP stdio session across a restart; AD-20 fixes the version rule and that the engine owns Shim connections. What this story deliberately does NOT own: Handoff Mode and its SIGTERM release, the in-place upgrade handoff, the service-manager checks (24.2); the crash-recovery matrix — cleanup vs adoption by mode, `kill -9` hold honesty, SM-7's suite (24.3); bypass detection's TCP comparison (22.4 — the Shim this story ships is the home it lands in, and T2's process-tree handle is its seam); anything Run-scale (24.4).
- **Who commits the spawn record.** 22-1's deferral wording says "the Shim commits the spawn record before launch"; AD-23 also says the Shim "never … writes state.db". The reconciliation (and this spec's rule): the ENGINE commits the record — now carrying endpoint, secret hash and claim — BEFORE sending the launch RPC, so the record strictly precedes the child while state.db stays single-writer in the engine. The invariant AD-5 cares about ("no spawn without its record committed first") is a property of the ORDER, not of the writer; the restructure in T8 applies the same order to the direct backends so the invariant no longer depends on which backend a record uses.
- **The ownership claim, and what replaced `probe_alive`.** The v10 owner columns arbitrated "is the spawning engine still alive?" against the engine's pid; the v11 lease CAS'd concurrent adopters. Both survive as ONE claim {pid, start_time, generation} — renamed because 23-2's Run Lease makes any `lease_*` column on a spawn record read as the wrong contract. The rename is behavior-preserving (the CAS keeps its exact arbitration; the v11 suite re-points, its assertions unchanged). With a Shim, the live-owner question gets a better answer than a pid probe: the Shim KNOWS whether an engine is connected. The adopter's gate becomes: connect → hello → if `busy`, another engine holds it (skip, exactly the live-owner skip); if `hello_ack`, no engine is connected → CAS the claim → supervise. `probe_alive` stays on the trait (and the code path) for direct records and for the Shim-unreachable fallback; nothing about the direct adoption path is deleted — pre-v22 records and Shim-loss reconcile ride it.
- **Sequencing honesty: what a crash means between this story and 24.3.** Today a crashed engine's attached agents are adopted-and-continued by the next opener (story 1-6; Unix in practice, Windows rarely alive to adopt). FR-55's end state is mode-dependent: reattach under Handoff Mode, cleanup when it is off — but Handoff Mode does not exist until 24.2 and the cleanup flip is 24.3's bullet. This story therefore changes WHERE the process lives, not the adoption SEMANTICS: after 24.1 a crash on either OS leaves the process alive in its Shim and the next engine reconnects and continues, exactly today's Unix behavior made uniform. This is recorded here (and in `docs/hosting.md` as "what happens today") so 24.3's spec closes the loop rather than discovering it.
- **The engine never holds the process; stops are the only stops.** The Shim arm of `ProcHandle` has no Drop teardown — a dropped engine, a dropped handle, a lost connection: none of them can kill a child, because no engine process owns a killable handle (NFR-9's cleanest form). FR-41 is preserved because the drain path is explicit: SIGTERM → the supervisor's stop ladder → stop RPCs → the Shims run the OS ladders. The embedder-visible change (a short-lived engine's Drop no longer stops its agents) is the behavior AD-20 names ("dropping the engine never kills a Shim-owned process"); it rides the 0.12 cycle with a banner and an `docs/embedding.md` note, and is marked for confirmation in Ask First.
- **`--detach` converges.** Every Shim-backed Run already has 12-1's durable-detach property (the process outlives the engine; disarm is moot when nothing is armed). The flag keeps its CLI shape and its record column (pre-v22 records still read it), its marker keeps rendering for direct Runs, and the docs say plainly that under a Shim the distinction collapses. No CLI break.
- **The transport and the wire.** A Unix domain socket per Shim in `<state>/shims/` (0700) and a Windows named pipe per Shim with an owner-only DACL are the two transports behind one seam (`shim/proto.rs` traits; `backends/{unix,windows}/shim.rs` impls — the spine's platform rule names "the Shim's OS parts and socket handoff" as backend residents). JSON lines over the stream: every frame one newline-terminated object, byte payloads base64 (the ACP stream is NDJSON in practice, but the protocol must not assume it); serde_json is in-tree, the frames are greppable, and the protocol is internal (never in PRD §7's public list) though versioned per AD-20. The engine is the version authority: it sends `v`, the Shim answers its own, and the engine's accept set is {its minor, minor − 1} on the same major. A Shim outside the set is reported (one event, one diagnostic, an honest degraded-supervised listing) and left alone — killing it would be the exact unrequested stop NFR-9 forbids.
- **The connection secret (P14, an owner ruling pending).** AD-23 as written (a random secret, hashed at rest, "the engine presents it on connect") has the same re-delivery problem the security review found for Run Keys (T1.13): a restarted engine holds only the hash. P14-A derives `secret = HMAC-SHA-256(host_key, launch_id)` — any engine holding the per-state-directory host key (`0600`, 32 bytes, generated once) recomputes it, the spawn record keeps only `SHA-256(secret)` for the Shim's own check, and R1.17's byte scan holds. Rotation: a new LAUNCH mints a new launch id (a fresh derived secret for free — the per-launch shape 22-1 gave Run Keys); regenerating the HOST KEY rotates every secret at once and fails safe (every live Shim answers `secret-mismatch`; the engines report each Run as degraded-supervised and never kill — the operator restarts the agents deliberately). P6-A's format rules (the engine's generator discipline, hash-at-rest, never shown) apply to the derivation unchanged. A same-user process can read the host key — the review's Stated limit (same-user is Operator-equivalent) applies; the secret's job is the OTHER-user boundary (uid/DACL) plus reconnect integrity, and it does that job.
- **One controller, and never steal.** The Shim serves one control connection at a time; a second hello — even a valid one — gets `busy`. This enforces the live-owner boundary at the only place that knows the truth (the Shim), while the state.db claim keeps the engines' bookkeeping straight and the CAS still picks one winner among concurrent openers when no Shim answers. A claim holder that reconnects and finds itself replaced (claim moved on) is told so by the record, reports, and never kills.
- **The pre-record window, closed twice over.** 22-1's deferral: the Run Key was minted before spawn but committed after exec plus the ~300 ms startup watch, so a request presenting it inside that window was refused as unknown (fail closed), and a crash in the window minted a key nobody honoured. With the record committed before the launch RPC, the window cannot exist: the key's hash is durable before the process that will present it exists. The startup watch itself is unchanged (it still gates `starting → running`); only the commit moved.
- **Shim lifetime and leaks.** A Shim that is never launched exits after `SHIM_IDLE_LINGER` (60 s — the engine died between spawning it and the launch RPC; the record reconciles `start-aborted`). A Shim whose child exited lingers `SHIM_EXIT_LINGER` (1 h) for an engine to fetch and ack the buffered exit, then exits; the record reconcile honestly reports "exited while unsupervised, code unavailable" when the exit was never fetched. Both constants are named, surfaced in the diagnostics, and revisited with 24.3 (which owns the full recovery matrix).
- **ACP stdio across a restart (AD-19).** The pipes live in the Shim; the engine subscribes (`subscribe_stdout`) and receives `stdout` push frames; `write_stdin` completes the session's other half. A reconnected engine resumes the subscription and the session continues — `session/load` is needed only after a real Shim loss (the pipes died with it). A DETACHED ACP start keeps today's shape (stdout redirected to the raw log, no pipe, `session/load` on the next start): flipping that too is Ask First 8, recommended against for now (it would change what `--detach` means for capture, and nothing in FR-55 asks for it).
- **What of the Windows graceful stop?** AD-4's drift note also says Windows "graceful" stop is a wait with no graceful request. The story's close-list names three drift items, and this spec closes those three; the graceful request itself is a separate behavior change (a `CTRL_BREAK_EVENT` to the new process group the Shim creates) offered as Ask First 9 — recommended to land here because the Shim's process group makes it possible for the first time, but cheaply deferrable if the owner wants the stop ladder untouched.
- **Version.** New public types (`ProcHandle`, `ShimHandle` re-exports, `EngineEvent::Shim`, `EngineOptions.shim_exe`, `SpawnRecord`'s renamed claim fields and new Shim columns), a hidden CLI subcommand, and the behavior change above: hekma-engine **stays 0.12.0** (the cycle rule), announced in the Unreleased banners. New `nix` feature (`socket`) and `windows-sys` features (`Win32_Security`) are manifest-side target gates — the OS-cfg gate greps code, not Cargo.toml, the established pattern. No new crate.
- **Threats considered** (review ids where they exist; N-ids are this story's):
  - another local user driving a Shim [B1, T1.13] → `0700` socket dir + peer-uid check on Unix; owner-only DACL on Windows; the per-Shim secret as the cross-check;
  - the secret unrecoverable after an engine crash, or stored cleartext to make it recoverable [T1.13, P14] → HMAC derivation under the `0600` host key; hash-only at rest; R1.17's byte scan;
  - a second engine stealing supervision [the live-owner boundary] → single-controller Shims (`busy`), the claim CAS, report-never-kill everywhere;
  - a version-skewed Shim killed for being old [AD-20] → report + degraded listing, never a stop;
  - the Run Key or spawn env leaking from the Shim [T8.5, R1.16] → env dropped after launch, token ids only in logs/events, redacting `Debug` on frames, the one greppable DTO site;
  - the agent inheriting the Shim's socket or the host's provider variables [T4.2, T4.3, R2.3, R2.4] → Rust close-on-exec defaults pinned by a descriptor-listing test; the Shim spawned with a cleared environment;
  - core dumps of the Shim exposing memory that held the spawn env [T8.1, T8.2, R2.12] → non-dumpable + `RLIMIT_CORE` 0 on Linux; honest per-OS docs;
  - a never-launched or exited-forever Shim leaking a process [N1] → the two linger bounds with honest reconciles;
  - an unrecorded child after an engine death mid-launch [AD-5's orphan window] → record-before-launch; `start-aborted` reconcile;
  - a stale socket file masquerading as a live Shim [N2] → connect-probe-then-unlink at listen; the unreachable-Shim fallback path;
  - pid-reuse false adoption [AD-5] → unchanged start-time fingerprints, now on both the Shim and child columns;
  - the engine's own crash cascading into Shims [N3] → the Shim holds no engine handles; the engine holds no child handles; connection loss never tears down.
- **What this story does NOT do.** No Handoff Mode, SIGTERM release, socket/`host.lock` handover, or service-manager checks (24.2); no crash-cleanup-by-mode, no `kill -9` hold/call honesty, no SM-7 suite (24.3); no bypass detection — the Shim ships with the process-tree handle 22.4 needs but no TCP comparison (22.4); no scale work (24.4); no `agent.log` rotation (a recorded AD-12 drift that stays deferred); no migration of live processes into Shims (impossible — pipes cannot be re-acquired, which is the very drift this story prevents going forward); no change to the stop ladder, pause dispatch, Restart Policy, budgets or the metering path.
