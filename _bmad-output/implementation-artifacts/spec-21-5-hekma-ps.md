## Intent

**Problem:** Runs are first-class entities now (21-2's registry, 21-9's labels, 21-3's resolved Policies), but the only listings are `hekma agent list` (the supervised-instance projection) and one-Run-at-a-time `hekma run show`. There is no CONTROL column anywhere, no Run Status or Anomaly view across the Fleet, no Selectors on listings, no paging (`select_runs` caps at 1000 and returns whole rows), no `GET /v0/runs` list route, and the SSE stream carries no frame ids, no filter and no resume. FR-50's exception-first operator view — the surface UJ-5 watches — does not exist, and the store has no read path that stays bounded as Runs accumulate (NFR-4).

**Approach:** One listing read, three surfaces. The engine gains `list_runs(ListRunsQuery)` over three new partial indexes (schema v16): the default view is exception-first (any Anomaly, or status `held`/`silent`/`stale`, or `ended` with an Anomaly inside the ended-Run retention window — a fixed, documented 7-day read-side bound until compaction lands), `--all` lists every Run inside the window, and healthy open Runs are counted, not listed. Pages are keyset on `run_id` DESC (newest first) with `--limit` (default 50, max 1000) and an opaque `--cursor`; Selectors filter (21-9 grammar, bound and caller labels) and page past the verb cap. Each row carries the CONTROL depth, Run Status, Anomalies with their latched breach actions, labels with source and origin, and usage plus headroom against the RESOLVED limits from 21-3's `run_policy` (per-run always; cumulative on process-owning rows), with each limit's source. `hekma ps` (read-only, never starts a host) and `GET /v0/runs` (operator bearer) project it; `/v0/events` frames gain `id: <outbox seq>`, a server-side `selector` filter and Last-Event-ID resume from the outbox. The perf harness gains a seeded-Runs mode so NFR-4's first-page number is measured from here on.

**Acceptance Criteria:**
- Given Runs in every shape — an active healthy Run, an active Run with the `breach` Anomaly (a latched `block`), a `held` Run, an ended Run with the `failed` Anomaly ended 2 days ago, an ended clean Run ended 2 days ago, and an ended Run with an Anomaly ended 20 days ago — when `hekma ps` runs with no flags, then the first three exception Runs and the recent failed one are listed (newest run id first), the 20-day-old one is not (outside the 7-day window), the healthy Run is not listed but is counted, and the footer names the listed and healthy counts; `--all` additionally lists the recent clean ended Run, still not the 20-day-old one.
- Given a supervised Run whose metering source is `self-reported`, then its CONTROL cell reads `supervised (no wire)`; given a child Run, then its row shows the run id where the process-owning rows show the instance name.
- Given a Run under a Policy that sets a per-run token ceiling (source `policy:<name>` in `run_policy`), when `hekma ps --json` runs, then the item's headroom is computed against THAT resolved ceiling with its source named, and after the Policy is lowered and re-resolved (21-3's change job), the next `hekma ps` shows the new headroom — never a stale or configured-only figure; an unpriced Cost Cap shows the `unpriced-model` Anomaly in the row, never a fabricated `$0.00` headroom.
- Given a latched `block` breach, then the row's ANOMALIES cell renders `breach[block]` (each latched action) and `--json` carries `latched: [{dimension, scope, action}]` — a fenced agent never reads as merely healthy (the 19-2 deferral's slice).
- Given more Runs than one page, when `hekma ps --limit 2` runs twice (the second with the printed cursor), then the two pages are disjoint, ordered `run_id` DESC, `next_cursor` is null exactly when the read is exhausted, and rows that change status between pages neither duplicate nor reorder (the keyset is `run_id`); `--limit 0` means the maximum (1000) and `--limit 1001` clamps to 1000 with a stderr note.
- Given a cursor that is not the codec's form (or a `v2:` prefix from a future shape), then the CLI exits 2 and `GET /v0/runs` answers `400 invalid-cursor`; given `--selector team=core,env=prod`, then only Runs carrying both labels (bound or caller) appear in whichever view is active, and a Selector matching more than 1000 Runs still pages (the verb cap does not apply to listings).
- Given `GET /v0/runs?view=all&selector=…&limit=…&cursor=…` with the operator bearer, then it returns `{schema_version, view, selector, items, next_cursor, counts}` with items byte-shape-equal to the CLI's `--json` items, `401` without a credential, `400 invalid-selector`/`invalid-cursor`/`invalid-limit` on bad params; every filter, Selector and page parameter of `hekma ps` has its equivalent (FR-50 parity).
- Given an SSE client with no `Last-Event-ID`, then every event frame carries `id: <outbox seq>` (the `lagged` frame carries none); given a reconnect with `Last-Event-ID: N`, then the server replays outbox rows with seq > N through the active selector filter before streaming live, with no duplicate and no gap at the seam; given N below the outbox floor or past the tail, then the connect answers `409` with the typed code (never a clamp); given `?selector=team=core`, then only events whose subject Run currently carries the label are delivered, and events naming no Run are dropped.
- Given a v15 state dir (21-3 merged), when the engine opens, then `user_version` is 16 and the three partial indexes exist; the listing queries' `EXPLAIN QUERY PLAN` show index reads only (no `SCAN` on `runs`), pinned by tests at v16 shape.
- Given `hekma ps` and `hekma agent list` on the same state dir, then both work unchanged beside each other: `agent list`'s human table and `--json` document are byte-identical to before (the frozen projection), and `ps` reads only Run tables.
- Given the bench at `--ps-seed 10000`, then the first exceptions page (default limit) plus counts completes with p99 < 1 s (strict), reported as `ps_listing.ps_first_page_p99_ms` alongside the seed and the counts cost; the default (no-flag) report stays byte-equivalent; a local `--ps-seed 100000` run's number goes in the build report (NFR-4's 10k/100k/1M ladder stays 24.4's).
- Given an empty state dir, then `hekma ps` prints the empty note and exits 0, creating nothing and starting no host.
- Given handoff: fmt, clippy `-D warnings`, the workspace tests, `check_docs.py` (+ `--self-test`), `test_automation.py` pass; changed-line coverage ≥ 95%; one independent review pass done.

## Design Notes

- **Exception-first, precisely.** The default view lists a Run iff `(anomalies <> '' AND (status <> 'ended' OR ended_at >= cutoff)) OR status IN ('held','silent','stale')`; `--all` lists iff `status <> 'ended' OR ended_at >= :cutoff`. `cutoff = now − ENDED_RUN_RETENTION_DAYS` (7). Healthy = `status = 'active' AND anomalies = ''`; `counts = {listed, healthy_open}` (COUNT queries over the same indexes). `held`/`silent`/`stale` are STORED statuses (AD-25: statuses are stored, never derived on read): `silent` is set by the Lease sweeper (23.2; thresholds are that story's — no Run can carry it before then) and `stale` by a Hub (Epic 25); `hekma ps` matches them the moment a producer exists and never computes either at read. The PRD Glossary's list of Anomalies naming "a Run gone `silent`" is satisfied by the status's exception-first loudness, not by a new Anomaly kind (Ask First 6).
- **The retention window.** FR-49 keeps ended Runs for "a configurable retention window, then compacted". Compaction (deleting detail rows into compacted rollups) and its knob belong together in 24.4; a knob with no enforcement behind it would be a lie (setting 1 day would hide rows, not remove them). 21-5 ships the READ side: the fixed, documented 7-day default (`ENDED_RUN_RETENTION_DAYS`, validated as the PRD's assumed default) bounds both views, `--all` shows full detail only inside it (AD-27), and deferred-work re-points the compaction trigger to 24.4 with the window's default recorded here. Ask First 1.
- **Ordering and the cursor.** Keyset on `run_id` DESC: ULID ids encode creation time, so DESC is newest-first and the PK is the index; stable under row updates (unlike `updated_at`), immune to paging duplicates when Runs are created mid-pagination (new ULIDs sort above page 1, legacy `run-…` ids sort below every `run_…` id and thus last — rare history, documented). The cursor is opaque: `base64url("v1:" + last run id)`, versioned so a future key shape refuses as `invalid-cursor` instead of mispaging. Rows deleted between pages (compaction, later) are skipped; a Run that stops matching mid-pagination does not appear; one that STARTS matching below the cursor is not chased (standard keyset semantics, documented in `docs/runs.md`).
- **Indexes (schema v16, one crash-atomic step).** `idx_runs_open` serves `--all`'s open arm and the open/healthy counts; `idx_runs_exception` serves the exception arms and the listed count; `idx_runs_ended_at` bounds the ended-inside-window arm by the window (the exception index alone would walk every historical anomalous row). The exceptions query is OR-arms over the indexes (SQLite's OR optimization / a `UNION ALL` merge, whichever the planner picks — the gate is `EXPLAIN QUERY PLAN` showing no `SCAN` on `runs`, pinned by test). v15 → v16 is additive DDL only, one-way like every step (21-3 lands v15; if its number moves, take the next).
- **Per-row detail is bounded point reads.** After the page query, each row's labels (`run_labels` PK), resolved limits (`run_policy` PK), subtree usage (`usage_rollup_run`), latches (`run_latches` PK) and — for process-owning rows — the instance cumulative rollup (`usage_rollup_instance`) are point lookups bounded by the page (≤ 1000). Instance-less Runs (23.1's wire Runs) read zero usage until that story re-keys the rollups — a recorded seam, never a fabricated figure. Cumulative usage/headroom appears ONLY on process-owning rows (21-2's `decide_chain` evaluates the cumulative scope only there); child rows omit the cumulative block entirely (absent, not zero — a shared instance pot must not read as a per-Run figure).
- **Headroom against RESOLVED limits (the 21-3 seam).** Headroom = ceiling − current, saturating at 0, per scope and dimension, computed from `run_policy` (the stored resolution: `LimitSource` per limit — `run` | `explicit` | `policy:<name>` | `default` | `unset`), never from instance config alone; a Policy change re-resolves and the next listing shows it. Dollar headroom is present only when a Rate resolves; an unpriced cap shows the `unpriced-model` Anomaly and no dollar figure (the FR-20/21-3 discipline). `effective_action` (post depth-fallback) rides beside the action. The `--json` headroom block reuses `BudgetView`'s stable field names (`per_run_limit`, `per_run_remaining`, `cumulative_limit`, …) plus `sources`, so instance and Run consumers parse one shape.
- **The human table.** Columns: `RUN` (instance name on process-owning rows, else the run id; 10–32), `CONTROL` (the depth, `supervised (no wire)` rendered whole; ≤ 20 — the string is 20 columns), `STATUS` (≤ 6), `ANOMALIES` (`breach[block],failed` or the honest `—`; 9–24), `LABELS` (`k=v`, a Caller label suffixed ` (caller)`; 6–24), `USAGE (est. $)` (subtree tokens + derived dollars, the qualifier in the header per AI-45), `HEADROOM (est. $)` (per-run tokens + dollars remaining, `policy:<name>` suffixed when Policy-sourced; on process-owning rows with a cumulative ceiling, `· cum 1.2M tok` appended). Width follows the house rule (the "tables no longer clip" banner): `COLUMNS`, else the terminal, else 80 (79 on Windows), clamped 40–132; a column's cap is never below its header; overflow cuts with `…`; `--json` carries every figure whole. The "kept on pause by upgrade" marker (21-3) rides `--json` items and `run show`/`fleet`, not the compact table (width discipline). The footer prints the counts and, when a next page exists, the full next-page command — the same view, Selector and `--limit` plus `--cursor <value>` (fix round 1, M4) — to continue (stderr; stdout stays parseable).
- **Selectors on listings.** The 21-9 grammar and `SelectorScope::Any` (bound and caller — FR-49's listing scope). `select_runs` (verb support) stays capped at `MAX_SELECTED_RUNS`; `list_runs` is a listing and PAGES past the cap (FR-50: "no read path loads the whole Run set" — a cap would force exactly that on big fleets). The selector arms drive off `idx_run_labels_kv` with PK probes, composed with the view predicate and the cursor.
- **`hekma ps` beside `hekma agent list`.** `ps` is the Run-grain listing; `agent list` stays the supervised-instance projection with its frozen JSON. No alias, no deprecation, no JSON change (Ask First 9). `ps` opens the read-only engine (21-4): never starts a host, never writes; on an older schema it follows the 21-4 `NeedsMigration` flow.
- **Exit codes.** The frozen table: `2` an invalid Selector/cursor/limit (`RunInvalid`), `1` store/host failure, `0` otherwise — including an empty result (a note, not an error; the 21-9 no-match precedent). No confirmation, `--yes` or `--dry-run`: a listing acts on nothing.
- **SSE ids, filter and resume.** The bus envelope becomes `(outbox seq, EngineEvent)` internally — the writer's ack already returns each committed event's seq (21-1), so the publisher sends them together; `subscribe()` still yields `EngineEvent` (hosts unchanged) and `subscribe_sequenced()` feeds the SSE path. Every event frame carries `id: <seq>`; `lagged` frames carry none (a gap marker, not an event). Resume: the handler validates `Last-Event-ID` BEFORE streaming (below the outbox floor → `409 cursor-below-retention`; past the tail → `409 cursor-past-tail`, matching the export contract's never-clamp rule), then subscribes first, replays outbox rows with seq > the id through the active selector, then streams live, dropping live seqs ≤ the replayed tail. The selector filter evaluates each event's subject Run (`RunEvent.run_id`; `UsageUpdate`/`BudgetBreach` via their run id; `Transition` via the snapshot's `owners` map) against its CURRENT labels — snapshot first (no SQL), one read-only store read when the Run is absent from the snapshot (ended Runs keep matching until compaction). Events naming no Run (`policy`, `breach-default-upgraded`) are delivered only without a selector. Honest limitation, documented: the filter sees current labels, not labels-at-event-time.
- **The bench mode (NFR-4 from here on).** `--ps-seed <N>` mirrors `--serve-shape`: additive scenario + `ps_listing` report block + gates that bind only on the flag; the default report stays byte-equivalent. Seeding writes rows directly through the store (no processes — Windows-safe): N Runs with 2 labels each, `run_policy` rows, subtree rollups on 10%, and the status mix named in the task. Gate: `ps_first_page_p99_ms < 1000` strict at the CI seed (10k), with the existing CI once-retry policy; a local 100k number goes in the build report. 24.4 owns the 10k/100k/1M ladder and the proxy p99.
- **Version.** New public types (`ListRunsQuery`, `RunListing`, `RunSummary`, the counts), new facade methods (`list_runs`, `subscribe_sequenced`), schema v16 (one-way): hekma-engine **stays 0.12.0** — nothing has been released since 21-2's 0.11.0 → 0.12.0 bump, every story in this unreleased cycle stays on 0.12.0, and the semver gate's baseline (7783aa4) already permits breaking changes at 0.12, so the additions land within it with no bump and no baseline move. No new `EngineEvent` or `Anomaly` variants; the bus envelope change is crate-internal.
- **Deferred-work decisions (the four triggers naming this story).**
  1. *Row-id cursor on per-instance event reads (from 21-1, trigger "21.5")* — **keep deferred.** `hekma ps` never reads per-instance event history (runs, labels, `run_policy`, rollups, latches only); the SSE replay reads the outbox, already seq-keyset. Re-point the trigger to 24.4's scale pass or the first paging consumer of per-instance events.
  2. *Ended-Run compaction and the retention window (trigger "21.5: `--all` and the retention window it lists against")* — **partially absorb.** The window's default and its read-side meaning land here; the configurable knob and compaction stay with 24.4 (one mechanism, one owner). Update the entry: resolved-in-part, new trigger 24.4.
  3. *Live-capture re-check (from 21-4, trigger "the 21.5 `hekma ps` supervision read")* — **keep deferred, re-point to 21.7.** `hekma ps` is a one-shot read with no polling; `hekma top` is the surface that polls.
  4. *`block` fence visibility (from 19-2, trigger 23.1/23.4 or an operator report)* — **absorb the slice.** Listing rows carry the latched (dimension, scope, action) set and render `breach[block]`; a fenced agent reads as breached-with-block on `ps` from this story. The full disposition surface (held count, oldest held age, per-call records) stays 23.4.
- **What 21.5 does NOT do.** No Selector set tokens or verbs (21.6); no live view (`hekma top`, 21.7 — the SSE filter here is the seam it builds on); no `held`-call count or age (23.4's producer; the item shape leaves room); no Lease/sweeper (`silent` has no producer until 23.2); no Nodes (`stale` none until Epic 25); no compaction or its knob (24.4); no 1M-Run measurement (24.4).

## Build Conventions

- User-facing text (docs, CLI help and messages, CHANGELOG, RELEASE_NOTES) never carries planning ids (no `21-5`, `FR-50`, `AD-25`, `NFR-4`) and never the word "pivot"; the first production Host stays unnamed. Code comments and `_bmad-output/` may cite ids.
