## Intent

**Problem:** Today the agent holds the real provider key. `apply_config_mapping` resolves every `secret:NAME` leaf and places the cleartext into the agent's environment, onto its argv (a `Flag` target — warn-only since AI-39) or into a rendered file inside its Agent Home (a `File` target); `agent.*` pass-through leaves go to the environment verbatim. Everything an agent prints, writes, uploads, commits or is tricked into revealing draws from what it was given. The child-environment allowlist that would fence this (17-2) is off by default, and its OS floor keeps `HOME` anyway — so a custodied agent would still find the user's own stored provider logins. The shared proxy (23-1) reads Run Keys but refuses one in the API-key slot (`hekma_custody_unavailable`); it has no Host/Origin guard (a browser page that reaches loopback can probe it); and the security review (2026-11-02) found AD-22 unsafe as written in two places a naive build would inherit: a call on a labelled binding with no credential, or a Run created by the proxy's announce header, would get the binding's custodied key (T3.1, H/H — any local process spends the real key credential-free), and the upstream origin comes from `config.toml` in the agent's own working directory, so an agent that edits it routes the real key to an origin it controls (T3.2, H).

**Approach:** A reserved unified key **`provider.api_key`** names the custodied key as a `secret:NAME` reference — the one leaf the engine recognizes as the provider key (P9). When an instance sets it, custody is **on by default** at start (`provider.custody = "off"` opts out). At start the engine: refuses a `File`/`Flag` mapping of `provider.api_key` (registration-time, like `run.key`) and refuses any second delivery of the same secret — another leaf resolving the same name, a pass-through `agent.<VAR>` or launch-env entry naming a variable on the enumerated, versioned **provider-variable list**; forces the child-environment allowlist on for that spawn (clearing everything but the OS floor, so inherited provider variables never pass); resolves and **pins the key's origins and paths beside the key** (P7/P15: an optional `[custody.NAME]` table in `secrets.toml`, else a versioned built-in table matched at operator start and **frozen on the Run for its life** — a relaunch after `config.toml` is edited changes nothing); validates that the real key resolves (fail closed) but lets its cleartext reach **only the proxy's in-memory custody cache** — the adapter's `provider.api_key` Env target receives the launch's **Run Key** (22-1) and `metering.base_url` the proxy URL, so the real key never enters the adapter config mapping, the environment, argv or the Agent Home. The proxy turns the API-key-slot Run Key into the swap, but only for a call authenticated by a **custody-eligible** Run Key (P4 — minted at supervised start or by a credentialed announce, or descended from one; never for an unattributed call, a binding's Run reached with no credential, or a header-announced Run, under every Scent-Check Mode): strip the presented credential headers, check the outbound origin (canonical `https` origin on the key's pinned list) and path (on the key's allow-list), insert the custodied key in the provider's scheme only, and **redact exact occurrences of the custodied key from relayed responses** (P11). A **Host/Origin guard** refuses, before any upstream dial, a request whose `Host` is not a loopback literal or an Operator-configured name, or whose `Origin` is present and not on the Operator allow-list; no CORS headers are ever added and no preflight is answered permissively. `config get --reveal` of a custodied key emits a `secret_revealed` event naming the secret before printing (P10); the Service Host sets itself non-dumpable with `RLIMIT_CORE 0` on Linux; an opt-in `provider.isolate_home` points the agent's home-directory variables at a directory inside the Agent Home (P13, off by default). A `self-reported` agent whose key Hekma does not hold shows `supervised (no wire)`; an `engine-observed` one is refused at start with a remediation. The docs carry the review's §10 threat-model text and call custody **Preview — not yet supported** until §11's conditions hold (Islam's rulings on P1, P4, P7 in the spine; both stories' criteria green in CI). Schema v19; hekma-engine stays 0.12.0.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-22 (ruled 2026-10-30) fixes custody's shape: the Run Key in the API-key slot, the swap, the allowlist forced on, `File`/`Flag` refused, the loopback Host guard, `supervised (no wire)`, the engine-observed refusal. The security review is **draft for ruling** (AI-58: Islam picks; this spec edits neither spine nor PRD): it builds on P4 (issued credentials only), P7 (origins pinned beside the key, frozen for the Run), P9 (the reserved key + refuse a second delivery), P10 (the reveal event, non-dumpable, the extended Stated limit), P11 (response redaction), P13 (home isolation, opt-in) and P15 (path scope), each an Ask First O-item; a different ruling changes the matching criterion. §11's gate is explicit: **the docs may not call custody supported until P1, P4 and P7 are ruled and carried in the spine, with P8's sentence, and both stories' criteria pass in CI** — so the docs say preview (O1).
- **Where the spine and the review disagree, and what this spec does.** Two places. (a) AD-22 says the proxy "inserts only the custodied key named by the call's Run's instance config **or its endpoint binding** — never for an unattributed call", which read literally grants a labelled binding's key to its Run's credential-free calls; the review's T3.1/P4 rates that H/H and this spec builds P4 (the binding's key is inserted only when the call is authenticated by a custody-eligible credential). (b) AD-22's "one token per Run … valid for its Run's life" cannot re-deliver a hash-only key to a relaunch; 22-1 already built P1 (a key per launch) and this spec inherits it. Both amendments are Islam's to write into the spine after ruling; the build does not wait (the 22-1 precedent).
- **Naming the custodied key (P9).** `provider.api_key` is a reserved unified key whose value must be a `secret:NAME` reference; the engine finally "knows which leaf is the provider key". The stored value stays a reference everywhere (config, `effective-config.json` renders the mask, state.db never sees a value — bindings already store references only). Delivery inverts the usual secret flow: `resolve_secrets` resolves the reference for **validation and the custody cache only**; the per-launch secrets map then **replaces** `provider.api_key`'s entry with the launch Run Key, so `apply_config_mapping` can only ever place the Run Key. The real key is resolved through `SecretResolver` for the proxy only, exactly AD-22's "never enters the adapter config mapping".
- **The second-delivery refusals.** Custody is only as honest as the absence: the start refuses (pre-transition, no state change) when any other leaf resolves the same secret name, when a pass-through `agent.<VAR>` names a listed provider variable (values inspected, not just references — `agent.OPENAI_API_KEY = "sk-live"` is caught by the variable name), and when the launch env (the manifest's `[lifecycle.start]` env) names one. The refusals name the conflicting delivery and the migration. The provider-variable list is deliberately a **closed, versioned list** (P9-B's inference-by-any-name is rejected as fragile and silent); the docs table is the version surface and additions ride the Adapter Contract's additive discipline.
- **Origin pinning and freezing (P7).** Origins travel with the key, in the key's trust tier: `[custody.NAME].origins` in `secrets.toml` (whoever can edit that already holds the key), else the built-in versioned table matched by the host of the operator-configured `metering.upstream_base_url` **at the moment custody starts** — an operator-time resolution, then frozen on the Run (`runs.custody_origin`) for the Run's life: a Restart Policy relaunch after the agent edits its own `config.toml` keeps the frozen origin (the review's §12 question answered for the custody origin; governance keys are §12's own finding, out of scope here). No origin resolvable → start refused with the remediation (declare origins beside the key). A binding naming an upstream whose origin is not on its key's list is refused at creation (Operator-only surface). Call-time, the 23-1 canonical URI check extends to the pin: scheme `https`, verification on, origin equality after canonicalisation; `CONNECT`, foreign absolute-form targets and any authority mismatch stay `hekma_bad_target`; redirects stay relayed-never-followed.
- **Path scope (P15).** Each custodied key carries a path allow-list beside its origins: `[custody.NAME].paths` else the built-in provider's synchronous-inference prefixes. A path outside is `hekma_path_not_allowed`, not forwarded — a Run Key cannot start batch, fine-tune or file jobs whose spend arrives unmetered, and cannot reach key-management endpoints. The docs tell Operators to custody inference-scoped project keys, never admin keys.
- **Issued credentials only (P4).** `custody_eligible` was recorded at mint by 22-1 (supervised starts and credentialed opens true; children inherit) and rides `KeyEntry` — the hot path reads one flag. The swap applies only when the call is authenticated by an eligible Run Key (API-key slot or `x-hekma-run-key`); the swap source is the **attribution Run's** held key — its instance's `provider.api_key` for a supervised Run (children of it included), the binding's `custodied_key` for a binding's Run or split. Never: a binding's Run with no credential, the unattributed Run, a header-announced Run's child. This holds on loopback and under every Scent-Check Mode (only `off` exists until 22-3; the rule is mode-independent by construction, and the announce header — when 23.2 adds it — never unlocks custody; `hk_ann_` stays a Control API credential). 23-1's `hekma_custody_unavailable` survives for exactly the ineligible/keyless slot case.
- **The strip/insert set and response redaction.** Under the swap the proxy removes the presented Run Key from **every** credential header (the wire contract's stripped set plus `authorization`/`x-api-key` when custody applies — a client's own key on a custodied Run is replaced, not forwarded: a custodied Run spends only its custodied key, which is what makes attribution total) and inserts the custodied key once, in the provider's scheme (`Authorization: Bearer`, or `x-api-key`, or the binding's declared header). The inserted value and every parsed credential are marked sensitive (hyper `HeaderValue`); no code path formats a request or header map with `Debug`. Redaction (P11): responses are buffered whole (23-1), so a single scan replaces exact occurrences in headers and body with `hekma_redacted_key`; when incremental relay lands, the redaction moves to a sliding window (noted as its trigger).
- **The custody cache (R2.11, AD-10's amendment).** The proxy reads only the snapshot — so the values live in a **separate in-memory cache** beside it (never in the snapshot the writer publishes, keeping secret values out of shared published state): a background refresh re-resolves held references through `SecretResolver` every ≤ 30 s and swaps the map atomically; the docs state the pick-up bound. Rotation at the provider propagates within the bound; a resolution failure keeps the last good value and raises a rate-limited diagnostic (a stale key fails at the provider, loudly, never silently).
- **The Host/Origin guard.** Loopback-only binding stays (23-1; no widening flag — beyond loopback is 22-5 with TLS and a credential). The guard is the DNS-rebinding half of the boundary: `Host` must be a loopback literal or on `--proxy-allowed-hosts`; `Origin`, when present, must be on `--proxy-allowed-origins` (browser pages send `Origin` on cross-site requests; SDKs don't). Refusal is `403 hekma_bad_host` before identification and any dial; no `Access-Control-*` header is ever added, so a page's read of a response body fails in the browser regardless. An `OPTIONS` preflight gets the same guard and no permissive answer. With P4 the guard is defence in depth: a page that gets past it still cannot spend the real key.
- **Environment, floor and home (R2.3, P13).** Custody forces `inherit_env: false` for the spawn — the 17-2 clear-then-apply path with the unchanged OS floor (`PATH`, `HOME` on Unix; `SystemRoot` et al. on Windows). Provider variables die in the clear, not by enumeration. The floor's `HOME` keeps the user's stored logins reachable by absolute path — P13's `provider.isolate_home = "on"` (opt-in, off by default; many agents need Git/SSH config) points `HOME` and the XDG base variables (Unix) or `USERPROFILE` and the profile variables (Windows) at a directory inside the Agent Home. It keeps agents from *finding* logins by default; it does not hide them from a shell that names a path — the docs say so, and bypass detection (22.4) stays the backstop. R2.3's "the Shim is launched with a cleared environment too" and R2.12's Shim half land with the Shim (24.1) — today the engine's spawn is the only launcher, and it is covered.
- **Visibility and refusal honesty.** `runs.custody_state/reason/origin` are stored, not derived: a Run live at upgrade shows `pre-custody` (its environment is fixed — T4.9), an opted-out one `opted-out`, a keyless one `no-held-key`. The engine-observed refusal is the FR-19 hard line restated with its remediation; the `self-reported` path renders `supervised (no wire)` through the existing `display_with_wire`, and turning custody on gives it a wire path (the PRD's "fully supervised").
- **Schema v19; hekma-engine stays 0.12.0** (the cycle rule; announced in the Unreleased banners). Additive: three `runs` columns, no backfill (`pre-custody` is the honest default for existing rows), one-way. New public types (`CustodyInfo`, the custody config keys, the two wire errors, `EngineEvent::SecretRevealed`, the additive `custody` field on run documents) ride the existing schema versions where 22-1/23-1 set the precedent (additive fields, no bump). No new dependency (`getrandom`, rustls, tokio, rusqlite in-tree; the non-dumpable helper is libc-free via `std` + a `backends/unix` prctl wrapper — the one OS-conditional addition, in the allowlisted home).
- **Threats considered** (review ids in brackets): the key delivered through config alongside custody [T4.1, P9] → the reserved key + second-delivery refusals; inherited from the host environment [T4.2] → forced allowlist; inherited descriptors [T4.3] → Rust close-on-exec (pinned by the fake's descriptor dump; the upgrade-handoff socket exception is 24.1's, documented); readable in the Agent Home / `--reveal` / `config.toml` edits [T4.4, T4.5, T4.8] → absence by construction, the `secret_revealed` event, the frozen origin, and the extended Stated limit in §10's text; the user's own stored logins [T4.6, P13] → `provider.isolate_home` opt-in + 22.4 backstop; credential-free spend [T3.1, P4] → eligibility flag, one read; origin redirection [T3.2, T3.3, T3.4, T3.5, P7] → pin-beside-the-key, canonical equality, no redirect following, `https` only; the Run Key reaching the provider [T3.6] → the strip set; provider echo [T3.7, P11] → redaction; `Debug` leaks [T3.8, R2.10] → sensitive values, no request `Debug` (23-1's rule extended to the insert); rebinding/CSRF [T3.9, R2.8] → the guard, no CORS; unmeterable endpoints [T3.12, P15] → the path allow-list; stale cache [T3.11] → the 30 s bound, documented; dumps [T8.1, T8.2, P10] → non-dumpable + `RLIMIT_CORE` 0 on Linux, per-OS docs; a leaked Run Key from the network [T1.8] → loopback-only proxy (22-5 revisits). Out of scope, with the review: Scent-Check behaviour (22.3), bypass detection (22.4), TLS/non-loopback/proxy-access acceptance (22.5), held-call re-validation (23.4), the Shim (24.1), announce (23.2), an OS-keychain resolver (Deferred, AD-10), containing a hostile same-user agent (NFR-6, never claimed).
- **What 22-2 does NOT do.** No Scent-Check modes or Q9 decision (22.3); no bypass detection (22.4); no TLS, non-loopback bind or `hk_pxy_` acceptance (22.5 — the credentials exist, inert, since 23-1); no announce header or endpoint (23.2); no hold/release/reroute/reject and no held-call re-validation (23.4); no Shim, no per-launch socket handoff (24.1); no reroute carrying custodied keys (23.4, where "a custodied key never leaves its origin" already binds); no incremental SSE relay (the redaction window moves then); no keychain resolver; no change to `--reveal`'s authority (FR-14 keeps `--reveal` the acknowledgment — the event makes it visible, not gated).
