## Intent

**Problem:** FR-50's acting half does not exist. Every lifecycle verb still addresses one Agent Instance by name; the only Selector fan-out is `hekma label`'s, and it is CLI-local — the Control API has no Selector resolution, no set token (the 21-9 deferral, Fibery 608), so a Host cannot act on a set at all. There is no `hekma budget`: an Operator reads limits through per-instance config, and a limit set on a *Run* exists only where 21-2 put it (child Runs at open). The within-Run latch re-arm and the live un-fence exist only for the Policy trigger (21-3); raising a ceiling through any other path leaves a latched, fenced Run stuck until it ends (the 19-2 deferral). And the readiness gate's Governance-Vector finding is open: nothing owns the vectors entry for the re-arm now that the Task story is gone.

**Approach:** One fan-out, three surfaces, and one budget noun. The engine maps a Run target to its instance verb (`stop`/`pause`/`resume`/`drain` on the process-owning Run; a child Run's cell is answered from `verb_cell` — unsupported cells are refused per Run, never silently skipped) and gains `set_run_limits`, the budget job: it validates scope and action per depth, checks the authority rule (`LimitActor`: only Operator or Host raise a ceiling; a Caller may only tighten), writes `run_limits` — and the limit BELONGS TO THE RUN, like a verb label: it ends with the Run, and a fresh `start` mints a new Run without it — re-resolves, and runs the SAME `re_arm` pass 21-3 built for Policy changes — promote it, do not re-implement — so a raise re-arms the latch and clears matching `block` fence reasons per reason, and a lower at-or-below usage breaches at once. The `budget.*` config-write path gains the same money half (the 19-2 live-un-fence trigger). The Control API gains `POST /v0/runs/select` (set resolution with a token: hashed at rest, bound to the creating credential, single-use, expiring) and set-taking forms of every verb route; `hekma label` migrates onto them. The CLI generalizes 21-9's fan-out into one shared module (`resolve → show → confirm on a terminal only → act on exactly that set → per-Run results → first failure's exit class`) and puts `--selector/--dry-run/--yes` on the lifecycle verbs it fits (stop, pause, resume, drain, run close) — not on `start` or `send`, with the reasons recorded. `hekma budget show|set` rides the same machinery. Governance Vectors move additively to 1.4.0 with the re-arm as a case kind.

- Given a cumulative token ceiling set with `hekma budget set` on an open Run — whose per-Run result SAID the limit is Run-scoped, in the human line and in `--json`, pointing at `budget.*` config or a Policy for durable limits — when the instance is stopped and started, then the fresh Run does NOT carry the ceiling (no `run_limits` rows survive; the resolution falls back to the instance/Policy layers; `budget show` on the new Run names no Run-level limit) — the limit belongs to the Run, like a verb label.

## Design Notes

- **Which verbs gain the flags, and which do not.** GAIN `--selector/--dry-run/--yes`: `agent stop`, `agent pause`, `agent resume`, `agent drain` (the Run-grain lifecycle verbs, through the process-owning Run), `run close` (a child's lifecycle verb), `hekma budget` (new), `hekma label` (21-9; migrated here onto the shared machinery and set tokens). Hold/release/reroute/reject adopt the SAME machinery with their own story (23.4) — the fan-out module is built verb-agnostic for exactly that. DO NOT gain: `start` (a Selector resolves non-ended Runs — there is nothing to start; start is instance-grain and only `start` mints a new Run, FR-49), `send` (interaction: one text to one agent's input channel per FR-24; it carries content, and the FR-49 table fails it fast below `supervised` anyway), `attach`/`logs` (one stream, one terminal; 21.7's problem), `run open` (creates one child under one parent), `register`/`remove`/`config`/`memory` (instance-grain configuration) and `policy` (standing rules, not a per-Run act; its own `--dry-run` already reports matched counts).
- **Run → instance verb mapping.** A Selector's set is non-ended Runs. For each: `process_owner = 1` → the verb maps to the instance verb on `runs.instance_id` (`stop`→stop, `pause`→pause, `resume`→resume, `drain`→drain), executed with today's engine semantics (capability honesty, the stop ladder, the drain bound). Anything else — child Runs, and any depth the cell does not serve — is answered from `verb_cell`, the ONE table (the conformance fixture and the mapping cannot drift); before 23.4 every wire-verb cell at `announced` and below is unavailable, so those Runs refuse per Run with the depth (or Metering Source) named. This is FR-50's per-Run success-or-failure, and it is why the set is never "filtered to what works" — a silent skip would be the AI-18 lie.
- **The shared fan-out (`cli/fanout.rs`).** Generalizes `cli/label.rs` verbatim where it exists: resolve the set once (read-only; a single target reads the Run so an unknown id fails before any host starts), show it (one line per Run), confirm (21-9's terminal-only rule), act on EXACTLY the listed ids, report per Run, exit with the first failure's class + the count. One act-results document for every verb, `schema_version: 1` (the act-results family): `{schema_version, verb, dry_run, matched, results:[{run_id, outcome, error?{code,message}, …verb fields}]}`; outcomes are the verb's past tense (`stopped`, `paused`, `labeled`, `set`…), `would-<verb>` under a dry run, `unchanged`, `refused`. No match: exit 0 with a stderr note. Selector matches > `MAX_SELECTED_RUNS` (1000): exit 2 / 400 `too-many-runs`, never truncated.
- **CLI routing.** Reads and `--dry-run` open the read-only engine and start no host (a dry run plans per Run from `verb_cell` + the Run's status and says so; engine-level refusals only the act can hit — adapter capability, process races — are named as planned-subject-to-act). A selector act goes through the host: `POST /v0/runs/select`, show, confirm, one set-act call. A single target (run id or instance name) skips the token: the per-Run route (`/v0/runs/{id}/…`) or the existing instance route for a name (`/v0/instances/{name}/stop` — byte-identical today).
- **Set tokens (AD-20's "act on a set token").** The token is a correlation handle for the SAME credential that minted it — the bearer still authenticates every call — but it follows AD-22's hygiene anyway: 256-bit OS-CSPRNG, `hkset_` + Crockford base32, stored only as SHA-256, never in a URL (it rides the request BODY as `set_token`; the brief's `?set=` sketch is deliberately not taken — URLs land in logs). TTL 10 minutes; single-use (one act consumes it — reuse after a partial failure re-selects honestly, because the set may have changed); bound to the creator's credential hash (a foreign credential is 403, so a token leaked into a log is useless to another client); ≤ 64 pending, oldest evicted, lazy expiry. In-memory on the host: a pending set is a conversation, not state — a host restart drops it (404 → re-select), which is also why nothing goes into state.db and 21-6 adds no schema step. `runs` in the answer reuses 21-5's `RunSummary`.
- **The select route vs the listing route.** `GET /v0/runs?selector=` (21-5) pages a listing; `POST /v0/runs/select` resolves an ACT set (capped at 1000, tokened). Both exist, both use the 21-9 grammar; acts never page.
- **`hekma budget` shape: `show|set` (no separate `raise`).** `set` with a higher value IS the raise; the direction is surfaced per Run in the outcome (`raised` — re-armed/un-fenced, `lowered` — may fire, `set`, `cleared`, `unchanged`) and in `limits-changed`. A second verb for the same row write would drift (the `hekma policy` precedent: one write verb per row). The authority rule is checked per limit direction inside the job, not per verb. Dollars parse through `parse_dollars_to_micros` (the `policy` precedent).
- **Where a set limit lives: `run_limits`, never instance config.** FR-60 names "a Run through `hekma budget`" as the layer that outranks Policies; 21-3's resolver already reads it (layer 2 over explicit instance config, the 21-9 verb-over-config precedent). The instance `budget.*` keys stay the per-instance layer, and Policies stay the standing rule — `docs/policies.md` says which to use when. Scopes: all four (tokens/dollars × per-run/cumulative) on a process-owning Run; per-run only on a child (cumulative is the hosting instance's, 21-2's ruling); the Breach Action rides the row and passes 21-2's `action_refusal` (so `block` refuses with no wire path, and child `pause`/`stop`/`block` refuse until 23.4). A dollar cap with no resolving Rate keeps FR-20's documented inert-with-notice (surfaced in `budget show`), not the Policy-sourced Anomaly (21-3's scope discipline: explicit operator caps). **And a limit set here BELONGS TO THE RUN** (the 21-9 verb-label precedent): `run_limits` rows cascade with the Run, so even a CUMULATIVE ceiling set this way is enforced against the instance's cumulative ledger only while this Run is open — a fresh `start` mints a new Run without it, and only the instance's `budget.*` config or a Policy covers the next Run. Every surface says so: the `budget set` result row (human and `--json`, the `run_scoped` note), `budget show` (Run-level limits carry source `run`), and the docs pointer to `budget.*` config or a Policy for limits every future Run should carry.
- **One re-arm implementation (no second copy).** 21-3's `re_arm` (in `domain/registry_policy.rs`: the raise half — unlatch, per-reason `WireFence::clear` through `ctx.after_commit`, Anomaly clear — and the breach-at-once half through `pipeline::evaluate` over the new arms) is PROMOTED to the runs domain (`ops.rs` or the new `limits.rs`) in the same change, the policy job calls the promoted function, and the budget job and the config-write path call it too. Three triggers, one rule, one function — the thing the readiness finding asked for. The budget job runs in the Service Host's writer; returned process actions are applied by the engine facade before it returns (D2, as the policy job does).
- **`budget show`.** One Run: the resolved limits with each source (`run`/`explicit`/`policy:<name>`/`default`/`unset`), subtree usage, headroom (21-5's `BudgetView` field names), the latched set, the effective action. Over a Selector: it is a listing read — it pages through 21-5's `list_runs` (default 50, max 1000, cursor) so no read loads the whole Run set (FR-50); the Control API equivalent is `GET /v0/runs?selector=…` items plus `GET /v0/runs/{id}/limits` per Run (parity without a new listing shape).
- **Slow verbs on a set.** `stop`/`drain` wait out their windows. The set-act route issues the per-Run calls concurrently and joins (the host's fleet-drain shape, 17-2); under the coarse locks the engine serializes the ladders, so a set's worst case is the SUM of windows — documented (the 17-2 accepted posture; parallel ladders are the deferred lock-model work, not this story). The CLI bounds its HTTP wait (10 s + matched × the verb's bound, capped at 10 min); past it the command reports that it lost patience and the acts may still be committing (`check with hekma ps`) — never a hang, never a silent pass.
- **Events.** One new Run event kind, `limits-changed` (`prior_limits`, `limits`, cause = the actor), additive with the Run event schema at 1 (the `labels-changed`/`prior_labels` precedent). Breaches fired by a lowering are the existing breach events; stop/pause/resume/drain emit the existing transition + Run events; a set-act needs no envelope event — the per-Run events are the record (AD-14). The OTLP v1 exporter ignores `limits-changed` (no instance; the AD-21 interim).
- **Governance Vectors 1.4.0.** Additive `rearm` case kind + `re-arm` cover tag, appended after every shipped case (1.3.0 bytes unchanged; a consumer pinned to 1.3 skips it). Cases: raise-above-totals re-arms (latch cleared, next crossing re-fires); per-reason fence clearing (one-of-two stays fenced, both clear → unfenced); lower-to-at-or-below fires now with the latch set; and the SAME expected outcome for all three triggers (policy change, run_limits write, config write) — the portability point of FR-44.
- **Engine version.** hekma-engine stays **0.12.0** — no bump, no baseline move in 21-6 (the orchestrator rule: nothing has been released since 21-2's 0.11.0→0.12.0 bump, every story in this unreleased cycle stays on 0.12.0, and the semver gate's baseline already permits breaking changes at 0.12). The public additions here — `LimitActor`, the `limits-changed` kind, the new facade methods — are additive within it.
- **What 21-6 does NOT do.** No hold/release/reroute/reject (23.4 adopts the fan-out then); no `verb_cell` availability flips (23.4); no Caller credentials — the `LimitActor` seam and the Operator-only reality today, Run Keys and announce classes wire in with 22.x; no cross-Node sets (a set is one Node; the Hub story routes verbs per Node); no `start`/`send` selectors (reasoned above); no per-window budgets (standing deferral); no `hekma top` (21.7); no schema step.
- **Deferred-work decisions (the entries naming this story).** (1) *21-9 "Selectors; Routing" (Fibery 608): the Control API has no Selector resolution or set token* — **absorb**: `select`, the set routes, and the `hekma label` migration land here; mark resolved. (2) *19-2 "when the fence lifts": a live Run's fence does not lift on a raised ceiling; trigger 21.6* — **absorb**: the budget-set AND config-write raise paths clear matching reasons per reason through the shared `re_arm` (the Policy path already did, 21-3); mark resolved, and update `docs/hosting.md`/`docs/commands.md` fence sections ("it lifts when the Run ends" becomes "or when the matching ceiling is raised above the totals"). (3) *The readiness gate's vectors-ownership finding* — **absorb**: the re-arm vectors land here as 1.4.0 (21-2 shipped 1.2.0, 21-3 ships 1.3.0).

## Ask First

Each is a public-contract choice taken under the delegated brief; the recommendation is the spec's current text.

1. **`hekma budget show|set` with no separate `raise` verb** — `set` with a higher value is the raise, the direction named per Run (`raised`/`lowered`) and in `limits-changed` (vs a literal `show|set|raise` reading of FR-50). Recommended: as written (one write path, one re-arm path; two names for one row write would drift).
2. **The set token rides the request body (`{"set_token": …}`), never a URL** (vs the `?set=` query form). Recommended: body (AD-22's never-in-a-URL discipline; URLs land in logs).
3. **Token semantics: 10-minute TTL, single-use, bound to the creating credential, in-memory, ≤ 64 pending** (vs reusable, durable, or longer-lived tokens). Recommended: as written (a token pins a conversation, not state; restart → re-select is honest and cheap).
4. **`start` and `send` do NOT gain `--selector`** (vs putting it on every `agent` verb). Recommended: as written (start acts where no Run exists; send is one agent's content-carrying channel — FR-24/FR-49).
5. **A Run that ended between select and act is a per-Run refusal; the rest of the set acts** (vs aborting the whole act). Recommended: per-Run (FR-50's letter: exactly that set, per-Run results; a whole-set abort would make one ended Run block the operator's stop).
6. **`budget set` writes `run_limits` only and never instance config, and a limit set this way belongs to its Run** (verb-label precedent: it ends with the Run, cumulative included; `budget.*` config or a Policy for limits every future Run should carry); instance `budget.*` stays the per-instance layer, Policies the standing rules. Recommended: as written (FR-60's own precedence sentence).
7. **A set-act on slow verbs is issued concurrently and documented as Σ(windows) worst case under the coarse locks, with a bounded client wait and a lost-patience note** (vs an async job/poll surface). Recommended: as written (the 17-2 accepted posture; the async surface is new API for a deferral to unblock).
8. **Governance Vectors 1.4.0 with the `rearm` kind covering all three raise triggers.** Recommended: as written (the readiness finding's owner answer).
9. **hekma-engine stays 0.12.0 — no bump in 21-6** (the cycle rule, now uniform across 21-3/21-5/21-6: nothing released since 21-2's 0.11.0→0.12.0 bump). Recommended: stay.
10. **`budget show` pages through the listing machinery when a Selector is used** (vs reusing the 1000-cap act resolution for the read). Recommended: pages (FR-50: no read loads the whole Run set).
