## Intent

**Problem:** The Shims exist (24-1), holds belong to their Runs (23-4), and the shared Metering Proxy listens on a sticky port (23-1) — but every restart of the Service Host still stops the world: SIGTERM drains and stops every Agent Instance (FR-41's only mode), a `hekma self-update` leaves the Operator to stop and restart the host by hand (every wire client sees refused connections, every held call's connection breaks without its typed answer), and nobody checks whether the service manager would kill the Shims with the host anyway. Handoff Mode — FR-55's rule that Runs survive the Service Host restarting or upgrading — has a Gate: opt-in until the FR ships, the default after. Nothing implements it.

**Approach:** Give `hekma serve` a second shutdown mode and a successor. **Handoff Mode** (`--handoff/--no-handoff`, default off until this story's acceptance passes): on the shutdown signal the host stops the Control API, answers each held call with the one retryable `503 hekma_hold_interrupted` 23-4 already speaks, lets in-flight calls finish within the existing grace, releases every Shim connection *without a single stop RPC* (one `shim released` event per Run), flushes and closes the store writer, and exits — the Shims keep their processes running, holds and Leases are durable rows, and the next Service Host reattaches through 24-1's adopt path showing the same Runs, Leases and holds. **The in-place upgrade** (`hekma serve --upgrade`, a Control API verb, or a signal; triggered by `hekma self-update` after it replaces the binaries): the predecessor launches its own successor, which connects to a versioned handoff channel inside the state directory (AD-23's access rules); the predecessor stops accepting on the Metering Proxy's listener *without closing it*, does the Handoff-Mode release above, and then hands the listening socket and `host.lock` over; the successor migrates state.db, reattaches every Shim, starts serving (rewriting `control.json` atomically), and only then does the predecessor exit — the kernel's listen backlog carries new connections across the gap, so the Metering Proxy refuses no connection during the upgrade. **Service-manager checks** (systemd `KillMode` via `INVOCATION_ID`, the Windows job chain's breakaway permission) verify what they can at start, warn when the setting would take Runs down with the host, and say honestly "unverified" where they cannot tell — and a handoff is never reported successful for a Run whose process did not survive. When this story's acceptance suite passes on all three OS legs, the default flips (Ask First O1) and the release says so.

**Acceptance Criteria:**
- Given a serving host with two Shim-backed Runs and Handoff Mode on, when SIGTERM arrives, then no stop RPC is issued to any Shim (a stop-suppression seam pins it), every held call is answered with the one retryable `503 hekma_hold_interrupted`, in-flight calls finish within the grace, one `shim released` event per Run is outbox-committed, the writer is flushed and closed, the host exits 0 — and both agent processes are still alive, with the next `hekma serve` reattaching both (claim CAS'd, `shim connected` events) and showing the same Runs, Leases and holds, with spend so far within FR-10's flush bound.
- Given the same host with Handoff Mode off, when SIGTERM arrives, then the FR-41 drain runs exactly as today (the bounded ladder, the concurrent stops, the honest roll-up) and no Run survives — the mode switch changes nothing else.
- Given `hekma serve --upgrade` on a serving host (or the Control API verb, or the signal), when the sequence runs, then: the successor is launched and hellos on the handoff channel with the right version and token; the predecessor stops accepting, answers held calls, releases Shims, flushes and closes its writer; the listening socket and `host.lock` are handed over (Unix: both processes observably hold each during the transfer, the predecessor's exit leaves exactly one holder; Windows: the successor acquires within the documented bounded window); the successor migrates state.db (`user_version` advances; an older binary then refuses the dir); every live Shim is reattached; the successor serves the Control API with a rewritten `control.json`; and only then does the predecessor exit — a continuous client poller against the Metering Proxy records ZERO refused connections across the whole sequence, and every call the sequence interrupted is a recorded retryable error (SM-7's in-place-upgrade arm).
- Given a held call interrupted by the upgrade, when its client retries, then the retried call lands on the successor, is held again from the first snapshot the successor published (or forwarded if the hold was released), meters to the same Run, and the Run saw exactly one retryable error for the restart — never two.
- Given a successor that dies (a kill seam) before its engine open, when the predecessor notices, then the predecessor resumes full service within a bounded window (writer reopened, accepting again, its Shims reattached through the adopt path), one `handoff aborted` event lands naming the reason, state.db's `user_version` is unchanged, and a client poller recorded no refused connection throughout.
- Given a successor that fails after its engine open (a migration-failure or reattach-failure seam), when it cannot reach `ready`, then the sequence is forward-only: the successor retries to readiness (or reports `handoff {result: partial}` naming each lost Run), the predecessor still exits last, the old binary refuses the migrated dir, and no surface claims the handoff succeeded for a Run whose process did not survive.
- Given a second plain `hekma serve` against the state root at any point — before, during or after the sequence — when it presents no handoff token, then it is refused as today (the holder named, exit 2), and only the tokened successor ever takes `host.lock`.
- Given reattach, then no credential changes: a Run Key presented right after the successor's `ready` is honoured exactly as before, run ids, budgets, latches, Leases and hold reasons are untouched, and a byte scan of state.db, its WAL/SHM and the state directory finds no handoff token in cleartext.
- Given the service-manager checks, when the host starts under systemd with `KillMode=control-group` (an `INVOCATION_ID` + query seam), then the startup warning names the setting and the risk, `handoff_check` reads `unsafe` on every surface, and the host still serves (drain-and-stop remains usable); given `KillMode=process` or `none`, then `verified`; given no manager the checks can read (launchd, Docker, a bare terminal), then `unverified` with the how-to-check line, never a fabricated verdict; given the Windows job chain with breakaway permitted on every job (or no job), then `verified`; given any job in the chain without it, then `unsafe` + the warning; given a query that fails, then `unverified`.
- Given the flip (T11), when the acceptance suites named above are green on all three OS legs in CI, then a `hekma serve` started with no flag and no env runs Handoff Mode by default (SIGTERM releases, a `--no-handoff` host still drains), and the CHANGELOG/RELEASE_NOTES state the change in the same release.
- Given `hekma self-update` with a serving host and a newer release (manual-channel seams), when the binaries are replaced, then the upgrade verb is called through the host, the handoff runs, and the command reports the outcome; with `--no-restart`, or with no host running, then no upgrade is attempted and the note says so honestly. **[pending O4]**
- Given the pre-Shim edge: a direct-record Run still running from before the Shim stories, when SIGTERM arrives in Handoff Mode, then the Run is released, not stopped — on Unix it survives for the direct adopt path; on Windows it dies with the Job — and the handoff report and `hekma ps` say which, never a blanket success claim. **[pending O7]**
- Given `hekma serve --upgrade` with no host serving the state root, when the CLI routes it, then the command refuses with a remediation (start the host first) and exits in the existing usage class; given the Control API upgrade route presented a non-Operator credential, then it is refused `403 forbidden` (the matrix).
- Given any handoff or upgrade path, then every event, notice, `--json` line and log the sequence produces carries no secret, token, bearer or Run Key (token ids only), user-facing text carries no planning ids, and `check_docs.py`'s vocabulary holds.
- Given handoff: fmt, clippy `-D warnings`, the workspace tests, `check_docs.py` (+ `--self-test`), `test_automation.py` pass on all three OS legs; changed-line coverage ≥ 95%; the two-pass review (own + one independent adversarial pass briefed on the security review's §7 and this spec's threat list, plus the AI-55 release-surface pass over the default flip and the new flags/routes) done.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-20 fixes the upgrade sequence verbatim ("an in-place upgrade (`hekma serve --upgrade` or a signal) launches the successor itself; the successor connects to a handoff channel inside the state directory …; the predecessor stops accepting, flushes and closes its store writer; the successor then receives the listening socket and the `host.lock` transfer, migrates state.db, reattaches Shims, and only then does the predecessor exit"), the channel's protocol-version rule, `SO_REUSEPORT`-never, and the socket-activation carve-out. AD-23 fixes the Handoff Mode release ("releases its Shim connections without stopping them, persists holds and Leases, and exits"), holds-belong-to-the-Run (a held call may see ONE retryable error and is re-held), the service-manager settings (systemd `KillMode=process` or `none`; `control-group` and `mixed` both kill Shims; Windows breakaway on every job in the chain), the unverified honesty and the never-report-success rule. FR-55 fixes the no-refusal guarantee for in-place upgrades, the per-Run one-error bound, identity/Lease continuity, and the Gate. AD-26 fixes that the socket hands over and held calls follow AD-23. 23-4 already built the graceful interruption row; 24-1 already built release/reattach, the claim CAS and the `shim` events. What this story deliberately does NOT own: the crash matrix — `kill -9` hold/call honesty, cleanup-vs-adoption by mode, SM-7's full suite (24.3); bypass detection (22.4); scale (24.4); telemetry (24.5).
- **"Persists holds and Leases" is a flush, not a new write path.** AD-23's SIGTERM sentence predates 23-2/23-4 making Leases and hold reasons durable rows committed by the writer. The predecessor has nothing new to persist: the right reading is that its writer must be FLUSHED AND CLOSED before the successor opens — which is exactly AD-20's order. The spec states it that way; a second persistence mechanism would fight the single-writer rule.
- **Why the socket must not close, and who holds it when.** FR-55's "refuses no connection during an in-place upgrade" is a kernel fact before it is a protocol fact: the listening socket's backlog keeps accepting SYNs while NEITHER process calls `accept`, so the guarantee holds iff the socket never gets an unowned moment. That drives the mechanics: Unix passes the descriptor twice (the listening socket and the locked `host.lock` file — an `flock` lives on the open file description, so `SCM_RIGHTS` shares the SAME lock; both processes hold it; the predecessor's close transfers it with no gap, and a third host is structurally excluded); Windows duplicates the socket (`WSADuplicateSocket`, bounded to the successor's pid) and accepts the honest lock gap (exit-then-acquire, the documented self-healing re-acquire — the one place the OSes differ, named in the docs and surfaced as a bounded window). `SO_REUSEPORT` stays banned (AD-20): a shared bind would give the no-refusal guarantee away to the scheduler and reintroduce two accept loops on one port.
- **The point of no return is the successor's engine open.** Rollback questions resolve on that line: before it, the predecessor has lost nothing it cannot take back (`resume_handoff` reopens the writer, resumes accepting, re-supervises through the adopt path against its own records — the Shims were released, which is precisely the state 24-1 builds for a crash); after it, state.db's one-way `user_version` means the old binary cannot re-open the directory, so the successor retries forward and reports honestly. This is the AI-19 discipline applied to the upgrade: "rollback" is only ever claimed where it is actually possible.
- **The single-owner invariant during handover.** FR-41 says exactly one Service Host owns a state directory; the handoff must not become a backdoor. The invariant: the predecessor keeps `host.lock` until the successor holds it (Unix: shared description; Windows: until exit), the writer closes before the successor's engine opens (no two writers ever), and the only second serve process allowed near the lock is the one that presented the handoff token on the channel. A plain second `hekma serve` during the sequence gets today's refusal.
- **The Control API is not the Metering Proxy.** FR-55's no-refusal guarantee names the Metering Proxy; the Control API listener is re-bound by the successor with a fresh loopback endpoint and token, `control.json` is rewritten atomically, in-flight Control API requests complete within the predecessor's grace, and SSE streams reconnect by cursor (the outbox is durable — FR-41's export-before-exit design). A CLI command landing in the window is covered by 21-4's discovery retry (it re-reads `control.json`, up to 10 s). The docs say this plainly instead of implying both sockets carry the guarantee.
- **Handoff Mode is a host mode; the handoff seams are engine-owned.** The host owns signals (AD-20); the engine owns the proxy listener, the writer and the Shim connections — so `prepare_handoff`/`resume_handoff` are public engine API the host drives. Embedders get the same seams without the host crate (documented in `docs/embedding.md`); the successor-launch choreography stays host-side because "launches the successor itself" is a host sentence. The argv replay is the honest mechanism (env rides through inheritance); flag-drift between versions is bounded by the successor refusing argv it does not understand — the invalid-usage class, never a crash.
- **The one-retryable-error bound is per host generation.** FR-55: "Each Run sees at most one such error per restart." A parked call's connection ends once per predecessor exit; a retry that parks again on the successor has consumed its one error; if a SECOND upgrade interrupts later, that is a new restart and a new one. The proxy's held-call answers are once-per-park-per-generation by construction (23-4's graceful shape), and the spec pins the wording in the docs rather than adding a counter.
- **Pre-Shim Runs: honest, not magical.** A direct-record Run's process is owned by the engine's own handles; "release without stopping" can only mean what a crash means today (Unix: the process survives, the direct adopt path takes it back; Windows: kill-on-close takes it). The alternative — running the stop ladder for just those Runs under Handoff Mode — would be a stop NFR-9's list does not authorize. Releasing with a per-Run report is the only option that is both true and legal (Ask First O7 records it).
- **The service-manager checks are read-only and honest by design.** The checks run at start (never on a hot path), they read what the OS will admit (`INVOCATION_ID` + the unit's `KillMode`; the job chain's breakaway flags), and every cannot-tell lands in `unverified` with a how-to-check line — AI-18's surfaced-not-silent applied to a fact Hekma can only partially observe. `unsafe` warns but never refuses: a default systemd unit or a Docker container would otherwise make Hekma unstartable, and the Operator may be running drain-and-stop deliberately (Ask First O5).
- **Threats considered** (review ids where they exist; N-ids are this story's):
  - a handoff token stolen by a same-user process → Env-only delivery, `0700` channel dir + peer-uid/DACL, token hashed nowhere needed (ephemeral lifetime), the same-user-is-Operator Stated limit documented [N1];
  - the listening socket leaking to an agent process during handover (close-on-exec cleared) → cleared on exactly ONE descriptor after the fork boundary the successor owns, re-set on failure; the conformance fake's descriptor listing proves the agent never sees it [T4.3, R2.4 → N2];
  - a hostile second process presenting on the handoff channel → the token gate + AD-23's transport access rules; a wrong-version or wrong-token hello is refused and reported [N3];
  - two writers on state.db during the window → writer closed before the successor's engine open; the single-owner invariant above [N4];
  - a third host stealing `host.lock` in the Windows gap → bounded window, self-healing re-acquire, the successor's acquire-failure surfaces as a failed upgrade with the holder named [N5];
  - the successor reattaching a Shim while the predecessor still supervises it → 24-1's single-controller Shims answer `busy`; the release strictly precedes the reattach [N6];
  - a Shim too old/new to speak after an upgrade → report-never-kill (AD-20), the Run honestly degraded, named in the `ready` frame [N7];
  - an upgrade replayed at a version the state dir cannot go back to → one-way `user_version`, forward-only after migration, the old binary's refusal unchanged [N8];
  - a held call double-billed by a retry → a retry is a new call with a new call id (23-1's rule); the interrupted park's record carries outcome `shutdown` [N9].
- **Version.** New public types (`HandoffMode`, `PreparedHandoff`, `Engine::prepare_handoff`/`resume_handoff`, `EngineEvent::Handoff`, `ServeOptions.handoff`), new CLI flags and Control API routes, one `windows-sys` manifest feature: hekma-engine **stays 0.12.0** (the cycle rule), announced in the Unreleased banners; the default flip is a release-surface change that rides the AI-55 two-pass review. No new crate; `nix`'s `socket` feature is already in-tree from 24-1.
- **What this story does NOT do.** No crash-recovery matrix, `kill -9` hold/call honesty, cleanup-vs-adoption by mode, or SM-7's full suite (24.3 — this story proves only SM-7's in-place-upgrade arm as its flip evidence); no bypass detection (22.4); no scale work (24.4); no telemetry changes (24.5); no Hub or multi-node upgrade (Epic 25, AD-24 reserved); no migration of live direct-record processes into Shims (impossible — 24-1's ruling stands); no change to the stop ladder, the drain path (FR-41 stays available), the held-call wire rows (23-4's verbatim), or the sticky-port behavior (23-1's).

- 2026-11-14 — **phase 2 built** (stacked on phase 1): the in-place upgrade on Unix.
  - **T3:** `hekma_engine::handoff`. `handoff-rpc v1` frames (`hello`, `offer`, `ready`, `abort`) as JSON lines over a Unix socket in the owner-only `shims/` directory, with the peer's uid checked. A 256-bit token travels in `HEKMA_HANDOFF_TOKEN`; it is compared by hash, and the successor removes it from its environment before any agent starts. The transport is `backends/unix/handoff.rs`: `SCM_RIGHTS` through nix's `uio` feature (a manifest feature, not a new crate). On Windows every call reports `Unsupported`.
  - **T2:** `Engine::shutdown_for_upgrade`. The proxy's accept loop stops but hands its socket back instead of closing it, then the engine releases and drains as in phase 1. `MeteringProxyOptions::inherited_listener` (`InheritedListener`) lets the next engine serve on that socket. Releasing a Shim agent now also clears this engine's claim on its spawn record (`Registry::release_spawn_owner`), so the successor adopts it while the predecessor is still alive. Without this, the successor skipped every agent as "supervised by another live engine", which the end-to-end test caught.
  - **T4:**
    - The trigger is `POST /v0/host/upgrade` (Operator only; `409 upgrade-unsupported` without a transport) and `hekma serve --upgrade`. The CLI never auto-starts a host; with none serving it refuses with exit 2 and a remediation. It waits up to 150 s for `control.json` to name a new pid.
    - The predecessor launches `<current exe> <its own args> --handoff-from <channel>`, dropping any earlier `--handoff-from`. `hekma-host` accepts the flag too.
    - The predecessor waits 30 s for the hello, then stops the OTLP exporter and the Control API. It leaves `control.json` in place, so no CLI starts a third host meanwhile.
    - It then runs the upgrade shutdown, waits until it holds the engine alone and drops it (closing the store writer), and sends `offer` with the socket and the locked `host.lock`. It exits 0 on `ready`.
    - The successor joins before anything else and adopts the same lock (`HostLock::adopt`, which rewrites the holder record). It opens the engine on the inherited socket, serves, and sends `ready` with the number of live agents.
  - **T5, partly:** a failure before the hello, such as a successor that cannot start or connect, a wrong token or another major version, kills the successor, notes why, and the predecessor keeps serving with nothing stopped. A failure after the offer is not rolled back: the predecessor exits non-zero and says the agents keep running in their Shims, and the next `hekma` command starts a host that reconnects to them. **Drift:** the spec's rollback between the offer and the successor's engine open is deferred.
  - **Tests:**
    - the transport, on real descriptors: the same listening socket, and the same lock held by both until the last copy closes;
    - the channel's token, abort and timeout paths;
    - the engine: the socket is handed back and is still connectable, and the next engine serves on it and adopts the released agent while the first is alive;
    - the route;
    - a real-binary end to end: an auto-started host with a Shim agent is upgraded by `hekma serve --upgrade` while a poller dials the proxy every 5 ms. There are zero refused connections, the old host exits, `control.json` names the new pid, the agent survives, and the new host reaches it with `send` and stops it. It passed five runs out of five.

- 2026-11-14 — **phase 3 built** (stacked on 24-3 phase 1, #424): the service-manager check (T6) and `GET /v0/host` (T9's read).
  - **T6:** `crates/hekma-host/src/service_manager.rs`, read-only and run once at start. Under systemd (`INVOCATION_ID` set) the unit is named from `/proc/self/cgroup` (a user unit asks `systemctl --user`) and `systemctl show --value -p KillMode <unit>` is classified: `process`/`none` → `verified`, `control-group`/`mixed` → `unsafe`, with a warning naming the setting and the fix. An unknown value, an unreadable query, an unnamed unit, or no systemd at all → `unverified`, with how to check. When agents run in their own Shim, the started notice carries it. It never refuses to start (O5). The checker is runtime-checked, not cfg'd, and its classification is unit-tested with an injected query.

- 2026-11-14 — **phase 4 built** (stacked on phase 3, #425): T9's `self-update` trigger, on O4's recommended option (a). After a successful binary replacement, `hekma self-update` asks a host serving the default state root to hand over in place, through `serve --upgrade`'s own path, and waits for `control.json` to name the successor. With no host running it asks nothing and says so; if the upgrade fails, the note says to restart the host. The update itself never fails on it. `--no-restart` skips it. The host-present path is not unit-tested: it is `serve --upgrade`'s tested path. Only the no-host note is tested here, since `self-update` reaches the network.
