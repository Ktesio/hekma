## Intent

**Problem:** The shared Metering Proxy (23-1, in build) already adds the outbound identity headers — `x-hekma-run-id` and `x-hekma-labels` — to every forwarded call, on by default, never content and never a credential (AD-26; security review R5.10/T6.4). But the Operator switch 23-1 ships is one serve flag, `--no-identity-headers`, and a flag cannot reach the host that matters: the **auto-started** Service Host (21-4) is launched with fixed arguments by the first CLI write, so an Operator who wants the headers off toward a provider — exactly the case PRD §6's note names ("FR-51's identity headers send run ids and labels … to the provider or gateway a call already goes to, and the Operator can turn them off") — has no durable way to say so, nothing to read back that says whether they are on, and no way to scope them (a binding pointed at LiteLLM wants them; a binding pointed straight at a provider may not). And the public promise has no public page: FR-51's "a gateway in front of the provider (e.g. LiteLLM, Portkey) can attribute them" and PRD §8's "Not a model gateway" exist in `docs/` only as one future-tense line on a page marked Planned, and no recipe shows an Operator how to put Hekma in front of a gateway at all.

**Approach:** Make the switch a **durable, live, Operator-only setting**: `proxy_state` gains `identity_headers` (default `1` = on), set through `PATCH /v0/proxy` and `hekma proxy set identity-headers <on|off>` (both routed through the Service Host, one `proxy_setting` event each, committed and published by the store writer before the acknowledgement), and carried on the **published snapshot's root** so the proxy applies it to the very next forwarded call — no restart, and the auto-started host picks the stored value up because it is in state.db, not in argv. A per-binding tri-state override (`run_bindings.identity_headers` ∈ unset|on|off, `hekma binding set <name> --identity-headers on|off|inherit`) resolves per call: the call's binding when it has one and set, else the root setting. 23-1's `--no-identity-headers` (and a new positive `--identity-headers`) stay as **per-run overrides** of the root for one explicit `hekma serve`, never persisted, with a start note when flag and stored value disagree. The header names, the strip rule and the never-list are **confirmed unchanged** (`proxy-wire v1` is additive-only): exactly the run id and the Run's labels; never request or response content, never an `hk_` token or token id, never a limit, total or instance name. A new `docs/gateways.md` carries the two recipes — a binding in front of a gateway (base-URL-only clients) and a supervised agent via `metering.upstream_base_url` — with the "not a model gateway" statement, what the gateway sees and never sees, the switch, and the custody note (a gateway origin must be declared beside a custodied key when 22-2 ships); every gateway-side fact the repo cannot source is marked "to verify against the gateway's docs", and the recipes are documented as **examples**, not validated integrations (the FR-52 CrewAI/LangGraph discipline — no "supported" claim without validation this repo's network-free CI cannot run). Schema takes the next number after the landed chain; hekma-engine stays 0.12.0.

## Design Notes

- **What this story owns, and what it only confirms.** 23-1 built the headers, the names, the strip rule and the default (its O3, recommended on; Islam's ruling still pending). 21-8 owns the **switch as a durable Operator surface** (global + per-binding + the per-run flag), the **live application** (snapshot root), the **read surfaces**, the **recipes page** and the **not-a-model-gateway statement** — FR-51's bullet and PRD §8's line made public. Nothing here renames a header, edits a wire body, or changes a Run status: `proxy-wire v1` stays additive-only, and the spec's confirmation of the names is an Ask First O-item (public contract).
- **Why a snapshot-carried setting, not a second flag.** The auto-started host (21-4) is launched with fixed arguments by the first CLI write — a serve flag can never reach it, so a flag-only switch fails FR-51's "the Operator can turn them off" for the common deployment. The stored value lives in `proxy_state` (state.db, beside the sticky port), is written only through Operator-authority surfaces (the matrix), and rides the published snapshot root — so the proxy, which already clones one snapshot `Arc` per call and takes no engine lock (AD-26), applies a change to the very next call. `ProxyShared.identity_headers` (the 23-1 open-time bool) becomes the per-run flag override the host passes; embedders keep the `MeteringProxyOptions` default. 22-2's Ask First 5 called `--no-identity-headers` "a flag, not a config key" — this story keeps the flag exactly as 23-1 built it and adds the **durable setting beside it**; the precedence (flag > stored > default-on) and the disagreement note are the honest seam between them.
- **Per-binding resolution, once, in the hot path.** `resolve_identity_headers(snapshot, binding)` is a pure function: the call's binding override when the call went through a binding with one set, else the snapshot root. It runs where `forward.rs` already holds the snapshot and the identified target — no new hot-path work (a branch). Supervised Runs' Run-route calls and the unattributed Run have no binding and follow the root. Released held calls and rerouted calls (23-4) forward through this same step, so they carry headers per the setting **current at their forward** — 23-4's "identity headers still apply" holds without a second mechanism; its release-time re-validation reads the then-current snapshot for everything already.
- **What is sent, precisely.** `x-hekma-run-id`: the Run's id (`run_` + ULID, or a legacy id). `x-hekma-labels`: **all** of the Run's labels, bound and Caller, as sorted, percent-encoded `k=v` items, comma-separated (`wire::labels_header_value`, unchanged). The labels are already validated (charset, ≤ 16 per hint, the Caller guard at creation); a Caller label reaches the gateway the call already goes to, where the client's own request content already reaches — the allow-list alternative (O2) would tighten it at the cost of a second knob. What is **never** sent: request or response content (any byte), an `hk_` token, a token id (R5.10 — the token id is a label for Hekma's records, not a wire value), a limit, a total, an instance name, a model, a cost figure. The breach header `x-hekma-breach` is a **response** header toward the client and is unchanged.
- **Schema and version.** One additive, crash-atomic, one-way step taking the next number after the landed chain (v22 expected if 19/20/21 land as specced — 22-2's v19, 23-2's v20, 23-3/23-4's v21; take whatever is next at build). Two columns, no backfill (`NULL`/absent = inherit/on). No public type is removed; `ProxySettings`, `EngineEvent::ProxySetting` and the binding event's additive field ride existing schema versions (the 22-1/23-1 additive-field precedent). hekma-engine stays 0.12.0 (the cycle rule); no new dependency.
- **The recipes, sourced honestly.** The repo sources: Hekma can sit in front of LiteLLM/Portkey (PRD §8, FR-51); `metering.upstream_base_url` can target them (the pivot proposal's A4); bindings take an `http` upstream "for a local gateway" (23-1); a binding's custodied-key reference is inert until custody (22-2, not built — so in both recipes **the gateway's key travels as the client's own `Authorization`**, exactly the pre-custody posture). The repo does **not** source either gateway's base URL, port, key header, or whether it can read custom headers for attribution — every such fact in `docs/gateways.md` is written as a placeholder marked "to verify against the gateway's docs", and the page never claims the gateway attributes by the headers (it says the headers are **available** to it). "Example, not validated" follows FR-52's CrewAI/LangGraph discipline; this repo's CI is network-free (the hermes-shim precedent), so "supported with CI validation" is not an honest option here — promotion to validated would follow the `docs/agents.md` recorded-manual-pass pattern (O4).
- **Custody through a gateway, stated for later.** The security review trusts a gateway "for A1's own origin" and has gateways see identity headers; 22-2 (not built) pins each custodied key's origins and paths beside the key. A gateway origin is not in the built-in provider table, so the recipes' custody note says: declare the gateway's origin (and its paths) beside the key in the secrets file when custody ships; a custodied key never leaves its pinned origins, and reroute routes carry their own key or none (23-4). Until then the gateway sees the client's key, the run id and the labels — never a Run Key (23-1's strip and API-key-slot refusal already guarantee it; this story's tests re-pin it with the switch in both positions).
- **Threats considered** (review ids where they exist; N-ids are this story's):
  - content or a credential in an outbound header [T6.4, R5.10, T3.6] → run id and labels only; the strip rule and the API-key-slot refusal unchanged; sentinel matrix extended across both switch positions;
  - Caller labels as a channel to the gateway [N1] → the client's content already reaches the same destination; labels are charset-validated and capped; the allow-list option (O2) and the off switch are the valves;
  - the switch reachable by the agent [N2, T4.8] → state.db behind Operator-only routes; no instance config key; a `config.toml` edit cannot reach it;
  - a stale or ambiguous setting [N3] → committed and published before ack; one snapshot root; `forced_by_flag` and the disagreement note make the flag's per-run override visible;
  - the recipes overclaiming [N4] → example wording, "to verify" markers, the docs probe, `check_docs.py`'s vocabulary pass;
  - renaming a wire name by accident [N5] → the names are confirmed-unchanged ACs and table-tested against `wire.rs`'s constants.
- **What 21-8 does NOT do.** No new header, no change to the strip rule, the breach header or any wire body (public contract confirmed, not edited); no custody, origin pinning or path scope (22-2); no reroute or hold (23-4 — its queues read the current setting at forward by construction); no announce or Lease surface (23-2); no inbound OTLP (23-3); no non-loopback or TLS surface (22-5); no OTLP metric changes; no per-instance `config set` key (the proxy is per data-path owner, and an instance's config file is agent-writable); no gateway integration code, no gateway binary in CI.
- **Base and order.** Build on the landed chain after 23-1's in-build tail merges (the proxy wiring, `hekma binding`, `--no-identity-headers`, `docs/metering-proxy.md` — this branch carries the engine modules and the option but not the wiring); ride whatever schema number the chain reached, taking the next. The epic order places 21.8 after 21.7 (`hekma top`); this story has no dependency on it — the orchestrator may swap the pair.
