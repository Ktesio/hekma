## Intent

**Problem:** The `observed` Control Depth has no producer. `ControlDepth::Observed`, its verb × depth cells (list and usage from its telemetry, budgets and `warn` honored, every acting verb fails fast), the Glossary's strict ladder and the FR-19 amendment ("`observed` Runs carry only the usage their own telemetry reports, labeled estimated") all exist on paper — the 2026-10-30 reviews called the depth a GAP and the fix pass answered them with FR-51's inbound-OTLP bullet — but nothing in Hekma accepts telemetry from a client: a framework flow that only exports OTel cannot become a Run, FR-52's third announce channel (an OTel resource attribute, which "issues no Run Key") has no receiver, `RouteFamily::OtlpIntake` exists in the authority matrix with the Announce cell open and no route behind it, the per-binding `hk_ann_` credentials 23-1 issues are accepted by no OTLP surface, and `docs/attach.md` still promises inbound OTLP "coming". Inbound telemetry is also cumulative by OTLP convention: committing posted counters naively would count the same tokens on every batch, and a Run whose calls already pass through the Metering Proxy would be metered twice.

**Approach:** A receiver route — `POST /v1/metrics` on the Control API listener (AD-28), OTLP/HTTP+JSON only — in `hekma-host/src/otlp/intake.rs`, authenticated by the announce-scoped credential class through the already-open matrix cell. From an accepted batch the receiver reads exactly three things: the resource attribute `hekma.run.external_id` (the Run identity, validated like a hint id), `hekma.label.*` resource attributes (Caller labels through the guard), and `gen_ai.client.token_usage` cumulative sum data points carrying `gen_ai.token.type` ∈ input/output/cached — nothing else is read, and nothing else is stored. The route is a thin adapter: after pure shape validation it calls one new engine facade, `ingest_telemetry`, whose single writer job rides 23-2's `announce` job (the OTel arm: `credentialed: true` because an `hk_ann_` was presented, and no mint — this channel never issues a Run Key or refresh credential, FR-52), renews the Lease and stamps `last_activity_at` (a telemetry post is a sign of life; a `silent` Run returns to `active`), diffs each token type's cumulative value against a new durable `telemetry_counters` row (equal-or-lower values are zero delta except a lower value, which re-bases to the client's restarted counter), commits positive deltas as usage rows with `metering_source: "telemetry-reported"` (dollars always `estimated`, priced by 23-1's wire-Run rule), and evaluates budgets in the same transaction — `warn` executes at `observed`; `pause`/`stop`/`block` keep the existing depth fallback because an observed Run has no wire path, and nothing is stopped, held or fenced (NFR-9). A Run that already has a wire path keeps per-call metering as its one truth: its telemetry deltas are skipped, counted and surfaced in the response's OTLP `partialSuccess` — never double counted. Binary protobuf and gRPC stay deferred behind their named trigger; the docs show an OpenTelemetry Collector translating. Schema v21; hekma-engine stays 0.12.0.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-28 (ruled 2026-10-30) fixes the whole receiver shape: `/v1/metrics` on the Control API listener under the announce-scoped credential, `hekma.run.external_id` + `hekma.label.*` as the identity, `gen_ai.client.token_usage` as the only usage source entering the AD-7 pipeline as `telemetry-reported` and always `estimated`, nothing else stored, protobuf/gRPC deferred with a Collector translating. FR-51's inbound-OTLP bullet and FR-52's third channel (which "creates or updates the Run's identity and Lease but issues no Run Key") are the FR teeth; FR-49's `observed` column is the behaviour contract; the 2026-10-30 review GAP ("no FR says how a Run becomes `observed`") closes here. 23-2 built the machinery this story rides: the `announce` job (its Design Notes promised the signature shaped for the OTel arm — `credentialed: true`, no mint), the binding-namespace identities, Leases and the sweeper, and the opened `Announce → OtlpIntake` matrix cell. 23-1 issued the per-binding `hk_ann_` credentials and named this story as their OTLP consumer. If 23-2's built flag names differ, ride them and record drift in the Spec Change Log.
- **The receiver is a host adapter; the money stays in the engine.** The route parses, validates shape and calls one facade (`ingest_telemetry`) — no pricing, identity or ledger logic in `hekma-host` (AD-20's "handlers stay thin projections"; AD-1). The intake structs are a new Deserialize mirror of the opentelemetry-proto JSON mapping beside the exporter's Serialize-only `payload.rs`, which is the frozen `otlp-metrics v1` exposition and is not touched: AD-21's amendment is explicit that inbound OTLP is AD-28's, not the exporter's, and 22-3 set the precedent that no new family gains a v1 counter — skipped-point counts are host diagnostics and a `partialSuccess` field, never an exported metric (the unscented-counter pattern).
- **One job, and the diff is the idempotence.** Inbound `gen_ai.client.token_usage` points are cumulative counters (OTLP convention, and what every OTel SDK exports); committing them verbatim would re-count the same tokens on every batch. The job therefore keeps one durable row per (run, token type) — the last cumulative value seen — and commits only the forward difference. This one row is three guarantees at once: no re-count across batches, idempotence under client retries (a re-delivered batch diffs to zero), and crash safety (the counter commits in the same transaction as the delta rows it produced). A lower value than stored is a client counter reset (process restart): the job re-bases — commits the new value as the delta — and notes it in one bounded diagnostic; the alternative (treat a reset as unknown and skip) would silently under-meter every restarted client. The key space is bounded by construction (three token types), so no attribute cardinality can grow it.
- **One Run, one metering source (the double-count rule, AI-18-honest).** An observed Run's only usage is its telemetry; a Run with a wire path already has call-accurate per-call metering (23-1, deduped on (run, call id)). When both arrive for the same identity, the ledger must not sum them. The rule: **a Run with proxied usage keeps per-call metering as its one truth**; its telemetry deltas are skipped, counted, and surfaced in `partialSuccess` with a static reason — skipped-and-surfaced, never skipped-and-silent, and never recorded-then-excluded (shadow rows the rollups must filter forever are a new honesty burden with no FR behind it). The Lease still renews: the post proves the client alive even when its tokens are already metered. Depth changes interplay: telemetry alone never changes a Run's depth (only its own wire traffic or a minting announce does, 23-2), so the rule keys on the Run's wire path, evaluated per post.
- **Always `estimated`, and what that never becomes.** Telemetry-reported dollars derive through the same per-row Rate path as every other row and render through the single currency module with `EstimateLabel::Estimated` — v1's only label, so the "always" holds by construction and is pinned by test. AD-8's amendment keeps reconciliation (19.5) the `reconciled` label's only producer, and reconciled figures never overwrite estimated rows; a provider's actuals may one day correct an observed Run's figures as NEW reconciled rows, never as edits.
- **Budgets and depth.** FR-49's table is explicit: at `observed`, "Budgets, `warn` — from its telemetry" are honored and everything that acts fails fast. So telemetry-reported usage counts toward the Run's per-run Token Budgets and Cost Caps (it is the Run's only usage; the estimate label is the honesty mechanism FR-23 already provides), and the only executable Breach Action at that depth is `warn` — `block` requires a wire path (23-1's `action_executable`), `pause`/`stop` require a process, so Policy-inherited ones keep the `depth-fallback` Anomaly. Cumulative ceilings stay inert on instance-less Runs (23-1's rule). Nothing in the intake path stops, pauses, holds or fences anything (NFR-9); the sweeper alone changes status, per 23-2.
- **Pricing.** 23-1's wire-Run rule, unchanged: the Run's Policy flat Rate, else the default Policy's model-keyed table for the point's `gen_ai.request.model` attribute when the client sends one (read for pricing inside the job, never stored — AD-28's "nothing else is stored" governs storage, not the transient read), else an unpriced row plus the `unpriced-model` Anomaly where a Cost Cap is set. No retroactive repricing.
- **Authority, attribution and scent.** The intake surface is exactly the matrix cell 22-1 pinned and 23-2 opened: `hk_ann_` only, its binding fixes the identity namespace, and the `hk_ann_` of binding A can never claim into binding B (T1.10's "a class never acts on another Run", held by construction — the body carries no binding field to override). The security review's actor table trusts an OTLP *collector* "for metrics only" on the outbound side; inbound, the posting client is trusted only as far as its credential: every attribute is untrusted input, validated like hint input (bounded length, visible ASCII, ≤ 16 labels, values through the guard), and a hostile batch can only ever create capped, budgeted, warn-able Runs in its own binding's namespace — attribution, not authentication (§10's line, carried by 23-2's docs page). Scent-Check governs calls at the proxy, not telemetry posts; an observed Run that later routes calls through the proxy with no key is unscented like any binding path (22-3's matrix, unchanged).
- **What is read, what is stored, and §6.** Exactly: the external id, the Caller labels, the token-type sums (and the transient model attribute for pricing). Nothing else — no other metric families, no scope or resource metadata, no exemplars — is read or stored, and `partialSuccess` plus the counted skips are how the batch learns its unused parts were dropped (graceful degradation, never a silent lie). Inbound telemetry is data arriving, not leaving; the §6 default is untouched, and the docs say what the receiver keeps. Exemplars in an inbound batch are ignored (v2 may carry run ids in exemplars; never a token id — T6.3).
- **Bounds and refusal codes.** The receiver rides the Control API listener, so TLS-beyond-loopback and the bind rules come free; it is always on and inert until an Operator issues an `hk_ann_` (23-1's `hekma binding credential issue --class announce`) — the credential is the switch, which keeps one more flag out of the surface. Caps: 4 MiB per body (`413`, parsed nothing), 8 `resourceMetrics` and 64 points per family per batch (excess skipped and counted — a partial batch beats a refused one), the hint validation for ids and labels, 23-2's identity caps (`409`), and the 1 s writer bound (`503`, retryable — a retry is safe because the diff is the idempotence). OTLP clients read `4xx` (except 429) as permanent and stop retrying — correct for malformed, oversized, unauthenticated and capped posts — and `503` as retryable, which is exactly the intent. `partialSuccess` (the opentelemetry-proto `ExportMetricsPartialSuccess` JSON shape) is the OTLP-native way to accept a batch and name what it rejected, so a Collector's delivery pipeline surfaces the skips instead of retrying them forever.
- **Semantic-convention posture.** One shape is accepted: the metric name `gen_ai.client.token_usage` as a cumulative sum with the `gen_ai.token.type` attribute — the name AD-21 pinned for the exporter and AD-28 for the receiver, and the current GenAI semconv. Legacy names (`gen_ai.tokens.*`, `llm.*`) and other families are skipped and counted, never aliased: a Collector's transform processors rename them if a client needs it, which is the same division of labour as the protobuf translation. No semconv "version" is negotiated; the accepted name-and-attribute shape IS the contract, documented as such (a §7-item-4-adjacent behaviour on a §7-item-5-adjacent transport, additive-only in practice).
- **No new event kinds; the exporter untouched.** Run `created`/`changed`, `credential` (never, for this channel), usage events, `StatusChanged`, `anomalies-changed` and breach events cover everything the job produces. The OTLP v1 exporter ignores nothing new (no new event families exist to skip), instance-less telemetry rows are already skipped by its instance-keyed v1 attributes, and no new exported counter appears before `otlp-metrics v2` (24-5, 22-3's precedent).
- **Schema v21; version.** One new table (`telemetry_counters`), additive, one-way, no backfill (a Run's counters begin at its first post). The `metering_source` column is TEXT with no CHECK — the third value is data-only, and an older binary's decode skips it. New public surface: the route and its code table, the `telemetry-reported` ledger value, `Engine::ingest_telemetry`, `TelemetryReport`/`TelemetryOutcome`, the `partialSuccess` body — breaking nothing; hekma-engine **stays 0.12.0** (the cycle rule), announced in the Unreleased banners. No new dependency (axum/serde/hyper are in-tree; the intake adds no client).
- **Threats considered.** Each with its mitigation (review ids where they exist; N-ids are this story's):
  - an uncredentialed or wrong-class poster reaching the intake [T1.10, R1.11] → the matrix cell and the typed 401/403 table, pinned per cell;
  - a stolen `hk_ann_` minting Runs by telemetry [A4's neighbourhood, T1.9] → per-binding, per-parent and per-root caps (23-2's), counted inside the job; telemetry Runs are budgetable and warn-able like any other; revocation of the credential stops the next post (no sleep, 22-1/23-1's snapshot rule);
  - cumulative counters double counting [N1] → the durable diff, one transaction per delta;
  - a client counter reset under- or over-counting [N2] → re-base on a lower value with a bounded diagnostic (over-count bounded by the restarted counter's own value, never negative);
  - proxy plus telemetry for one Run double counting [N3] → the one-truth rule (skip-and-surface, `partialSuccess`);
  - a Run invented for telemetry with no identity [N4] → no external id, no Run: points skipped and counted; the unattributed Run is a wire-only concept;
  - label or cardinality flooding through `hekma.label.*` [T9.5] → hint-grade validation, ≤ 16 labels, through the guard; no client string becomes a series, key or log value;
  - oversized or pathological batches [N5] → the 4 MiB cap, the 8/64 point bounds, malformed-JSON 400, per-minute rate-limited diagnostics;
  - secrets or content smuggled in unused attributes [T6.3, N6] → only the three documented inputs are read; sentinel scans of every surface including `state.db` bytes;
  - an error body echoing the credential or a client string [T6.5] → static bodies, `partialSuccess` messages are fixed strings;
  - the receiver blocking the host [N7] → one bounded writer job per post (1 s), no engine lock on the host side, the route stops with the listener;
  - cross-binding identity squatting [N8] → the credential fixes the namespace; no body field can name another binding;
  - replayed batches after a crash [N9] → the counter commits with its delta; a replay diffs to zero.
  Out of scope, with the seams: hold/release/reroute/reject (23.4), the per-call read surface (19.4), `otlp-metrics v2` and any exported intake counter (24-5), protobuf/gRPC and https collectors (the deferred trigger), CrewAI/LangGraph helpers (23-2's follow-up), bypass detection (22.4 — an observed Run has no process to inspect), a second Metering Source for one Run (the one-truth rule makes it unnecessary).
- **What 23-3 does NOT do.** No protobuf or gRPC intake (a Collector translates; the trigger is a real client that cannot run one); no Run Key or refresh credential on this channel, ever; no depth change from telemetry alone; no change to Policy resolution, Breach Actions, the fence, the sweeper's windows or the proxy; no new OTLP exported metric; no CLI verb; no storage of anything beyond the three documented inputs; no Collector bundling or config generation (a documented recipe only).
- **Deferrals (new entries at build).** The OTLP protobuf/gRPC receiver (trigger: a named client or SDK that cannot post OTLP/HTTP+JSON through a Collector — re-records the spine's 2026-10-30 deferral); per-binding intake enable/disable switches (trigger: an Operator asks — the credential is the switch today); batching of multiple posts per writer job (trigger: a measured writer-load report at Run scale); a `telemetry-received` signal in the exporter (trigger: `otlp-metrics v2`, 24-5).

## Ask First

Each is a public-contract or scope choice; the recommendation is the spec's current text. **O-items are the owner's (Islam's)** — the PRD questions this story exists to answer, every public-contract change (the route, the status codes and bodies, the ledger's source value), and the AD-28 deviation below; the numbered items are the orchestrator's. Until ruled, the build proceeds on the recommended option and the PR stays unmerged past review.

- **O1. Do telemetry-reported tokens count toward budgets and Breach Actions, given they are always `estimated` (PRD question — confirm).** Recommended: **count.** FR-49's verb table honors "Budgets, `warn` — from its telemetry" at `observed`, telemetry is an observed Run's only usage, and FR-23's label is the honesty mechanism (a figure being estimated never barred it from enforcement — every proxied dollar is estimated too). The only executable action at that depth is `warn`; Policy `pause`/`stop`/`block` keep the depth-fallback Anomaly. Alternative: advisory-only (budgets read, never breach) — rejected: it contradicts the FR-49 cell and leaves observed Runs ungovernable. Meanwhile: as written.
- **O2. Double counting — the same Run's usage arriving from the proxy and from OTLP (PRD question — confirm).** Recommended: **one Run, one metering source: a Run with a wire path keeps per-call metering; its telemetry deltas are skipped, counted, and surfaced in `partialSuccess`** (never summed — totals would lie; never recorded-then-excluded — shadow rows are a permanent honesty tax). Alternatives: (a) count both — over-counts real spend and breaks FR-22's totals-truth; (b) let telemetry win — an estimated cumulative counter replacing call-accurate rows is the worse source. Meanwhile: as written.
- **O3. Payload limits and refusal codes (public contract — confirm).** Recommended: 4 MiB body cap (`413`), `400` malformed, `401` unauthenticated/unknown/revoked, `403` wrong class, `409` identity cap, `415` non-JSON encoding with the Collector recipe, `503` + `x-should-retry: true` past the 1 s writer bound, and `200` + `partialSuccess` for skipped points (≤ 8 resourceMetrics, ≤ 64 points per family, hint-grade id/label validation). Alternatives: smaller cap (1 MiB) or refusing whole batches on any bad point — a partial batch beats a refused one for cumulative telemetry. Meanwhile: as written.
- **O4. May an OTLP post create a Run, or only update one that was announced (PRD question — confirm).** Recommended: **create** — AD-28 ("creating or updating an `observed` Run"), FR-51 ("telemetry carrying a run identity creates or updates an `observed` Run") and FR-52's third channel all say so; creation is capped by 23-2's per-binding/per-root caps and leaves no credentials. Alternative: update-only — rejected as contrary to three planning documents and to the epic's premise (framework flows with no Hekma integration). Meanwhile: as written.
- **O5. Which OTLP semantic-convention versions are accepted (public behaviour — confirm).** Recommended: **one shape, undated**: the cumulative sum `gen_ai.client.token_usage` with `gen_ai.token.type` (input/output/cached) — the name AD-21/AD-28 pin. No version negotiation exists in OTLP/HTTP metrics; the accepted shape is the contract. Alternative: an alias table for one or two legacy names — rejected: no FR, and aliases rot invisibly. Meanwhile: as written.
- **O6. Where the third Metering Source value lives (AD-28 deviation — rule).** AD-28 says usage enters "as a third Metering Source value"; the `MeteringSource` enum is public in `hekma-adapter-api` (crates.io, semver-checked), and the Glossary defines the two existing values as *adapter-declared*. Alternative: add the variant to the public enum (a semver event and an exhaustive-match break for every embedder). If Islam prefers the literal spine reading, the variant goes in with the next adapter-api minor and the engine constant becomes it. Meanwhile: the engine-side value.

The receiver is always on (no disable flag).** Recommended: yes — it rides the Control API listener, is inert until an Operator issues an `hk_ann_`, and its failure modes are typed and bounded; a switch adds surface for no exposure reduction.
