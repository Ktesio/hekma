## Intent

**Problem:** A framework or plain client that Hekma did not start can only become a `wire` Run by accident — a hint split or a binding's shared Run — and only on its first call: Hekma learns the Run exists when traffic arrives, cannot tell one client's job from another's beneath the same binding before that, and never learns a discovered Run went away (23-1's wire Runs stay open forever; the cap bounds them instead of the truth). The `hk_ann_` announce credentials 23-1 issues are inert — nothing accepts one, the `Heartbeat` route family has no route, and 22-1's authority matrix refuses a Run Key on it. No Run holds a Lease, `RunStatus::Silent` exists but nothing produces it, and no sweeper exists; the PRD's `[ASSUMPTION]` on Lease length and inactivity windows is undecided, so FR-52's `silent`/`ended` transitions are untestable. The announce channels FR-52 promises — a header on the first proxied call, a Run-scoped Control API endpoint, later OTel — have no wire names, and "one Run per identity across channels" has no mapping that a hint split and a later announcement share.

**Approach:** Announcing claims an identity in the one registry 23-1 already publishes — `run_identities` — under the SAME key a hint split uses beneath the client's binding (`binding:<name>` + external id; `run:<parent id>` + external id beneath a Run Key or Run route), so a Run discovered on the wire and later announced under the same identity stays one Run (FR-49/FR-52). Two channels ship here: an `x-hekma-announce` request header (with `x-hekma-labels` Caller labels) processed at identification — the claim job runs in the writer, awaited with 23-1's 1 s bound, and the response carries `x-hekma-run-key` / `x-hekma-refresh` once, after publish — and `POST /v0/runs/announce` under the binding's `hk_ann_` credential (201 with `credentials` once on create, 200 renew-only on re-announce; the OTel channel is 23-3's, riding these same jobs). A mint happens exactly once per Run creation, on either channel; a re-announce renews and upserts Caller labels through the guard, never re-mints (revocation must stick; recovery is the refresh credential, or close + re-announce). The endpoint's mint is custody-eligible and the header's is not (P4's credentialed-announce distinction). Announced Runs hold a **Lease** (default 60 s, renewed by heartbeat or by any identified proxied call); wire Runs (a binding's Run, splits, hint children, the unattributed Run) hold none and go `silent` after an inactivity window (15 min). A sweeper task beside the reaper in the proxy-owning engine marks `silent`, returns a renewed Run to `active`, ends a Run `silent` past the silent window (60 min, cause `silent-window`, tokens revoked through 22-1's run-ended path, identity released for the next claim), never touches a process-owning Run (its process is its heartbeat), and never stops anything (NFR-9: silence is a status, not an action). Announce claims count in the existing per-binding/per-parent caps plus a new per-root cap (L8). The CrewAI/LangGraph helpers are deferred to a named follow-up with CI lanes against real flows; this story ships the framework-agnostic recipe. Schema v20; hekma-engine stays 0.12.0.

**Acceptance Criteria:**
- Given a first call through the proxy on binding `/openai` carrying `x-hekma-announce: job-7` and `x-hekma-labels: team=a`, then the call is served, one Run exists with identity `binding:openai`/`job-7`, depth `announced` (the announcing call is its wire path), Caller labels `team=a`, a Lease, and the response carries `x-hekma-run-key: hk_run_…` and `x-hekma-refresh: hk_ref_…` exactly once — no later response, read route, `--json` document, event, SSE frame, log or byte-scan of the state directory carries either token (R1.4/R1.15), and both are named by token id everywhere else.
- Given `POST /v0/runs/announce` with binding `openai`'s `hk_ann_` credential and `{external_id: "job-7", labels: {team: a}}`, then the answer is `201` with the Run (depth `observed`, `wire_path` false — it announced without traffic), `lease_expires_at` set, and `credentials {run_key, refresh_credential, token_id}` once; the minted key is custody-eligible, so (with 22-2 built) its presentation in the API-key slot swaps in the binding's custodied key — while the header channel's mint is custody-ineligible: its key in `x-hekma-run-key` identifies the Run and forwards with the client's own credential, and in the API-key slot answers 23-1's `400 hekma_custody_unavailable` (P4's distinction).
- Given any other credential class on `POST /v0/runs/announce` — operator bearer, Run Key, refresh, proxy-access — then `403 forbidden`; given the `hk_ann_` of binding A announcing, then the Run's identity namespace is binding A's, the Run carries A's bound labels (the split rule), and that credential can never announce, heartbeat or close into binding B's namespace (the class × family matrix, pinned cell by cell).
- Given a hint split `job-7` on binding `openai` (a wire Run from an earlier call) and a later announce under the same identity on either channel, then the Run is ONE Run — same id, depth `wire → announced` with one `changed` event, the Lease set, Caller labels upserted through the guard (a differing label set replaces the Caller layer, never the bound labels); given 50 concurrent first announces with the same identity, then exactly one Run and one minted pair exist afterwards (the writer serializes the claims).
- Given a re-announce of an open identity, then `200` (endpoint) or no credential headers (header channel): the Lease is renewed, Caller labels upsert, and NO new Run Key or refresh credential is minted — a revoked key cannot be re-minted by announcing; recovery from a lost pair is the refresh credential (22-1's rotation) or closing the Run and announcing a new one.
- Given an announce beneath a supervised Run's route or beneath a presented Run Key, then the claimed Run is a CHILD (`run:<parent>` + external id): its usage rolls up to the parent, every ancestor's ceilings apply, and the parent's `block` fences it (23-1's ancestor walk, unchanged); given an announce beneath an unlabelled binding or the catch-all, then the claim still creates its own Run in `binding:<name>` (unlike a hint, it mints a credential) and counts toward that binding's 1,000-open-Run cap.
- Given a Run whose Lease expires with no heartbeat and no identified traffic, then the sweeper marks it `silent` — one `StatusChanged` event, `hekma ps` lists it through 21-5's existing filter — and NOTHING else changes: its next call is served, its budgets, labels, dispositions and keys are untouched, and no process is stopped, paused or fenced by silence (NFR-9); given a heartbeat (`POST /v0/runs/{id}/heartbeat`, the Run's key or its binding's `hk_ann_` for a Run that credential created → `204`) or an identified call, then the Run returns to `active` with one `StatusChanged` and the Lease extended.
- Given a Run Key heartbeating a Run outside its subtree, or an `hk_ann_` heartbeating a Run its credential did not create, then `403` (out-of-scope / forbidden); given a heartbeat on an ended Run, then `409 run-ended` naming the re-announce path.
- Given a wire Run (a binding's Run, a split, a hint child, the unattributed Run) with no traffic past the 15-minute inactivity window, then `silent`; given a Run — Lease-holding or wire — `silent` past the 60-minute silent window, then `ended` with cause `silent-window`, its tokens revoked in the same job (the next call presenting its key: `401 hekma_credential_revoked`, no sleep), its identity row kept; given a later call or announce under that identity, then a NEW Run is created and the old one stays ended (23-1's "the unattributed Run never ends before Leases" clause retires here — the unattributed Run now ends by inactivity and is recreated on the next unattributed call).
- Given a live supervised agent idle past every window, then its Run stays `active` — the sweeper never marks a process-owning Run `silent` (its process is its heartbeat); its exit, not the sweeper, ends it, and a `silent` marking can never reach one (pinned by a table test over the sweep predicate).
- Given the Run Key closing its own Run (22-1's close route, now also the creating `hk_ann_` for its Runs), then the Run ends (cause `closed`), the Lease is gone and the tokens are revoked — "a Run that announces its end" is the close verb; a close by an `hk_ann_` for a Run it did not create is `403`.
- Given an announcing first call under Scent-Check `enforce`, then the call is SERVED (announcing obtains an identity — the review's T9.1/R3.7 posture, stated in the docs as attribution-not-authentication), and the Run's subsequent calls presenting its Run Key are scented (22-3's key rule); under `shadow`, the announcing call is served and the Run carries the `unscented` Anomaly until a Policy change clears it (22-3's reserved announce row, filled) — the fence still wins over everything (a fenced announcing call answers 402 with the credentials riding the response).
- Given `hekma run revoke-keys` on an announced Run and a call presenting its key sent immediately after the command returns, then `401 hekma_credential_revoked` (22-1's no-sleep guarantee through 23-1's snapshot); given that revoked key presented together with an announce header claiming the SAME identity, then the `401` wins — failed authentication precedes the announce claim, and the claim on the still-open Run mints nothing.
- Given the per-root cap: a Run Key or announce chain with 1,000 open descendants, then the next open or announce below that root is refused (`409 too-many-children` on the endpoint) or attributed to the parent with the rate-limited diagnostic (header channel) — never a silent extra Run; the Operator and Host are not capped.
- Given only the proxy-owning engine runs the sweeper: a read-only CLI engine never sweeps, a second engine beside the host never sweeps, and after a `kill -9` of the Service Host and restart the sweep resumes from durable state (a Run that went silent before the crash is still silent, one event, no re-issue).
- Given an upgrade from a v19 (or next-numbered) state directory, then `user_version` is 20, existing open Runs carry `last_activity_at` from `updated_at` and no Lease, no Run's status or depth changed at upgrade, and an older binary refuses the directory.
- Given a sentinel Run Key and refresh credential minted by each channel, then after mint → present → heartbeat → close → sweep → restart, the raw bytes of `state.db` (+ `-wal`/`-shm`), the calls store, logs, `control.json`, `serve.log` and every Agent Home contain no sentinel (before and after a checkpoint), and every read surface carries token ids only.
- Given the sweeper at 100,000 open Runs, then its job reads only the two partial indexes (no full scan — pinned by `EXPLAIN` in the store tests), and an announce claim adds no wait beyond 23-1's existing create bound on the hot path.
- Given handoff: fmt, clippy `-D warnings`, the workspace tests, `check_docs.py` (+ `--self-test`), `test_automation.py` pass; changed-line coverage ≥ 95%; the two-pass review (own + one independent adversarial pass briefed with the security review's §7.1/§7.9 and this spec's threat list) done.

## Design Notes

- **What this story owns, and the rulings it builds on.** FR-52 (added 2026-10-30) fixes the three channels, one-Run-per-identity, the Lease consequences and the helpers rule; AD-25 fixes the identity registry (`run_identities`, UNIQUE, inside the writer), stored-not-derived statuses, the sweeper as a task in the data-path owner, and that depth changes keep the id and emit an event; AD-26 fixes that an announce header creates the Run from the request path — awaited with a bound, credentials returned only after publish — and that the response headers returning a Run Key and refresh credential are `proxy-wire v1` surface; AD-20/AD-22 fix the `hk_ann_` class, its authority row and token rules (22-1 built the format; 23-1 the per-binding issuance). The security review is draft for ruling (AI-58): this spec implements its §9 note for 23.2 — the P4 credentialed-announce distinction (endpoint mints custody-eligible, header does not) and the T1.9 breadth bound (the per-root cap) — and builds on P3 (refresh) as 22-1 built it. If Islam rules P4 differently, the `credentialed` flag's wiring follows the ruling; the channels and the Lease machinery do not move.
- **One identity, one Run, across channels.** The registry key IS the unification: an announce claims exactly the namespace a discovery would have used — `binding:<name>` + external id (the hint-split namespace, beneath the binding the call routes through or the `hk_ann_`'s binding) and `run:<parent id>` + external id beneath a Run Key or Run route (the hint-child namespace). A Run discovered as a split, later announced, keeps its id (FR-49 "stays one Run"); an OTel resource attribute (23.3, AD-28) will claim the same `binding:<name>` key through the same job with `credentialed: true` and no key mint — the job's signature is shaped for it now, the receiver is not built here. The one seam left alone: a Host-opened child's optional external id lives in the `host` namespace (21-2), which does not unify with `run:<parent>` beneath the same parent — recorded in deferred-work (changing it touches 21-2's contract for no FR-52 need). Collisions: an OPEN identity re-announced is idempotent (renew + label upsert, no second Run — the UNIQUE constraint is the arbiter, as for concurrent first calls); an ENDED identity is released and re-claimed by a new Run. Any local process can announce any unclaimed identity, and under the same identity claim another client's Run's labels — possession is the binding, attribution is not authentication (§10's line; the docs carry it).
- **Mint exactly once per Run creation.** Both channels mint the Run Key + refresh pair only when the claim CREATES the Run. A re-announce that re-minted would let anyone re-obtain a key for an open identity and would defeat 22-1's on-demand revocation (announce-after-revoke = un-revoke); recovery from a lost pair is the refresh credential (the announcing process holds it), or close + re-announce. FR-52's "each stating what it returns" is read per channel: the header channel returns both in response headers on the first claim; the endpoint in the body on create; OTel never. This is O1's ruling to confirm.
- **Depth and the Lease.** A fresh announce creates at `observed` (it declared itself; no traffic yet — the Glossary's "known from its telemetry or its announcement"); the first identified proxied call flips it to `announced` (wire path true), one `changed` event, id kept (AD-25). A claimed wire Run goes `wire → announced` at claim. The Glossary gives a Lease to Runs that announced (at `observed` or `announced`) "or runs supervised": this story honours the supervised half by NEVER sweeping a process-owning Run — its process is its heartbeat, and pretending a live process went silent would be the exact guarantee-theater AD-25's stored statuses exist to avoid; a supervised Run's Lease column stays NULL (supervision, not the sweeper, owns its aliveness), recorded in the docs. Wire Runs hold no Lease and go `silent` on inactivity — the review rubric's Lease-scope alignment, resolved in the Glossary's direction. Renewal: heartbeat (the new route) or any identified proxied call — including refused-but-recorded ones (a 402-fenced client still trying is alive) — in `commit_proxied_call`'s transaction.
- **The sweeper.** One tokio interval task beside the reaper, spawned for proxy-owning engines only (AD-25: "a sweeper task in the data-path owner"; a read-only CLI engine or a second engine beside the host must not race the host's writer). Each tick submits one writer job: two indexed passes (silent, then ended), each status change one `StatusChanged`/`Ended` event with its outbox row, published before return — statuses are stored, never derived on read, so 21-5's exception-first listing is an index read. `silent` is a status, not an Anomaly and not an action: it never stops, pauses, blocks or fences anything (NFR-9), and a renewed silent Run returns to `active` with one event. `ended` from silence is bookkeeping (the `RunStatus::Ended` contract): tokens revoke (22-1's run-ended path), the identity row stays for audit and is released on the next claim, usage rows and rollups survive. The knobs are host config (`LeaseOptions`), not Policy limits — a Policy is made of limits (FR-60), and windows are operational timing; a Policy-scoped window is a deferred idea with no FR behind it.
- **The header channel on the hot path.** The announce header is resolved inside `identify` (pure, table-tested): it produces the same `Attribution::Ensure`/`Run` shapes a hint does, in the same namespaces, so `forward` needs one new arm — on `Ensure`-with-announce, the job is `announce` (which mints) rather than `ensure_wire_run`, awaited with 23-1's 1 s bound (`503 hekma_run_unavailable` past it, nothing forwarded). The claim happens at identification, BEFORE the disposition check, so a fenced announcing call creates its Run and the 402 response still carries the credential headers (the Run exists and is listed; its calls are refused by its own ceiling — which is the Operator's loud signal, not a reason to hide the identity). An announce is never ignored (unlike a hint beneath the unattributed Run) because it mints a credential; the flood bound is the per-binding cap plus the sweeper, which now ends abandoned claims — 23-1's "these Runs stay open; the cap bounds them meanwhile" retires. External ids and labels reuse the hint validation (≤ 128 visible ASCII, ≤ 16 labels, percent-decoded, `check_caller_labels`).
- **Custody and scent interplay (22-2 and 22-3 are built before this story).** Custody: the endpoint mint is credentialed (an `hk_ann_` was presented), so its keys are `custody_eligible` and 22-2's swap applies on the API-key slot exactly as for a supervised Run's key; the header mint is not, and never unlocks custody under any mode (P4, mode-independent). Scent: a presented valid Run Key is scented (22-3's rule — so a header-announced Run becomes scented the moment it presents its minted key); an announcing call carries no credential, so the RUN counts unscented under `shadow` (22-3's reserved row) while the call itself is SERVED under `enforce`, because announcing is how a caller obtains an identity (T9.1/R3.7: "on loopback any process can announce itself and get one" — the docs must and do say Scent-Check is attribution, not access control). Refusing announces under `enforce` would make the mode self-defeating: no client could ever earn the identity the mode demands.
- **Authority-matrix cells opened.** 22-1 built `(RunKey, Heartbeat) => false` and `(Announce, _) => false` with "Heartbeat has no route until Leases (23.2)". This story opens: `Announce → Announce | Heartbeat | OtlpIntake | RunClose(its own creations)` and `RunKey → Heartbeat (own subtree)`, per AD-20's matrix wording (announce-scoped: "create a Run, set its Caller labels, heartbeat or close only Runs it created"; Run Key: "heartbeat, close … on its own Run and its children"). `created_by_hash` on `runs` is what "Runs it created" is checked against (the `hk_ann_` token's hash, NULL for engine/Operator creations); the job re-validates it inside its transaction (22-1's time-of-check rule). These cells are public contract — O8.
- **Breadth (T1.9, L8).** Announce claims join the existing caps: per binding (1,000 open identities — `open_identities_in`, 23-1), per parent (`open_children`), and the new per-root cap: ≤ 1,000 open descendants per root subtree, counted inside the announce and `open_child_as` jobs (a recursive count bounded by the existing chain walk; the cap that closes L8's "1000^7 from one key" hole). Past a cap: the endpoint refuses `409 too-many-children`; the header channel attributes to the parent/binding Run with the rate-limited diagnostic (attributed, never refused — NFR-9, 23-1's pattern).
- **No schema for statuses, one for columns.** `silent`/`ended` are existing enum values (21-5's listing already matches them); the sweeper only writes them.
