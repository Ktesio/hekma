## Intent

**Problem:** A supervised agent is asked to send its model calls through the Metering Proxy, but nothing checks. An agent that ignores its injected base URL — or that holds *another* credential entirely (a stored login under `HOME`, an inherited variable a pre-custody spawn let through, a second provider key pasted into its config) — calls the provider directly, and today that traffic is invisible: unmetered, unfenced, and indistinguishable in `hekma ps` from a Run that is behaving. The PRD's own docs lines ("the fence is as cooperative as the meter"; "an agent that bypasses the listener bypasses the fence too") state the gap without closing it, and every custody story points here as the backstop. FR-54 names the mechanism — the Shim compares its process tree's TCP connections against the resolved provider-host list — and 24-1 ships that Shim with the process-tree handle but no comparison.

**Approach:** The engine composes one **resolved provider-host list** per data path — the built-in well-known provider hosts (22-2's versioned table), every open process-owning Run's recorded upstream (23-1's `runs.upstream_base_url`), every endpoint binding's upstream, and every origin pinned beside a held key (22-2's `[custody.NAME]` / `runs.custody_origin`) — resolves each host to addresses (engine-side, `getaddrinfo` through tokio, a 60 s TTL cache, keep-last-good on failure), and pushes `{host → addresses}` to every live Shim in the spawn frame and on change (`shim-rpc v1.1`, additive). Each Shim polls its own process tree's **established TCP connections** every 5 seconds through a per-OS enumerator under `backends/` — Linux: the `/proc/<pid>/stat` ppid walk + `/proc/<pid>/fd` socket inodes matched against `/proc/net/tcp{,6}`; macOS: `proc_listallpids` + `PROC_PIDTBSDINFO` ppids + `PROC_PIDFDSOCKETINFO` foreign addresses (libproc, the backend's existing source); Windows: `QueryInformationJobObject(JobObjectProcessList)` (the Job the Shim owns IS the tree) + `GetExtendedTcpTable` rows owned by those pids — compares remote addresses against the pushed set, and reports **by host name, never a bare verdict**: a hit is pushed to the engine, buffered like the buffered exit when no engine is connected, and the engine's writer job records it. A Run **with a wire path** (custody on, or an observed Run's proxy path) gets the `bypass` Anomaly naming the Run and host; a `supervised (no wire)` or custody-off Run gets an **informational note** naming the host and why — reported as what it is, never as a bypass. Every Run carries an explicit detection state — `unreported` (no report yet), `active` (polling on an implemented OS), `unavailable` (no implementation, a runtime enumerator failure, or a pre-Shim direct record) — so no surface ever reads clean without having checked. Detection signals only: no Breach Action, no stop, no pause, no proxy-wire change. The OTLP counter by host is designed (`hekma.bypass.detected`, attribute `host`, the Run via exemplar) and lands with `otlp-metrics v2` (24-5), per the 22-1/22-3/23-1 precedent. Schema v23; hekma-engine stays 0.12.0.

**Acceptance Criteria:**
- Given a Shim-backed supervised Run with a wire path (key custody on) whose process tree holds an established TCP connection to an address of a host on the resolved provider-host list, then within one poll interval (5 s) the Run carries the `bypass` Anomaly, `runs.bypass_hosts` names the host, `hekma ps` and `run show` (human and `--json`) name the Run and the host, exactly one `bypass` event per new host is on the bus, in the outbox and on SSE carrying the host, and the Run is not stopped, paused, blocked or fenced by the detection itself (NFR-9; detection signals only).
- Given the same connection on a `supervised (no wire)` Run, then no Anomaly is raised: the listing carries an informational note naming the host and saying direct calls are expected until key custody is turned on for it, the event carries `informational: true` with reason `no-wire`, and the note persists on the Run row for the retention window.
- Given the same connection on a Run whose custody is off (`custody_state = off`, opted out), then the surface reports the Run as custody-off — an informational note, not a bypass (the security review's §9 rule) — and given that Run's next start with custody on, then a subsequent detection is the `bypass` Anomaly and the informational note is gone.
- Given the per-OS enumerator on each CI leg (Linux, macOS, Windows), then a fixture agent that dials a loopback fake listed through a binding's upstream (`http://127.0.0.1:<port>` — an Operator-configured local gateway is on the provider-host list by construction) is reported within the interval, and a sibling process OUTSIDE the tree dialing the same host is not — the ppid-walk / Job-Object scoping is proven, not assumed; the enumeration returns the tree's established remote addresses only (v4 and v6; non-ESTABLISHED states excluded).
- Given an arm with no implementation (the other-Unix compile arm) and a runtime enumeration failure (a Linux seam with `/proc` unreadable), then the Run's detection state is `unavailable` with a reason, rendered in `ps`, `run show` and `--json`, and no surface reports that Run as checked or clean — the honest per-Run state is `unreported | active | unavailable`, and a Run no report has arrived for yet renders `unreported`, never clean.
- Given the polling loop, then a poll costs ≤ 5 ms at ≤ 64 processes in the tree (the CI-seed gate through `perf-budgets --bypass`, recorded in `docs/testing.md`), the interval (5 s) and the per-OS signal source are named in the docs (the review's T10.4 ask), and a connection held across two consecutive polls is always caught.
- Given the engine-side resolution, then a provider host whose addresses change reaches every live Shim within the TTL (60 s) plus one push, a resolution failure keeps the last good set with one rate-limited diagnostic (never `unavailable`, never a clean claim), a host resolving to many addresses matches on each of them, and when several listed hosts share one address the finding names every such host — the Anomaly is a signal naming hosts, never a verdict (T10.2), and the docs list the shared-CDN limit.
- Given a `kill -9` of the engine with a finding already buffered in the Shim, then on reconnect the report is delivered through `status` and the verdict applies exactly as if the engine had been connected; a Shim that exits with undelivered findings loses them honestly (the Run's state stays at the last delivered report) and that bound is documented beside 24-1's linger bounds.
- Given a pre-v22 direct record still running after the upgrade, then its detection state is `unavailable (no-shim)` with the reason named, and its next launch is Shim-backed and reports; given an `observed`, `wire` or `announced` Run, then no bypass surface exists for it (no process tree to inspect) and none is implied.
- Given the new event family, then the OTLP v1 exporter ignores it (no new counter before `otlp-metrics v2`), and the counter — `hekma.bypass.detected`, attribute `host`, allow-listed labels, the Run via exemplar — is recorded in deferred-work with trigger 24-5 (the 22-1/22-3 precedent; FR-59's gate).
- Given the whole scenario (detection → informational → reconnect → upgrade), then no event, log, diagnostic, listing or `--json` document carries a remote address, a credential, a token or any request content — host names and states only; `check_docs.py`'s vocabulary holds (no planning ids in user-facing text).
- Given an upgrade from a v22 state directory, then `user_version` is 23, both columns default honestly (`unreported`, no hosts), an older binary refuses the dir, and every existing listing, `--json` schema and event schema is additive-only (no field moves, no version bump — the additive-field precedent).
- Given handoff: fmt, clippy `-D warnings`, the workspace tests, `check_docs.py` (+ `--self-test`), `test_automation.py` pass on all three OS legs; the OS-cfg gate holds (all new OS code under `backends/`); changed-line coverage ≥ 95%; the two-pass review (own + one independent adversarial pass briefed on the security review's §7.10 and this spec's Design Notes) done.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-23 (ruled 2026-10-30) fixes the home and the mechanism: the Shim owns "bypass detection for its process tree", "per OS in `backends/`", "comparing the tree's TCP connections against the resolved provider-host list", and "an OS without an implementation reports `unavailable`". FR-54 fixes the signals: the Anomaly naming the Run and host, the informational note for `supervised (no wire)`, signals-only (never stops or pauses), and the never-clean-without-checking bar. The security review (draft for ruling) adds three obligations this spec treats as binding: §7.10's limits list in the docs (T10.1-T10.7), the sampling interval stated (T10.4), and custody-off Runs reported as such, not as bypasses (§9's 22.4 note). 24-1 ships the Shim, the process-tree handle, the push/buffer/adopt shapes and the OS-cfg home this story rides; 22-2 ships the custody states and the built-in provider table; 23-1 ships the upstreams and bindings that make up the configured half of the list. This story adds the comparison and nothing else.
- **Who resolves, who compares (the AD-23 reading).** "The Shim compares" and "the resolved provider-host list" together fix a split: the ENGINE composes and resolves the list (one cache for every Shim; the engine already resolves upstream hosts for the proxy's dials), and the SHIM enumerates its tree's TCP connections per OS and matches addresses. The Shim therefore never does DNS — keeping 24-1's cleared-environment posture pure (no resolver env levers, no new capability) and every Shim's view consistent with the proxy's. The list is configuration, not a secret, so it survives the spawn-env drop. The comparison itself is trivial (an address-set membership test); all the per-OS difficulty is in the enumeration, which is exactly the part AD-23 pins to `backends/`.
- **The list, and why it is global.** A bypass matters most when the agent uses a credential Hekma does not know about — the review's §7.10 framing ("a backstop for one case custody cannot close: an agent with another credential"). So every Shim gets the same list: the built-in well-known provider hosts (22-2's versioned table, the same surface the docs table versions), plus every configured origin in this state directory — open Runs' recorded upstreams, bindings' upstreams, pinned custody origins. An agent calling a provider that is not its own is still caught. The list is bounded (≤ 512 hosts: ~10 built-ins + ≤ 256 bindings + pinned origins + open upstreams), sorted, and versioned only through 22-2's table (a host added there is a docs-versioned change, not a code change).
- **Address matching, DNS and CDNs.** TCP endpoints are addresses; the list is host names; the engine resolves with `getaddrinfo` (tokio's blocking pool — the same resolver the proxy's dials use) and pushes `{host, addrs}`. A TTL cache (60 s) with keep-last-good balances cost against drift; a check-time resolve per Shim per poll would multiply lookups by Shim count for no accuracy gain, and no-cache-at-all would let a slow resolver stall polls. The known imprecision is stated, not hidden: a host behind a shared CDN resolves to an address other services use (false positives — the finding names the host, a signal, not a verdict, per T10.2); a provider address the engine's cache has not seen yet is missed until the TTL refresh (false negatives — bounded by the TTL); an agent that resolves a host to a different address than the engine did (GeoDNS) can slip for one TTL. SNI and the HTTP layer are invisible to a TCP-table enumerator on every one of these OSes — that deeper match would need capture tooling Hekma does not ship, and the docs say the match is by address.
- **The per-OS enumerators, exactly.** Linux: one `/proc` scan builds pid → ppid (field 4 of `/proc/<pid>/stat`, parsed after the last `)` exactly as the existing fingerprint code does), the tree is the transitive children of the Shim's child pid, each tree pid's `/proc/<pid>/fd` symlinks name `socket:[inode]`, and `/proc/net/tcp` + `/proc/net/tcp6` rows (state `01`) whose socket inode is in that set contribute `rem_address`. macOS: `proc_listallpids` + `proc_pidinfo(PROC_PIDTBSDINFO)` for ppids (libproc through `nix::libc` — the documented, stable source the backend already uses for start-times), then `proc_pidfdinfo(fd, PROC_PIDFDSOCKETINFO)` per tree fd for the foreign address (v4/v6). Windows: the Shim owns the Job Object, so `QueryInformationJobObject(JobObjectProcessList)` returns exactly the tree — no walk at all — and `GetExtendedTcpTable` rows in `ESTABLISHED` owned by those pids give the remotes. All three are documented, stable APIs; no new crate (Linux is pure std fs; macOS rides `libc`; Windows adds two `windows-sys` features to the manifest target block, the 24-1 `Win32_Security` pattern). Nothing shells out to `lsof`/`netstat`/`ss` — external tools are not dependencies the repo can promise.
- **Unavailable means three things, all honest.** (a) Compile-time: an OS without an enumerator (the other-Unix arm) — FR-54's own case. (b) Runtime: an enumerator that fails (`/proc` unreadable, a short read, a table call failing) — reported once per state change with the reason, retried on the poll cadence, never silently treated as clean. (c) Topology: a pre-v22 direct record has no Shim to watch it (`no-shim`), and non-supervised depths have no process tree at all (23-3's note) — no surface is drawn for them. The per-Run stored state (`unreported | active | unavailable`) is what makes FR-54's "never reports a Run as clean without having checked" testable: silence plus `active` is checked-and-clean; anything else says why it is not checked.
- **The verdict, and where it lives.** The writer job applies the pure verdict from T1: a wire path (`wire_path: true` — custody on, or an observed Run's proxy path) plus a hit is the `bypass` Anomaly; `supervised (no wire)` and custody-off Runs get the informational note with the reason. The wire/no-wire and custody states already exist (23-1/22-2's columns) — this story only reads them, so turning custody on for a previously no-wire Run upgrades its verdicts with no migration. The Anomaly stays payload-less (the house design — a stored flag list); the host names live in `runs.bypass_hosts` beside it, which is how `ps` names the host without changing the Anomaly type. Set-once per host: a flapping connection never re-joins the event stream; hosts are bounded at 8 per Run with further distinct hosts counted in one diagnostic (the T9.5-style flood discipline). Nothing auto-clears while the Run is open — a detected bypass is a fact about the Run; the Anomaly dies with the Run's row (ended Runs keep their Anomalies for the retention window, the existing `--all` rule).
- **Signals only, and the counter.** Detection never acts: no Breach Action dimension exists for it, none is added, and NFR-9's list is untouched (a Policy cannot name it; `block` still fences only proxied calls). The OTLP counter is FR-54's second signal, but FR-59's gate (allow-listed labels, no run id, exemplars) plus the 22-1 precedent (no new event family gains a v1 counter; 22-3 and 23-1 both deferred theirs to 24-5) make it a 24-5 landing: the name, the `host` attribute and the exemplar design are recorded in deferred-work now so 24-5 picks up a decided shape. Until then the signals are the Anomaly, the event, the informational note and the listing — all of which this story ships.
- **Events, and what never rides them.** One new boxed family (`EngineEvent::Bypass`), committed with its outbox row in the writer job, on the bus and SSE — carrying the run id, the host name, the detection state and the informational flag. Never: remote addresses (a host may resolve to thousands; the name is the stable surface), credentials, tokens, request content. The OTLP v1 exporter ignores it (one arm, the established pattern).
- **Schema and version.** v23 is two additive `runs` columns, no backfill (`unreported`/`''` are the honest defaults for every existing row), one-way (an older binary refuses the dir). New public shapes: `Anomaly::Bypass`, `EngineEvent::Bypass`, the additive `bypass` field on run documents, the `shim-rpc` minor bump. hekma-engine **stays 0.12.0** (the cycle rule), announced in the Unreleased banners. No new dependency on any OS.
- **Threats and limits considered** (review ids where they exist; N-ids are this story's):
  - traffic through an HTTPS proxy, VPN or tunnel shows as a connection to the proxy, not the provider [T10.1] → best-effort by design; docs list it;
  - provider hosts share CDN addresses — false positives and negatives [T10.2] → address-match naming the host, never a verdict; docs list it;
  - QUIC / HTTP/3 over UDP is not a TCP connection [T10.3] → TCP only (the spine's own scope); docs list it;
  - a short-lived connection between polls is missed [T10.4] → the interval is a named constant, stated in the docs and the diagnostics; connections held ≥ two polls are always caught (tested);
  - a process outside the tree makes the call [T10.5] → process-tree scope is the design; docs list it; the scoping itself is pinned by the sibling-is-not-reported test;
  - an OS with no implementation [T10.6] → `unavailable`, never clean — a stored, rendered state;
  - OAuth/subscription agents are not custody-capable [T10.7] → they are the no-wire population: the informational note, per FR-54;
  - the tree walk mis-scoping (a grandchild escaped the group; an adopted pid reused) [N1] → the walk is from the live child pid over ppids (Linux/macOS) or the Job's own list (Windows) each poll — no cached pid set to go stale; pid reuse inside one poll window is bounded by the same start-time discipline the supervisor uses (a mismatched start-time excludes the pid);
  - a hostile agent forking, exiting and reforking to dodge the walk [N2] → best-effort, listed; the signal is not a containment claim;
  - findings flooded at the engine [N3] → set-once per host, ≤ 8 stored, one event per new host, buffered pushes dedup'd in the Shim;
  - a Shim reporting a host not on any list (a protocol confusion) [N4] → the engine re-checks the pushed list before committing the job; an unknown host is counted, not stored;
  - the engine pushing a stale list after a binding/custody change [N5] → the refresh pushes on list change and TTL expiry; the Shim replaces the whole set atomically;
  - detection read as a security claim [N6, NFR-6] → the docs carry §10's signal-not-guarantee wording and the limits list; no surface says "clean", "contained" or "sandboxed".
- **What 22-4 does NOT do.** No OTLP counter before `otlp-metrics v2` (24-5); no Breach Action, fence or any acting surface on a detection (FR-54, NFR-9); no SNI/hostname-level matching, no packet capture, no UDP/QUIC visibility (TCP tables only — the spine's scope); no detection for `observed`/`wire`/`announced` Runs (no process tree — 23-3's note); no migration of pre-v22 direct Runs into Shims (24-1's own impossibility); no per-Run or per-host configuration surface (the list is composed, not configured — a bypass with another credential is the case); no change to the proxy, `proxy-wire v1`, the stop ladder, budgets or the metering path; no new OTLP, CLI-refusal or wire surfaces.
- **Deferrals and the deferred-work trigger naming this story.** 24-1's build adds the "bypass-detection seam → 22.4" entry; this story's build resolves it. New entries: the OTLP counter `hekma.bypass.detected{host}` + exemplar (trigger 24-5); SNI/HTTP-layer matching and UDP visibility (named trigger: a capture story that does not exist — recorded as a limit, not a promise); per-Run detection toggles (no ask exists — do not build one).

## Ask First

Each is a public-contract or product choice; the recommendation is the spec's current text. **O-items are the owner's (Islam's) rulings** (product honesty and scope calls this story makes on his behalf); the numbered items are the orchestrator's. Until ruled, the build proceeds on the recommended option and the PR stays unmerged past review. Items marked **[public contract]** change a public surface and need explicit confirmation.

- **O1. How provider hosts are resolved to addresses, and the CDN posture.** Options: (a) the engine resolves the list with `getaddrinfo`, a 60 s TTL cache, keep-last-good on failure, and pushes `{host, addrs}` to every Shim; a shared-CDN address match names every listed host that resolves to it — a signal, not a verdict — with the limit documented (recommended: one resolution for the whole fleet, consistent with the proxy's dials, no DNS in the cleared-env Shim, and the false-positive cost is a named host on an informational-first surface, not an action); (b) each Shim resolves at check time (fresher, but N Shims × N hosts of lookups inside a hardened process that should not do DNS, and per-Shim drift); (c) no address matching — reverse-DNS of endpoints (racy and wrong on CDNs — rejected). Meanwhile: (a). The CDN/shared-address honesty wording is part of the ruling.
- **O2. The polling interval and its cost budget.** Options: (a) 5 s, a named constant surfaced in the docs and diagnostics, with a measured budget of ≤ 5 ms per poll at ≤ 64 tree processes (≈ 0.04% CPU — far inside NFR-4's 2%) (recommended: SDKs hold keep-alive sessions far longer than 5 s, so sustained use is caught; the miss window is honest and documented per T10.4); (b) 2 s (twice the cost, marginal catch gain); (c) 10 s or higher (cheaper, starts missing real sessions).
