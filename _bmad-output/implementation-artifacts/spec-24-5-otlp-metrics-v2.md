## Intent

**Problem:** `otlp-metrics v1` keys its series by `hekma.run_id`: at a million Runs the exposition is unbounded (v1 papers over it with a 64-runs-per-instance window that silently narrows dashboards), a wire Run or an observed Run exports nothing at all (the AD-21 interim: instance-less usage and breaches are skipped), and an Operator cannot group telemetry by the things they actually steer — Control Depth and the Policy that supplied a limit. FR-59 (AD-21's 2026-10-30 amendment) rules the fix: `hekma.run_id` leaves metric attributes; metrics carry `hekma.control_depth`, `hekma.policy` and only Operator-allow-listed label keys (empty by default) under a per-key cardinality cap with an overflow fold; instance series are bounded; per-Run detail rides exemplars; `https://` collectors move from refused to supported. Traces and spans stay OUT — they are gated by a dated PRD §6 amendment that does not exist yet (FR-59's Gate; PRD §6's 2026-10-30 note; AD-21's amendment; the spine's Deferred list).

**Approach:** Version the change, don't mutate v1. The exporter emits `otlp-metrics v2` (the version marker rides the instrumentation scope, as v1's does) selected by `--otlp-exposition v1|v2` (default `v2`); v1 stays emittable, deprecated, through the §7 window (minimum one minor-version notice, removal only at a major). v2's attributes come from the events themselves per the AD-14 amendment: the engine's run-bearing payloads gain their Run's Control Depth, the Policy names that supplied its limits, and its labels as ADDITIVE optional fields (`UsageUpdate`'s envelope, `BudgetBreachEvent`) — the honest fix for the spine-vs-code drift, because an exporter-side registry join would go blind exactly where v1 already goes blind (Runs alive before the exporter started, restart and lag windows). New on the wire: `hekma.label.<key>` attributes for allow-listed keys (both bound and Caller values, FR-49's "any label dimensions telemetry"), a per-key distinct-value cap (default 200, `--otlp-label-cardinality`, 2..=10_000) folding overflow into one value (`__hekma_overflow__`) that is counted on a `hekma.otlp.folded` self-metric and named in a once-per-flush diagnostic; an instance recency window (256 most-recently-observed instances) replacing v1's run window; exemplars on the token-usage, breach and bypass families carrying ONLY `hekma.run_id` in `filteredAttributes` (never a token id — T6.3/R1.15; no `traceId`/`spanId` until traces ship), at most the 8 most-recent distinct Runs per data point; and the counters other stories promised to this one — `hekma.calls.unscented` (22-3, R3.5-bounded), `hekma.telemetry.received` (23-3), `hekma.bypass.detected` (FR-54 names FR-59; rides 22-4's built surface), plus `hekma.run.anomalies` so the Glossary's "every Anomaly is counted in OTLP" becomes true. `https://` collectors are supported over the host's in-tree rustls stack (webpki-roots vendored set — the 12-3 precedent — plus an optional `--otlp-ca-file` PEM root, the self-signed test seam the deferral names). The whole change — a public, semver'd surface (§7 item 5) — ships under AI-55's two-pass review.

## Design Notes

- **Versioning, precisely.** The version marker is the instrumentation scope's `version` ("v1" → "v2" — it already rides every payload) plus the `--otlp-exposition` switch (default `v2`). v1 is **deprecated and selectable**, per §7's deprecation policy ("announced in release notes, minimum one minor-version notice window, removal only at a major"): the CHANGELOG/RELEASE_NOTES banner announces the deprecation at the minor that ships v2; v1 is removed only at a major. An Operator on v1 dashboards flips nothing until they choose: same flags, same endpoint, add `--otlp-exposition v1` only if they need to hold back. The migration section maps every v1 series to its v2 successor and names what has no successor (`hekma.run_id` grouping → depth + allow-listed labels + exemplars). The reconcile review's F17 ("`hekma.run_id` is marked deprecated in `otlp-metrics v1` for at least one minor release before v2 removes it") is satisfied by the switch: v1 keeps emitting `hekma.run_id` (deprecation noted in docs) while v2 exists, so no removal happens inside the window at all.
- **The AD-14 drift, and why the engine fields are the fix.** The spine's AD-14 amendment says run-bearing events carry Control Depth, Policy names and bound labels "so the OTLP exporter (AD-21 v2) derives every attribute from events" — but the built `UsageUpdate` envelope and `BudgetBreachEvent` carry none of them (only `RunEvent` does; 23-1 made `instance` optional and stopped). An exporter-side registry joined from Run events is the alternative and it is rejected: it goes blind for every Run alive before the exporter started, across restarts and lag resyncs — exactly the windows v1's docs already excuse, which v2 would then re-excuse under a new name. The additive engine fields (Ask First 1) are the spine-faithful route: every usage/breach event self-carries its attributes, no join, no staleness. They are additive optional serde fields — old rows decode unchanged, no schema bump (the 23-1 precedent kept the usage schema at 1 through exactly this kind of addition), and "no new event kinds" (AD-21's v1 rule) still holds.
- **What carries `hekma.policy`.** FR-59: "the name of the Policy that supplied the limit a metric reports on (the default Policy's name when none did; metrics not tied to one limit carry no Policy attribute)". Only `hekma.budget.breaches` reports ON a limit, so only it carries the attribute — the supplying Policy's name, `default` when the default Policy's fallback filled the limit, or the closed value `explicit` for an explicit Run/instance ceiling (Ask First 8: FR-59's letter would stamp `default` on an explicit-limit breach — a misattribution; F17 implies the third case without naming it). Token usage reports observations, anomalies/unscented/telemetry counters report counts — no Policy attribute, stated in the docs so the omission reads as the rule, not a gap.
- **Series arithmetic, stated.** Worst case per family: instances (≤ 256 by the window) × depths (4 — the ladder; `supervised (no wire)` does not split series, documented like `display_with_wire`'s display-only status) × policies (the Operator's own policy set, like instances an Operator-controlled factor — called out in the docs) × the product of per-key caps (≤ 8 keys × cap each, 200 by default). The per-key cap is what makes Caller-supplied values safe (T9.5/R3.5): the Operator allow-lists the KEY, the cap bounds the VALUES, the fold makes the bound visible. The unscented and bypass feeds never take a client string at all.
- **Why run ids may ride exemplars (and nothing else).** The PRD §6 strict reading — "metrics only … never content, never secrets" — does not name identifiers, and the opaque run id already leaves the machine on v1 metric attributes and in FR-51 identity headers; the security review's T6.3 row settles the shape: "Exemplars (v2) carry run ids only; never a token id". So: `filteredAttributes` = exactly `{hekma.run_id}`; no labels (the allow-listed ones are already metric attributes — an exemplar copy would only duplicate them into a sample), no token ids, no trace/span ids until the §6 amendment. Ask First O4 puts the strict/loose call with the owner. The versions review's F-9 caveat is adopted verbatim in the docs: exemplars are a sample, and the complete per-Run record stays the Control API and the outbox.
- **The counters this story owes.** 22-3 deferred its unscented OTLP counter to 24-5 by name; 23-3 deferred a `telemetry-received` signal to 24-5 by name; FR-54 says the bypass counter shows "by provider host and allow-listed labels (the Run via exemplar, FR-59)". All three land here. The feeds are host-side samplings (the proxy and the intake live in the host with the exporter), never per-call events — 22-3's own reasoning (a per-call event family is the flood T9.5 warns against) is the design. `hekma.run.anomalies` closes the Glossary's blanket "counted in OTLP" promise using the Run events that already exist. 23-4's held-call/disposition counters are NOT owed here: its text only excludes them from 23-4; they are recorded as a deferred entry with an Operator-ask trigger.
- **https posture.** The deferral's own sketch is the design: a TLS connector on the host's POST client over the in-tree rustls stack, vendored roots, plus a self-signed-root test seam. The trust set is the webpki-roots vendored Mozilla set (the security review's 12-3 posture — NOT the system store, which rustls does not read by default and which would vary by platform) plus the optional `--otlp-ca-file` PEM root for private collectors; the flag is public surface and rides O5. No verification bypass exists in any build. Certificate validation failures are terminal (not retryable) with a surfaced diagnostic naming the host.
- **What does NOT change.** Resource attributes (`service.name/version/instance.id`), temporality rules, the fixed histogram bounds, the estimate-honesty rule, the restart-reset semantics, the observation window, the bounded-queue/drop-oldest discipline, the shutdown bound, `partialSuccess` handling, and the whole v1 wire shape behind the switch. The otel SDK (AD-21 option (b)), protobuf encoding, per-agent routing, Prometheus scrape, ledger-sourced re-derivation and configurable temporality stay deferred behind their existing triggers.
- **Traces stay out — where that is written.** PRD FR-59's Gate ("trace and span export ships only with a dated §6 privacy amendment"); PRD §6's 2026-10-30 note (naming trace/span export as needing its own amendment before it ships); AD-21's amendment ("Traces and spans ship only with the dated PRD §6 amendment"); the spine's Deferred list ("traces/spans (until the dated PRD §6 amendment — this supersedes the 2026-10-23 entry's trigger)"). Nothing in this story emits a span, a trace id or a span id.
