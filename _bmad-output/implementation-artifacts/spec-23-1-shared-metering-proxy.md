## Intent

**Problem:** Every `engine-observed` instance gets its own loopback listener on its own port, and that listener attributes every call to "whatever Run this instance has now", by socket. A client Hekma did not start has nothing to point its base URL at, so a `wire` Run cannot exist; a child Run receives no calls at all (its usage is test-only); wire Runs read zero usage; `block` lives on a per-instance flag that dies with the listener; with a pinned `--metering-listen` port only one observed instance can run at all; a Run Key minted by 22.1 has no data path that reads it; and nothing writes per-call records, so the Host read surface (19.4) has no source. The Operator also has no surface to say "calls under this path, to this upstream, carry these labels".

**Approach:** One Metering Proxy per engine that owns the data path (`hekma serve`, or an embedder that enables it), on one loopback port that is sticky per state directory, replaces every per-instance listener. Per call, before any upstream dial and reading only the published snapshot (no engine mutex, no SQLite, no file read): refuse a credential in the URL; identify the Run — a presented Run Key (hash lookup, 22.1), else the engine-made **Run route** path a supervised agent's injected base URL carries (`/_hekma/runs/<run id>`), else the longest-matching Operator **endpoint binding** (its Run when it has labels, else the single **unattributed** Run); an `x-hekma-run` hint then names or creates a child (beneath a Run Key or Run route) or a split Run (beneath a binding); choose the upstream (the supervised Run's recorded upstream, or the binding's); apply the Run's disposition — `block` reasons from the snapshot, over its whole ancestor chain, with 19-2's 402 unchanged; strip every `x-hekma-*` header; add the Operator-switchable outbound identity headers; forward; relay the buffered response with the breach header. A call-start record and a closing per-call record travel to the store writer under a bounded permit pool (full → a typed retryable refusal *before* forwarding, never a silent drop); the close job writes the per-call record to the new **calls store**, commits the usage row keyed on (run, call id), evaluates every ancestor's ceilings in the same transaction, publishes the new `block` disposition before anything can read it, and hands process Breach Actions to the Supervisor. `hekma binding` and `/v0/bindings` (Operator bearer only, each change an event) manage bindings, their reroute routes, a custodied-key reference and per-binding announce and proxy-access credentials. `proxy-wire v1` is documented in full. Schema v18; hekma-engine stays 0.12.0.

**Acceptance Criteria:**
- Given `hekma serve` with no `--metering-listen`, when it starts for the first time on a state directory, then one proxy listens on `127.0.0.1` at an OS-picked port, the port is recorded, `control.json`, the started notice and `GET /v0/proxy` name the URL, and a restart re-binds the same port; given `--metering-listen 8400`, then the proxy binds 8400 and records it; given the recorded port taken, then the host starts, says which port and why, and refuses an `engine-observed` start naming the proxy; no code path binds a non-loopback address.
- Given two `engine-observed` instances started on one host (with or without a pinned port), then both run, each agent's environment carries `OPENAI_BASE_URL=<proxy url>/_hekma/runs/<its run id>` and no per-instance listener exists; each agent's calls are attributed to its own Run, forwarded to its own instance's upstream, and its usage reaches its own ledger rows, rollups and budgets.
- Given a call with a valid Run Key in `x-hekma-run-key` and the client's own provider key in `authorization`, on a binding path, then the call is attributed to the key's Run (the binding's labels do not apply), forwarded with the client's key, and the upstream fake sees no `x-hekma-*` header and no `hk_` token in any header; given a Run Key in the API-key slot (`authorization: Bearer hk_run_…` or `x-api-key`), then the answer is `400 hekma_custody_unavailable`, nothing is forwarded, and the body echoes nothing.
- Given an unknown Run Key, then `401 hekma_unknown_credential`; given a revoked one, `401 hekma_credential_revoked`; given `hekma run revoke-keys` on a Run and a call presenting its key sent immediately after the command returns — no sleep — then that call is refused, while a call already forwarded before the revocation completes and is recorded; error bodies carry no sentinel token; given a token in the path or query (raw or percent-encoded), then `400 hekma_credential_in_url` and the upstream fake receives nothing.
- Given a Run Key whose Run is not the Run route's Run or one of its descendants, on that Run route, then `403 hekma_run_out_of_scope` and nothing is forwarded; given a child's Run Key on its parent's Run route, then the call is attributed to the child.
- Given a binding `/openai` with labels `team=core` and no Run Key on the call, then the call goes to the binding's Run (created on the first call, depth `wire`, bound labels with origin `binding`), its upstream is the binding's upstream with the prefix stripped, and the binding's Policies resolve on that Run; given an unlabelled binding, then the call goes to the single unattributed Run; given a path matching no binding and no Run route, then `404 hekma_no_route`, not forwarded; `CONNECT`, an absolute-form target naming another authority, and any built outbound URI whose scheme, host or port differs from the upstream's are `400 hekma_bad_target`, not forwarded; an upstream `307` is relayed, never followed.
- Given 50 concurrent first calls on a new binding, then exactly one binding Run exists afterwards and every call is attributed to it; given the writer not taking the create within 1 s (a test barrier), then each waiting call gets `503 hekma_run_unavailable` with `x-should-retry: true` and `retry-after`, and nothing is forwarded.
- Given `x-hekma-run: job-7` beneath a supervised agent's Run route, then the call is attributed to a child Run of that Run (depth `wire`, the hosting instance, Caller labels from `x-hekma-labels`, identity `run:<parent>`/`job-7`), a second call with the same hint reaches the same child, the child's usage rolls up to the parent, the parent's and the child's ceilings both apply, and a call without the hint stays on the parent; beneath a labelled binding, the same hint creates a split Run carrying the binding's bound labels; beneath the unattributed Run, the hint is ignored and counted; with 1,000 open Runs beneath one parent or binding, a call with a new hint stays on the parent and a rate-limited diagnostic says so — never a refusal.
- Given a supervised Run whose cumulative `block` ceiling is crossed by a proxied call, then the call that crossed it is relayed, the breach commits with its latch, the snapshot carries the `block` reason before the writer acks the batch, and the next call on that Run, on any of its child Runs, and on any Run route or Run Key resolving beneath it gets 19-2's 402 body byte for byte, without being forwarded; `GET`/`HEAD`/`OPTIONS` still pass; a child's own `block` ceiling fences the child and its descendants only; raising the ceiling through `hekma budget` lifts the reason per reason on the live Run.
- Given a `wire` Run (no instance) with a Policy `block` ceiling, then its proxied usage commits and breaches like a supervised Run's and the fence applies, with no `depth-fallback` Anomaly for `block`; given a Policy `pause` on that Run, then it acts as `warn` with the `depth-fallback` Anomaly; given a Policy cumulative ceiling on an instance-less Run, then `budget show` reports it not applicable and nothing fires on it.
- Given a host restart (engine reopen) with a `block` latch on an open Run, then the reason is in the first snapshot the proxy reads — before it accepts a connection — whether or not the configured action changed since.
- Given a proxied completion with usage, then exactly one usage row exists for (run, call id), exactly one `calls` record with the call id, run id, token id when presented, Control Depth, binding, disposition `pass`, outcome `completed`, status and status class, model, tokens, sub-second start and end, and latency, and no request or response byte in either; given the close job failing then succeeding (a test seam), then still exactly one row and one record; given the store failing for every attempt, then the record is retried, never forwarded twice, and after the bounded attempts skipped with a diagnostic naming the call id and run id; given a 402-refused call, then a record with disposition `block`, outcome `refused`, no usage row.
- Given the permit pool exhausted (a test seam holding the writer), then a new call waits at most 1 s and gets `503 hekma_ledger_unavailable`, the upstream fake receives nothing, and a call already holding a permit still writes its close record.
- Given a `kill -9` of the Service Host with calls in flight, then on the next start every `open_calls` row the dead process owned is closed — `recovered` when the ledger holds its usage row, else `crash` with unknown tokens — rows owned by a live process are left alone, and no usage row is duplicated.
- Given a client that disconnects while its call is upstream, then the upstream request is cancelled, a record with outcome `client-disconnect` and unknown tokens is written, and no usage row is invented.
- Given a streaming chat completion, then the request carries `stream_options.include_usage` unless the client set `stream_options`, the buffered SSE response is relayed whole, and its terminal usage frame is metered; the docs state that time to first token equals the full response time through the proxy.
- Given a Run with a current breach under `warn`, then every relayed response for it (and for Runs beneath it) carries `x-hekma-breach` naming the latched codes; given identity headers on (the default), then the upstream fake sees `x-hekma-run-id` and `x-hekma-labels` and never a token, token id or content; with `--no-identity-headers`, neither.
- Given `hekma binding create openai --prefix /openai --upstream https://api.openai.com/v1 --label team=core`, then the binding exists, one `binding` event is in the outbox and on SSE, `show` prints `http://127.0.0.1:<port>/openai` as the client base URL, and the same works through `POST /v0/bindings`; a prefix under `/_hekma`, a duplicate or overlapping-equal prefix, an upstream with userinfo, a query or a non-http(s) scheme, and a custodied key that is not a `secret:` reference are refused naming the field; a non-Operator credential on any binding route is `403 forbidden`.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-26 (ruled 2026-10-30) fixes one proxy per data-path owner, the identification order, the wire contract as a versioned public surface, per-call records through a bounded channel that never drops silently, request-time attribution with call-id dedup, Run creation awaited with a bound, and buffered streaming. D3 (ruled by Islam) puts `hekma binding` — bindings, routes and per-binding credentials — here. The security review is draft for ruling (AI-58): this spec lands the proxy halves 22.1 deferred (R1.6, R1.8, R1.12) plus R2.5's strip, R2.6's URI check and R2.10 as the review's 23.1 note asks, and builds on P4 (custody eligibility, recorded by 22.1, never granted to a path-attributed call), P5 (trivially true: the proxy is loopback-only) and P6-A (the `hk_pxy_` format). Custody itself, the Host/Origin guard, Scent-Check behaviour, announce, Leases, hold/reroute/reject and beyond-loopback serving stay with 22.2, 22.3, 23.2, 23.4 and 22.5.
- **Where the proxy runs and how clients find it.** The proxy is an engine part (AD-20: the engine owns the Metering Proxy listener) started from `EngineOptions`. `hekma serve` always enables it with a **sticky** port: `--metering-listen <port>` if given, else the port recorded for this state directory, else an OS pick that is then recorded (a v18 `proxy_state` row). A fixed global default would make two state directories on one machine fight for one port, and an ephemeral port per start would strand every adopted agent, as today's unpinned listeners do; sticky-per-state-dir gives external clients a stable address and adopted agents a live `base_url` across restarts. The URL is in `control.json`, the started notice, `GET /v0/proxy` and `hekma binding show`. A taken port never hops (AI-18): the host serves on, says which port, and refuses `engine-observed` starts until the Operator frees it or passes another; adopted agents on the old port are named in the diagnostic. Embedders get the proxy by default on an ephemeral, unrecorded port; a read-only engine never runs one.
- **Bind and auth posture.** `127.0.0.1` only (IPv6 `::1` stays deferred, as today); a resolved non-loopback address is a start error, and there is no flag to widen it — beyond loopback is 22.5 (TLS plus a credential). On loopback the proxy requires no credential (Scent-Check is `off` until 22.3); a Run Key is an identity, not a gate. The loopback proxy authenticates its callers, not itself: another OS user can bind the port while no host holds it (B9, T5.2) — the Stated limit, documented, with the socket-activation recommendation left to 22.5.
- **Identification, per call, in this order** (all from one snapshot `Arc` taken at the request head; `identify.rs` is pure and table-tested):
  1. **Credential in the URL** (R1.12): an `hk_run_`/`hk_ref_`/`hk_ann_`/`hk_pxy_` token in the path or query, raw or percent-decoded → `400 hekma_credential_in_url`, not forwarded. (22.1 also revokes an exposed token on the Control API; on the proxy the request may have come from anyone on loopback, so revoking would let any local process kill any Run's key — refuse only.)
  2. **A presented Run Key** in `x-hekma-run-key`, or an `hk_` token in `authorization: Bearer` / `x-api-key`: shape-check, hash, look up in the snapshot's key index (22.1; R1.8). Unknown → `401 hekma_unknown_credential`; revoked → `401 hekma_credential_revoked`, answered from a bounded **recently-revoked set** the snapshot carries beside 22.1's active-key index (hashes revoked in the last 24 h, at most 100,000, oldest evicted, loaded at open from `tokens.revoked_at`), so a client is told to stop rather than to fix its key; an older revoked key answers "unknown"; a refresh or announce token → `401 hekma_unknown_credential`. A Run Key in the **API-key slot** identifies the Run but there is no custodied key to swap in before 22.2, and forwarding it would leak it upstream (T3.6), so the call gets `400 hekma_custody_unavailable` ("send your provider key in Authorization and the Run Key in x-hekma-run-key"). 22.2 turns this case into custody.
  3. **The Run route** `/_hekma/runs/<run id>/…`: the engine-made binding of a supervised Run (and its legacy root route, see Migration). It names the Run and its upstream; the prefix is stripped. A path naming no open Run → `404 hekma_no_route`.
  4. **An endpoint binding**: the longest prefix that matches on a segment boundary (`/openai` matches `/openai/v1/x`, never `/openai2`); a `/` binding is the catch-all.
  5. Nothing matched → `404 hekma_no_route`.
  The **Run** is then: the Run Key's Run if one was presented — and when the path is a Run route, the key's Run must be the route's Run or beneath it, else `403 hekma_run_out_of_scope` (this is how an in-process helper's own child Run Key is attributed to the child on its parent's base URL); else the Run route's Run; else the binding's Run if the binding has labels; else the unattributed Run. The **upstream** is always the route's or binding's: a Run Key never chooses where a call goes. Under `off` every call that has an upstream is served and attributed; the "unidentified" case is the unattributed Run, listed, metered and budgetable like any other (FR-51), and refusal of unidentified traffic is `enforce` (22.3).
- **Hints (`x-hekma-run`, `x-hekma-labels`).** A hint is never an identity on its own (AD-26). Beneath a Run Key or a Run route it names a **child** of that Run, keyed `run:<parent id>` + external id in `run_identities` (FR-43: "a hint beneath the parent's identity"); the child is depth `wire`, carries the parent's hosting instance (usage rows carry it, AD-25), no bound labels (the 21-2 rule), and Caller labels from `x-hekma-labels` through `check_caller_labels`. Beneath a labelled binding it **splits**: a top-level Run keyed `binding:<name>` + external id carrying the binding's bound labels, so per-run Policies apply to each split Run rather than capping their sum (FR-51 "until a per-run identity splits it"). Beneath the unattributed Run it is ignored and counted: anyone on loopback could otherwise mint Runs without any Operator setup. A hint's labels apply when it creates the Run; later differing labels are ignored (Caller label updates come with announce, 23.2). Breadth: 1,000 open Runs per parent or per binding (22.1's `MAX_CALLER_OPEN_CHILDREN`); past it the call stays on the parent with a rate-limited diagnostic — attributed, never refused (NFR-9). Without Leases (23.2) these Runs stay open; the cap bounds them meanwhile. External ids: ≤ 128 visible ASCII characters; at most 16 labels per hint, each validated like any label.
- **Run creation on the request path.** A first call for a new identity sends `ensure_wire_run` to the writer and awaits its commit and publish for at most the writer's 1 s ack bound — the only hot-path wait on the writer (AD-26). The job inserts the Run, its labels and its `run_identities` row (UNIQUE, so concurrent first calls converge on one Run), resolves Policies, emits `created`, and publishes. Concurrent first calls for the same identity in one proxy share one pending creation. Past the bound: `503 hekma_run_unavailable`, retryable, not forwarded. The unattributed Run is created on the first unattributed call and never ends in this story; a binding's Run is created on its first call and ends with the binding.
- **The disposition and `block`.** The snapshot entry carries the Run's `block` reasons, rebuilt from durable `run_latches` rows with action `block` at open and republished by every job that changes a latch, before its caller is acked (AD-25: one publisher; AD-7: the pipeline alone triggers it). A call is refused if its Run **or any ancestor** (≤ 8 levels) holds a reason — an ancestor's breach applies over the Runs beneath (AD-25), which is also exactly today's per-instance fence for a supervised Run's in-process children. The refusal is 19-2's 402 body, headers and reason order, unchanged; GET/HEAD/OPTIONS stay exempt. A reason clears only when a raise or reset re-arms its latch (21-3/21-6's `re_arm`), per reason — AD-25's rule. That retires today's adoption-time filter ("rebuild only if the configured action is still `block`"): a latched `block` now holds across a restart even if the action changed meanwhile, which is what a live Run already did; recorded in the I/O matrix. `action_executable(Block)` becomes "any depth with a wire path", so `block` works for `wire` and `announced` Runs from this story; `pause` and `stop` below `supervised` keep the `warn` + `depth-fallback` behaviour until wire hold and reject (23.4).
- **Metering a call exactly once.** At admission the call takes a **permit** from a pool of 4,096 (one permit covers its start and close records); none free within 1 s → `503 hekma_ledger_unavailable`, before any upstream dial, so nothing is ever spent that cannot be recorded. The proxy mints a call id (`call_` + ULID) and submits the call-start record unacked (`open_calls`). After the upstream answers and the body is buffered, usage is parsed (the existing OpenAI/Anthropic JSON and SSE seams) and the model taken from the response (else the request), capped at 128 visible ASCII characters. The close is submitted unacked and the response relayed at once (AD-26/27: proxy records are an unacked stream bounded by the 250 ms batch window). The close job, in one writer SAVEPOINT: the `calls` record, the `open_calls` delete, the usage row keyed (run id, call id) — the v12 `idx_usage_events_call` index makes a replay a `DuplicateReplay` — both rollups, the outbox row, and `evaluate` over the ancestor chain. A failed job is re-queued with the same call id and record (idempotent); `Busy` never counts as an attempt; after 10 consecutive failures of one record it is skipped with a diagnostic naming the call id and run id and counted (the 12-4 loud-skip rule), and its permit is released. A client retry is a new call with a new id, and is billed again because the provider billed it again.
- **Crash, restart and disconnect.** Calls in flight when the host dies fail at the client as connection errors (retryable). The calls store is attached to the writer's connection, so one batch commits state.db and the calls store together, but WAL makes the commit atomic per file, not across files: on the next open the proxy-owning engine closes every `open_calls` row whose owner process (pid + start-time fingerprint, the spawn-record pattern) is dead — `recovered` when state.db holds a usage row for its call id, else `crash` with unknown tokens. Rows of a live owner are untouched, so a second engine opening the state dir never closes the host's calls. Usage of a call relayed in the last batch window before a `kill -9` can be lost: an under-count bounded by AD-27's flush bound, visible as a `crash` record, never a double count. A client disconnect drops the call's future: the upstream request is cancelled (the client asked to stop; a streaming provider stops generating), and a drop guard submits the close with outcome `client-disconnect` and unknown tokens — the provider may still bill a partial generation Hekma cannot see, and the docs say so. Graceful host shutdown stops accepting, lets in-flight calls finish within the host's existing grace, aborts the rest (`shutdown`) and flushes the record pump before the writer closes.
- **Enforcement inputs and process actions.** The close job takes the evaluator's inputs from the snapshot (D2: "from state the writer owns"): the Run's stored resolution for its own level and its process-owning ancestor's for the process level, exactly what `re_resolve_matched` already uses. That makes the stored resolution the live enforcement read for proxied usage, so AC-B ("a budget changed while running applies on the very next event") requires every write that changes a resolver input — config writes of `budget.*`, `cost.*`, `model`, labels; Policy changes; `hekma budget` — to re-resolve the affected open Runs in the same job. 21-3 and 21-6 do this for Policies, labels and budgets; the build verifies the config-write path and adds it where missing, pinned by a test that lowers `budget.tokens.per_run` and sees the very next proxied call breach. Process Breach Actions cannot run on the proxy's task: the job's post-commit hook pushes the committed `Evaluation` into a lock-free Supervisor inbox, and the reaper tick (≤ 250 ms) mirrors breaches, publishes events in commit order and executes `pause`/`stop` under its locks, exactly as `apply_evaluation` does now. `block` needs no Supervisor: it is in the snapshot before the batch acks. Overshoot: calls made between a crossing call's relay and its batch commit (≤ the batch window) pass — the same bound as today's reaper-drained fence.
- **Pricing wire Runs.** A supervised Run keeps its instance-configured model and Rate. A Run with no configured model (wire Runs, their splits and hint children) prices each row at its Policy's flat Rate if one resolves, else at the default Policy's model-keyed Rate table entry for the call's reported model, read inside the close job; neither → an unpriced row and the `unpriced-model` Anomaly where a Cost Cap is set (21-3's rule). No retroactive repricing. Cumulative ceilings bind an Agent Instance, which an instance-less Run lacks: a Policy cumulative ceiling matching one is reported "not applicable" by `budget show` and never fires; only its per-run ceilings and its ancestors' apply.
- **Streaming, back-pressure and timeouts.** Responses stay buffered whole (AD-26; incremental relay deferred with its trigger), so through the proxy time to first token equals the full response time — documented. Caps: 64 MiB per body (today's), 512 concurrent calls and a 512 MiB buffered-byte budget per proxy (a same-user process can already do anything; the budget is for other OS users who can reach loopback, B9) → `503 hekma_proxy_busy`, retryable, `retry-after: 1`; an oversized request body → `413 hekma_body_too_large`. Timeouts: 30 s to read request headers (slowloris), 10 s to connect upstream, no total bound on a call — a long completion is legitimate and the client's own timeout ends it. An upstream connect failure, TLS failure, oversized response or reset → `502 hekma_upstream_error` (typed JSON replaces today's static text; SDKs retry 502 as before).
- **The outbound request (R2.5, R2.6's URI check, R2.10).** Every request header named `x-hekma-*` is removed, hop-by-hop headers as today; an `hk_` value can never reach upstream (case 2 refuses it before this). The outbound URI is `<upstream base> + <path after the prefix> + <query>`, and the proxy checks that its scheme, host and port equal the upstream's after canonicalisation (lowercased host, no trailing dot, effective port) before dialling — the `https://api.example.com@evil/` class of tricks cannot redirect a call. `CONNECT` and absolute-form targets naming another authority are refused; redirects are relayed, never followed (made a tested rule, T3.4). Presented credential header values are marked sensitive; nothing formats a request or header map with `Debug`. Identity headers (`x-hekma-run-id`, `x-hekma-labels`: the Run's bound and Caller labels, percent-encoded `k=v` items, sorted, comma-separated) are added unless the Operator turned them off; never a token, a token id or content (R5.10). The response gets `x-hekma-breach: <code>[, <code>]` when the Run or an ancestor holds a latched breach of any action (PRD FR-21: "a response header where the call passes through the Metering Proxy").
- **`proxy-wire v1`, complete for this release** (documented in `docs/metering-proxy.md`, additive from 19-2's slice): request headers `x-hekma-run-key`, `x-hekma-run`, `x-hekma-labels`; the strip rule (every `x-hekma-*` request header); outbound `x-hekma-run-id`, `x-hekma-labels`; response `x-hekma-breach`; every refusal is `{"type":"error","error":{"type":"hekma_…","code":"…","message":"…","param":null,"proxy_wire":"v1"}}` with `content-type: application/json` and `x-should-retry`. The table: 402 `hekma_budget_block` (unchanged, `false`); 400 `hekma_credential_in_url`, `hekma_custody_unavailable`, `hekma_bad_target` (`false`); 401 `hekma_unknown_credential`, `hekma_credential_revoked` (`false`); 403 `hekma_run_out_of_scope` (`false`); 404 `hekma_no_route` (`false`); 413 `hekma_body_too_large` (`false`); 503 `hekma_proxy_busy`, `hekma_ledger_unavailable`, `hekma_run_unavailable` (`true`, `retry-after: 1`); 502 `hekma_upstream_error` (SDK default retry). No body carries a limit, a total, an instance name, a token, a token id or any request or response content. The response headers that return a Run Key on announce are 23.2's addition.
- **Per-call records and the calls store.** `<state-dir>/calls/` holds SQLite segment files; this story creates the first (`calls/<UTC date of creation>.db`, `user_version` 1) and writes only it — rotation, retention and drop-whole are 24.4's on the same naming. Tables: `calls (call_id TEXT PRIMARY KEY, run_id TEXT NOT NULL, token_id TEXT, control_depth TEXT NOT NULL, binding TEXT, disposition TEXT NOT NULL, hold_end TEXT, outcome TEXT NOT NULL, status INTEGER, status_class TEXT NOT NULL, model TEXT, input_tokens INTEGER, output_tokens INTEGER, cached_tokens INTEGER, started_at TEXT NOT NULL, ended_at TEXT NOT NULL, latency_us INTEGER NOT NULL, upstream_us INTEGER)` with `idx_calls_run (run_id, started_at)`; `open_calls (call_id TEXT PRIMARY KEY, run_id, token_id, control_depth, binding, started_at, owner_pid, owner_start_time)`. `disposition ∈ {pass, block}` (23.4 adds hold/reroute/reject and fills `hold_end`); `outcome ∈ {completed, refused, upstream-error, client-disconnect, shutdown, crash, recovered}`; `status_class ∈ {2xx, 3xx, 4xx, 5xx, refused, transport-error}`; tokens NULL = unknown. Every call identified to a Run gets a record, refusals included; a call refused before identification (URL token, unknown credential, no route, bad target, busy) is counted by reason and noted at most once a minute, never recorded against a Run. Token id is a label, never a key (P12). No read surface ships here: 19.4 is the Host read surface.
- **Endpoint bindings.** A binding is {name (the instance-name charset), path prefix (`/` plus segments of `[A-Za-z0-9._~-]`, no `..`, ≤ 128 chars, never under `/_hekma`, unique), upstream base URL (`http` or `https`, no userinfo, query or fragment — `http` stays allowed for a local gateway; custody will require `https`), bound labels, optional custodied key (a `secret:NAME` reference, stored as the reference only; inert until custody, and `create`/`show` say so), routes, credentials}. At most 256 bindings and 16 routes each, so the hot-path match stays a short scan. A route is {name, upstream base URL, optional custodied key reference}: stored and validated now, used by reroute (23.4). Changing a binding's prefix or upstream keeps its Runs; changing its labels re-resolves them (AD-25); deleting it ends its Run and its splits (`binding-removed`). Every change is one `binding` event (`created`, `changed`, `deleted`, `route-added`, `route-removed`, `credential-issued`, `credential-revoked`), committed with its outbox row; Operator bearer only (AD-20).
- **Per-binding credentials (D3, P6-A).** One active credential per class per binding: `hk_ann_` (announce-scoped) and `hk_pxy_` (proxy-access), minted by 22.1's credential module (256 bits, Crockford base32, `SecretString`, shown once, SHA-256 at rest, 12-hex token id). Issue rotates (revokes the previous one in the same job); revoke is per class; listing returns token ids, classes and states. They live in `binding_credentials`, not 22.1's `tokens` (whose rows are Run-scoped). Nothing accepts either credential in this release — announce (23.2), OTLP intake (23.3) and the proxy beyond loopback (22.5) do — and the docs and the issue output say so.
- **Schema v18** (one `BEGIN IMMEDIATE` step after 22.1's v17; if another step lands first, take the next number): `run_bindings (name TEXT PRIMARY KEY, path_prefix TEXT NOT NULL UNIQUE, upstream_base_url TEXT NOT NULL, custodied_key TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL)`; `binding_labels (binding TEXT NOT NULL REFERENCES run_bindings(name) ON DELETE CASCADE, key TEXT NOT NULL, value TEXT NOT NULL, PRIMARY KEY (binding, key))`; `binding_routes (binding … ON DELETE CASCADE, route TEXT NOT NULL, upstream_base_url TEXT NOT NULL, custodied_key TEXT, created_at TEXT NOT NULL, PRIMARY KEY (binding, route))`; `binding_credentials (token_hash BLOB PRIMARY KEY CHECK (length(token_hash) = 32), token_id TEXT NOT NULL, binding … ON DELETE CASCADE, class TEXT NOT NULL CHECK (class IN ('announce','proxy-access')), state TEXT NOT NULL CHECK (state IN ('active','revoked')), issued_at TEXT NOT NULL, revoked_at TEXT, revoke_cause TEXT)` with `UNIQUE (binding, class) WHERE state = 'active'`; `runs.upstream_base_url TEXT`; `usage_rollup_run` rebuilt keyed by `run_id` alone with `instance_id` nullable (one row per Run already — 21-2's subtree totals are per Run — so the copy is 1:1); `proxy_state (id INTEGER PRIMARY KEY CHECK (id = 1), port INTEGER)`. No backfill beyond the copy; one-way.
- **Usage rows and events.** An instance-less usage row must carry a call id (the store refuses it otherwise), which closes 21-1's NULL-distinct dedup hole. `UsageEvent.instance` becomes optional — omitted for a Run with no Agent Instance — and gains `call_id` (omitted for self-reported rows); the usage event's `schema_version` stays 1 (additive for every row that existed before). The OTLP v1 exporter skips instance-less usage (AD-21's interim: no run id or label on a metric before v2). Metering Source stays `engine-observed` for every proxied row.
- **Launch generation at adoption.** The adoption-time bump existed so engine-minted observed sequences restarting at a new attach never collided. Observed usage now keys on call ids, so the bump only causes 21-1's recorded overcount (an agent re-emitting a self-reported line after an adoption). Adoption therefore stops bumping; spawn and Restart Policy relaunch still bump. 22.1's per-launch Run Keys key on the launch generation and promise "adoption changes no credential" — consistent with this; if 22.1's build relied on the adoption bump, ride its code and note it.
- **Migration from the per-instance listener.** Manifests keep `[config."metering.base_url"] env = "OPENAI_BASE_URL"`; the injected value changes from `http://127.0.0.1:<port>` to `<proxy url>/_hekma/runs/<run id>`, and the upstream still comes from `metering.upstream_base_url`. An agent that appends its paths to its base URL works unchanged; one that builds URLs from the base URL's origin and drops its path would miss the route — it gets `404 hekma_no_route` loudly, never misattribution; the docs and the conformance fake agent pin the concatenating behaviour. `--metering-listen` keeps its flag and now names the shared proxy's port. Agents running across the upgrade: with an unpinned old host their listeners died with it, as today (restart them); with a pinned port only one `engine-observed` agent could have been listening on it, so when exactly one adopted pre-v18 `engine-observed` Run exists, the proxy gives it a **legacy root route** (calls with no matching binding or Run route go to it, with its instance's upstream) until it ends, `hekma ps` notes it, and creating a `/` binding meanwhile is refused naming it; more than one → none, with a diagnostic naming them. The `block` docs move from "the metering listener" to the proxy; the fence works at every wire depth; `--detach` of an `engine-observed` agent no longer strands its base URL under a Service Host.
- **Cross-process freshness.** One data-path owner (21-4) means `hekma run revoke-keys`, bindings and Policy changes commit through the host's writer and reach its snapshot before they are acknowledged — R1.6's no-sleep guarantee. A second read-write engine on the same state dir (an embedder beside the host) commits through its own writer; the proxy-owning engine notices foreign commits through `PRAGMA data_version`, checked on the reaper tick, never on the hot path, and reloads changed keys, latches, Runs and bindings, so a foreign revocation applies within 1 s. Recorded as the bound for that topology (22.1's cross-engine deferral, half here, the O(changed entries) half 24.4).
- **Performance (NFR-4: the proxy adds ≤ 10 ms p99).** The hot path is one `Arc` clone of the snapshot, at most one SHA-256 (only when a token is presented), map lookups, a ≤ 8-level ancestor walk, a short prefix scan, a non-blocking permit take and an unacked channel send; nothing waits on the writer except Run creation. `perf-budgets --proxy` drives 64 concurrent clients × 10,000 non-streaming calls through the proxy at a loopback upstream fake returning a 1 KiB completion with usage, against the same fake called directly, with 1,000 open Runs (a mix of supervised routes, Run Keys and bindings) in the snapshot; it reports p50/p99 added latency and gates p99 ≤ 10 ms at the CI seed with the once-retry policy (21-5's pattern). The 10k / 100k / 1M ladder stays 24.4's. Buffering means the overhead of a large or streamed response grows with its size; the gate measures the proxy, not the provider.
- **Version.** New public types and variants (`MeteringProxyOptions`, `ProxyInfo`, the binding types, `EngineEvent::Binding`, `RunError` variants, `UsageEvent` field changes), removed internals (`ObservedListener`, `WireFence`), schema v18: hekma-engine **stays 0.12.0** (the orchestrator's cycle rule), announced in the Unreleased banners. No new dependency (hyper, hyper-util, rustls, tokio and rusqlite are in-tree).
- **Threats considered.** Each with its mitigation (review ids where they exist; N-ids are this story's):
  - token in a URL reaching logs [T1.5, R1.12] → `400` before identification, not forwarded; no revocation by an unauthenticated peer;
  - a revoked key still spending [T1.6, R1.6] → revocation published before ack; per-call snapshot read; foreign commits within 1 s;
  - responses echoing a presented credential [T6.5, R1.8] → static bodies;
  - the Run Key reaching the provider or a gateway [T3.6, R2.5, R5.10] → every `x-hekma-*` stripped, `hk_` in the API-key slot refused, identity headers carry no token or token id;
  - the request target redirecting the call to another authority [T3.3, R2.6] → canonical scheme/host/port equality before dial, `CONNECT` and foreign absolute-form refused;
  - an upstream redirect carrying the call elsewhere [T3.4] → relayed, never followed, tested;
  - `Debug` or panic leaks [T3.8, R2.10] → sensitive header values, no request `Debug`;
  - a non-loopback bind, or `0.0.0.0` read as loopback [T5.7] → `127.0.0.1` only, resolution checked, no widening flag;
  - another OS user squatting the port while no host runs [T5.2, B9] → Stated limit, documented; sticky port makes it a known address, not a moving one;
  - spoofed attribution by any local process on a Run route, binding path or hint [N1] → attribution, not authentication: the same posture as today's per-instance port; such calls are never custody-eligible (P4); they can only be billed to and fenced by the Run they name;
  - Run-creation floods through hints or first calls [N2] → splits need an Operator binding or a Run route; the 1,000 per-parent / per-binding cap; unattributed hints ignored; 256 bindings;
  - Caller labels steering Policy [N3] → hint labels are Caller labels and never select a Policy (FR-60); validated; at most 16;
  - memory exhaustion by large or many bodies [N4] → 64 MiB per body, 512 concurrent calls, a 512 MiB budget, typed 503/413;
  - slowloris and idle connections [N5] → 30 s header read, keep-alive idle timeout, connect timeout;
  - a ledger outage turning into unmetered spend [N6] → permits taken before forwarding; full → retryable refusal, never a forwarded unrecorded call;
  - a silently dropped record [N7] → re-queue with the same call id; loud, counted skip after 10 failures;
  - double counting on retries [N8] → (run, call id) dedup in the job; a client retry is a real second call;
  - lost usage on a crash [N9] → bounded by the batch window; `open_calls` closure makes it visible (`crash`), `recovered` when the ledger has it;
  - a second engine closing another engine's open calls [N10] → owner fingerprint on `open_calls`;
  - fence bypass through a child or a hint [N11] → ancestor walk on every call; a hint never escapes its parent's subtree;
  - a fence lost across restart or a config change [N12] → rebuilt from durable latches at open, before the first accept; cleared only by re-arm;
  - an open forward proxy [N13] → upstreams come only from Operator bindings and instance config, never from the client;
  - content leaking into records [N14] → no bodies or headers stored; model capped and charset-checked; no read surface yet;
  - log or outbox flooding by refused calls [N15] → counters and one diagnostic per minute, not events;
  - misrouting a legacy agent after upgrade [N16] → the legacy route only when exactly one candidate exists, ended with its Run;
  - privacy of identity headers sent to a provider [N17] → run id and labels only, never content, Operator-switchable, stated in the docs (PRD §6 note);
  - a binding upstream or route pointing anywhere [N18] → Operator bearer only (trusted); custody's origin pinning is 22.2's (P7).
  Out of scope, with the review: custody's swap, origin pinning, path scope and response redaction (22.2: R2.6's pinning half, R2.7–R2.9, R2.18), the Host/Origin guard (R2.8, 22.2), Scent-Check (22.3), held-call re-validation (R1.7, 23.4), the authenticated proxy (22.5).
- **What 23.1 does NOT do.** No custodied-key insertion, provider-variable strip or Host/Origin guard (22.2); no Scent-Check modes (22.3); no announce header, announce endpoint, Run Key in response headers, Leases or inactivity ending (23.2); no inbound OTLP (23.3); no hold, release, reroute, reject or verb-driven dispositions, and no `pause`/`stop` at wire depth (23.4); no per-call read surface (19.4); no TLS, non-loopback bind or proxy-access acceptance (22.5); no calls-store rotation, retention or compaction (24.4); no incremental SSE relay; no new OTLP counters.
- **Deferrals (new entries at build) and the existing entries naming this story.** New: incremental relay (trigger: mid-stream hold or a time-to-first-token report); Caller label updates from hints (23.2); IPv6 loopback (a report needing it); the cumulative-scope meaning for instance-less Runs (a Host asking for a binding-level all-time ceiling); the recently-revoked set's bound (24.4). Existing: 21-1 instance-less dedup — **resolved** (call id required); 21-1 launch generation at adoption — **resolved** (no bump at adoption); 21-1 calls store — **resolved in part** (created; rotation 24.4); 21-2 child usage before 23.1 — **resolved** (attributed calls through the pipeline job); 21-2 child `block` refused at open — **resolved in part** (`block` accepted with a wire path; `pause`/`stop` stay 23.4); 21-3 wire enforcement through the proxy — **resolved** for `warn` and `block`, `pause`/`stop` re-pointed to 23.4; 21-5 wire usage on the listing — **resolved** (re-keyed rollup); 21-9 Caller guard — **resolved in part** (hint labels at creation go through the guard; the Caller upsert's first caller re-pointed to 23.2); 21-9 lost Caller label — not fired (hint labels are creation-only); 19-2 fenced marker — unchanged, stays 23.4; 22-1's proxy halves of R1.6/R1.8/R1.12 and announce-credential issuance — **resolved**; 22-1 cross-engine revocation — **resolved in part** (≤ 1 s pickup; 24.4 owns O(changed)).
