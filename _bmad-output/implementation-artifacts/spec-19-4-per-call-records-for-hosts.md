## Intent

**Problem:** The shared Metering Proxy (23.1) writes one content-free record per proxied call into the calls store, and nothing reads it. A Host that runs agent workloads through Hekma cannot see which calls a Run made, which key made them, how each was answered (passed, refused by the `block` fence, an upstream error, a client that hung up), how long they took or what they used; it can only see the Run's rolled-up usage. It cannot answer "why did that call fail" or "which calls did this Run Key make", and the embedder has no facade method for any of it. The records also have no stated contract for what they may never hold.

**Approach:** A read-only surface over the calls store, on the three places Hosts already look. The engine gains `list_calls(CallsQuery)` and `call(call_id)` (async plus the blocking twins) that read the calls-store segment files through their own read-only connections: no Registry lock, no writer message, no effect on the proxy's hot path. `GET /v0/calls` and `GET /v0/calls/{call_id}` serve them to the operator/Host bearer, and `hekma calls list|show` serves the CLI, read-only, never starting a host (the `hekma ps` pattern). A listing is newest call first, keyset-paged on the call id with 21-5's cursor codec and paging rules, filtered by Run, token id, outcome, disposition, status class, model, Control Depth, binding and a time window, with a `problems` view that lists only calls that were not a clean pass. A record exposes the documented metadata fields and never a request or response byte, a header, a credential or a token (a token id is a label); the model text a client supplied is masked if it is credential-shaped. Every page is bounded: a page is at most 1,000 records, and a filter that matches sparsely stops after a fixed scan budget and says so, so no read walks an unbounded history. The calls store gains one additive step (schema 2: the indexes these reads need). No subscription ships: Hosts tail committed usage events, which carry the call id, and read the record for the detail.

**Acceptance Criteria:**
- Given calls of every shape recorded by the shared proxy — a completed `200`, a completed `429` from the upstream, a call refused by the `block` fence, an upstream transport failure, a client that disconnected, and a call closed `crash` or `recovered` at restart — when `GET /v0/calls` runs with the operator bearer, then the items are ordered by call id descending, each carries exactly the documented fields (`call_id`, `run_id`, `token_id`, `control_depth`, `binding`, `disposition`, `hold_end`, `outcome`, `status`, `status_class`, `model`, `input_tokens`, `output_tokens`, `cached_tokens`, `started_at`, `ended_at`, `latency_us`, `upstream_us`), an unknown token count is `null` (never `0`), `token_id` is `null` for a call that presented no Run Key and the 12-hex label for one that did, `hold_end` is `null`, and no key, header, body or upstream address appears anywhere in the document.
- Given a Run and its child Run, each with calls, then `run=<child>` returns only the child's calls and `run=<parent>` only the parent's (a listing never expands a subtree); given `token_id`, `outcome`, `disposition`, `status_class`, `model`, `depth` and `binding` filters alone and combined, then only records matching every given filter appear; given `view=problems`, then a completed `200` pass is absent and the refused, upstream-error, disconnect, `429`/`5xx`, `crash` and `recovered` records are listed.
- Given `limit=2` read twice (the second with the printed cursor) over a window of five records, then the pages are disjoint, descending, `next_cursor` is `null` exactly when the read is exhausted, a record that closes between the pages with an id below the cursor appears on a later page, one with an id above it is not chased, and nothing duplicates; `limit=0` serves the maximum (1,000) and `limit=1001` clamps to 1,000 (the CLI notes the clamp on stderr, the API clamps quietly); an absent `limit` serves 50.
- Given a cursor that is not the codec's form, a `v2:` prefix, or a Run cursor (its id is a run id), then `GET /v0/calls` answers `400 invalid-cursor` and `hekma calls list` exits 2; given a calls cursor on `GET /v0/runs?cursor=…` or `hekma ps --cursor`, then that answers `400 invalid-cursor` / exits 2 too.
- Given `from` and `to` (RFC 3339), then the window is half-open on the call's start (`from` inclusive, `to` exclusive) and bounds the id range, so a record starting exactly at `from` is listed and one starting exactly at `to` is not; an unparseable time or `to` at or before `from` is `400 invalid-time`; a malformed `run` is `400 invalid-run`; a `view` other than `all`/`problems` is `400 invalid-view`; an outcome, disposition or status class this build does not know is `400 invalid-filter` naming the parameter.
- Given `GET /v0/calls/{call_id}` for a record in an older segment, then the record is returned; an unknown id is `404 call-not-found`; a malformed id is `400 invalid-call-id`; `hekma calls show` prints the same record (`--json` equal to the API's item) and exits 0, while an unknown id exits 1 with a message naming the id (a malformed id exits 2).
- Given a Run Key (including the key of the very Run whose calls are asked for), a refresh credential, an announce credential and a proxy-access credential (test seams for the last two), then `GET /v0/calls` and `GET /v0/calls/{call_id}` answer `403 forbidden` for each; no credential answers `401`; the operator bearer and the `--bearer-secret` value both read on the local endpoint and on `--listen`.
- Given the no-leak matrix, then with a sentinel provider key, a sentinel Run Key, a sentinel prompt and a sentinel response body sent through the proxy, every new surface (listing and by-id JSON, the human table, `--json`, every error body, the OTLP payloads and the SSE and export streams, which must carry nothing new) and a raw byte scan of the calls segment, its `-wal` and `-shm` find none of them; given a call whose `model` field was a credential-shaped string (`hk_run_…`), then the stored value is never returned — the reader answers `[redacted]` for it.
- Given no `calls/` directory (the proxy never recorded a call, or an embedder with the proxy disabled), then the listing is `200` with no items, no cursor and no error, and `hekma calls list` prints the empty note and exits 0 creating nothing; given two segments with records, then one listing merges them newest-first and a cursor continues across the boundary without a gap or a duplicate; given a segment written by a newer build (a `user_version` above the supported one) or an unreadable file, then it is skipped, `skipped_segments` counts it, one diagnostic names the file, and the other segments are still served; given a schema 1 segment (no 19.4 indexes), then it still reads correctly.
- Given a seeded segment of more rows than the scan budget and a filter that matches almost nothing (the test lowers the budget), then the first page returns the matches found so far with `scan_limited: true`, a non-null `next_cursor` and `searched_back_to` naming how far back it looked, following the cursors reaches an exhausted read (`next_cursor: null`), and the same data read through the `problems` view for a refused-call filter is served by its index with no scan limit; the CLI prints the scan-limited note and the continuing command.
- Given `EXPLAIN QUERY PLAN` for each production statement at schema 2 (the unscoped page, the Run-scoped page, the `problems` page, the by-id probe, the windowed page), then each reads an index (`SEARCH` or `SCAN … USING INDEX`) with no `USE TEMP B-TREE FOR ORDER BY` and no bare `SCAN calls`; pinned by tests that run the statements the code runs.
- Given the proxy-owning engine opening a schema 1 segment, then it migrates it to 2 in one crash-atomic step, a crash between the DDL and the stamp re-runs cleanly, a read-only engine opening the same segment changes nothing, and an older binary opening a schema 2 segment skips it as newer (the row above).
- Given the Registry mutex held by a test, then `list_calls` and `call` still complete; given a proxy writer batch committing while a read is mid-page, then neither blocks the other (WAL), and the `perf-budgets --proxy` gate (23.1: added latency ≤ 10 ms p99) still passes with the schema 2 indexes in place.
- Given the facade, then `Engine::list_calls`/`call` and their `Blocking` twins return the same records and errors as the API on the same state directory, and a read-only `Engine` reads while a Service Host writes.
- Given a recorded call, then it is listable within one batch window after the response is relayed (the records stream is unacked: documented, not guaranteed read-your-write), and a call still in flight is not listed.
- Given the bench at `--calls-seed 100000`, then the unscoped, Run-scoped and `problems` first pages and the by-id probe each complete with p99 < 1 s (strict), reported as `calls_listing.*_p99_ms` with the seed and the segment count; the default report stays byte-equivalent; a local `--calls-seed 1000000` number goes in the build report.

## Design Notes

- **What this story reads, and what it does not own.** 23.1 owns the calls store: the tables, the writer path, the call-start and close records, `open_calls`, the outcomes, status classes and the `crash`/`recovered` closure. This story only reads it, plus the one additive index step it needs. It adds nothing to a record and changes nothing the proxy writes. If 23.1's build lands a field or index differently from its spec, the build rides the merged code and records the drift in the Spec Change Log (the 21-5 precedent).
- **The record, field by field.** `call_id` (`call_` + ULID, minted at admission); `run_id`; `token_id` (the 12-hex label of the Run Key the call presented, `null` when it presented none — a call attributed by Run route, binding or the unattributed Run has no key, so the readiness note's "always present" cannot hold and the wording is `null` when absent); `control_depth` (`observed`/`wire`/`announced`/`supervised` as the Run had it at the call); `binding` (the binding name, `null` off a binding); `disposition` (`pass` or `block` today; 23.4 adds hold, reroute and reject); `hold_end` (always `null` until 23.4 fills it); `outcome` (`completed`, `refused`, `upstream-error`, `client-disconnect`, `shutdown`, `crash`, `recovered`); `status` (the HTTP status the client got, `null` when none); `status_class` (`2xx`, `3xx`, `4xx`, `5xx`, `refused`, `transport-error`); `model` (the model the response or request named, at most 128 visible ASCII characters, `null` when absent); `input_tokens`, `output_tokens`, `cached_tokens` (`null` is unknown, never zero; `input` includes the cached subset, as everywhere else, so the three never sum); `started_at`, `ended_at` (RFC 3339 UTC with fractional seconds, as stored); `latency_us` (the whole call as the client saw it); `upstream_us` (the upstream leg, `null` when no upstream was dialled). There is no dollar figure: a record holds tokens, and derived dollars stay on the ledger and the Run, so a record never carries an estimate that could be mistaken for a bill; the call id on the usage event and ledger row is the join key (and 19.5's).
- **What a record never exposes.** No request or response body, no prompt, completion, tool call or system text, no request or response header (no `Authorization`, no provider key, no `x-hekma-*` value), no Run Key, refresh, announce or proxy-access token and no token hash, no upstream URL or client address, no label values (join through the Run), no instance name, no error message text from the upstream (`status` and `status_class` only). The reader returns a fixed field list built from named columns, never `SELECT *` into a pass-through, so a column a later story adds is not exposed by accident until this story's DTO names it. A token id is a display label (22.1, P12): it is not a lookup key anywhere in this surface except as a filter equality on the stored label.
- **`model` is client-supplied text.** The proxy caps and charset-checks it (23.1) but it is whatever the client wrote or the provider echoed; a client could paste a key into the model field. The reader therefore masks any value that carries a Hekma token shape (`hk_run_`, `hk_ref_`, `hk_ann_`, `hk_pxy_` followed by the credential alphabet, the shape 22.1's `parse_presented` knows) as `[redacted]`, and replaces any character outside visible ASCII with `?` (a tampered or foreign file). A provider key of another shape (`sk-…`) cannot be recognised and is not masked; the docs say the model field is client text. A note for 23.1's build: masking at the writer too would keep such a string off disk; if it lands there, this reader-side mask stays as defence in depth.
- **Authority.** The one credential class that reads is the operator/Host bearer, on the local endpoint and on `--listen` (22.1's matrix, route family `Operator`). A Run Key is a Caller on its own subtree for open, close and tighten and "nothing else" (AD-20), so it cannot read even its own Run's records; refresh, announce and proxy-access credentials are refused; Node credentials do not exist yet. This is the matrix as ruled, not a new row. If a Host later wants to hand a tenant a credential that reads only that tenant's Runs, that needs a new credential class and a scope rule — an AD-20 change that is Islam's, not decided here (Ask First O1).
- **Route shape.** Flat: `GET /v0/calls` (a collection, the Run an ordinary filter) and `GET /v0/calls/{call_id}`. A call belongs to a Run but is addressed by its own id, ids are unique across Runs, and a Run that has been compacted away (24.4) leaves its records readable until their segment's retention, so nesting them under `/v0/runs/{id}` would turn a missing Run row into a `404` over readable data. Hosts get one query shape for "this Run's calls" and "all refused calls today". The document is `{schema_version: 1, filters, items, next_cursor, scan_limited, searched_back_to, skipped_segments}`; `filters` echoes what was applied so a saved page is self-describing.
- **Ordering, the cursor, and what "newest first" means.** Keyset on the call id, descending. A call id is a ULID minted at admission, so descending id is descending start time to the millisecond and the primary key is the index. A record is written when the call closes, so records arrive out of id order (a long call closes after shorter, later ones). Paging therefore has the standard keyset semantics 21-5 documents: nothing duplicates; a record that appears below the cursor is found by a later page; one that appears above a cursor already served is not chased. A client that wants to follow new records re-reads from the newest page with an overlap and de-duplicates on the call id; a record never changes once written, so re-reading is safe. Wall-clock steps can make ids non-monotonic across a step; ordering is by id and the docs say so. The cursor is 21-5's codec unchanged — `base64url("v1:" + id)` — with the id required to be a call id, so a Run cursor and a calls cursor cannot be confused in either direction; it binds no filter (the CLI's next-page command repeats the flags, as `hekma ps` does).
- **Filters and the index each uses.** Run-scoped: `idx_calls_run_call (run_id, call_id)` answers `run_id = ? AND call_id < ? ORDER BY call_id DESC` with no sort (23.1's `idx_calls_run (run_id, started_at)` is in start-time order and would sort). Unscoped: the primary-key index in descending order. `problems`: the partial `idx_calls_problem`; SQLite uses a partial index only when the statement carries its predicate literally, so the `problems` statement repeats the index's `WHERE` text and the plan pin catches a drift. Every other filter (`token_id`, `outcome`, `disposition`, `status_class`, `model`, `depth`, `binding`) is a residual predicate on whichever ordered scan the rest chose. `from`/`to` become call-id bounds with the shared Crockford encoder (the ULID's timestamp is the admission time, which is the record's `started_at` to the millisecond; the build verifies that against 23.1's merged code and, if they differ, adds the exact `started_at` predicate as a residual), so a window narrows the index range rather than filtering after it.
- **Bounded pages: the scan budget.** A residual filter that matches rarely would otherwise walk a whole segment. Each page examines at most `CALLS_SCAN_BUDGET` (100,000) rows across segments. If the page fills first, the read is as 21-5's. If the budget runs out first, the page returns what it found, `scan_limited: true`, a `next_cursor` set to the last row examined and `searched_back_to` (the start time of that row), and the client continues; `next_cursor` is `null` only when the read is exhausted. A short page with a cursor is therefore normal for a sparse filter and is said so in the CLI. The budget is a constant with a `#[cfg(test)]` override, not a user setting: it protects the Host from a careless query, not a tuning knob.
- **Segments and the 23.1 store's limits.** 23.1 creates one segment, `calls/<UTC date>.db`, and never rotates, retains or drops it; 24.4 owns rotation, retention and dropping whole segments on the same naming. Until then the single file grows without bound, and this story does not change that; it does keep reads cheap on a large file (indexed, bounded) and it **already reads many segments**, so 24.4 changes nothing here. The reader lists `calls/*.db` (ignoring `-wal`/`-shm` and anything else), queries each segment newest-name-first for its top `limit + 1` below the cursor and merges by id, so overlapping segments (a call that started before a rotation and closed after) stay correct; the cost is one indexed probe per segment, bounded by retention. A file that will not open, is not SQLite, or carries a newer `user_version` is skipped with one diagnostic and counted in `skipped_segments` (surfaced, not silent; the listing is partial and says so). A segment at schema 1 reads correctly without the new indexes, only more slowly for Run-scoped pages. Records of a Run whose row was compacted stay readable until their segment is dropped.
- **Freshness and what a listing is not.** A record is written when a call closes: in-flight calls (`open_calls`) are not listed, and the listing is not a ledger. Proxy records are an unacked stream (23.1), so a call appears within about one batch window (250 ms) after the response is relayed, not at that instant, and a record skipped after its bounded write attempts (23.1's loud skip) never appears. For money, the ledger and the usage events are the record of use; a record is the per-call detail beside them. The docs say all three.
- **Concurrency.** Each call opens its own read-only connection and holds no transaction between pages, so a reader never holds a WAL checkpoint open and never blocks the proxy's writer batch. `list_calls` takes no Registry or Supervisor lock and sends nothing to the writer, so it cannot slow supervision or the proxy hot path (AD-26: no SQLite in the request path stays true; this is a separate reader). The two new indexes add work to the writer's batch; the 23.1 `--proxy` gate is re-run to prove the added latency budget still holds (the batch is off the hot path, so the expectation is no change).
- **Performance at scale.** Page cost is O(page) on an index for the unscoped, Run-scoped and `problems` shapes, O(budget) for a sparse residual filter, plus one probe per segment, and a page is at most 1,000 small rows. NFR-4's first-page placeholder (under 1 s at 1M) is the bar: the CI seed is 100,000 records (bulk-inserted in one transaction, direct SQL, no processes, Windows-safe) and gates strict p99 < 1 s; the local 1M figure goes in the build report; the 10M ladder and the calls-store retention numbers are 24.4's.
- **No subscription, on purpose.** The story asks for a read surface. Hosts that want to follow calls already have the committed usage event with its call id on the SSE stream and the export outbox, and read the record for the outcome, status and latency. A per-call event would add one outbox row per call (23.1 keeps refusals out of the event stream to avoid exactly that), and a tailing cursor over the calls store would need an insertion sequence that does not survive segment rotation. Both are deferred with their trigger (below). A Host that must see refused calls polls `disposition=block` or `view=problems` over a short window and de-duplicates on the call id.
- **The CLI.** The story names the facade and the Control API; the standing CLI-first gate and the verb table's `logs`/`list` rows ("per-call records" at `wire` and `announced`) point at a CLI read, so `hekma calls` ships thin and read-only, beside `hekma ps`, rather than leaving an operator to `curl`. It is not the `logs` verb: `hekma logs` keeps its own story and will read the same facade. Human table columns, with the 21-5 width rule (`COLUMNS`, else the terminal, else 80, clamped 40–132, a column never narrower than its header, `…` truncation, `--json` whole): `CALL`, `RUN`, `STATUS` (the code, else the class), `OUTCOME`, `MODEL`, `TOKENS IN/OUT` (`—` for unknown, never `0`), `LATENCY` (ms), `STARTED`. The footer and any next-page command go to stderr (stdout stays parseable); `hekma calls show` prints every field. Exit classes as `hekma ps`.
- **The 23.4 and 19.5 seams.** `hold_end` and the hold/reroute/reject dispositions are 23.4's producers: the item shape and the forward-compatible enums leave room, and the `problems` predicate is widened by 23.4 in the same index step style. 19.5 (reconciliation) joins Host-confirmed usage to calls by `call_id`; `Engine::call` is its lookup.
- **Deferred-work decisions (entries naming this story or the calls store).**
  1. *21-1 calls-store entry (trigger "23.1 (calls store)")* — 23.1 resolves it in part (created); **this story resolves the read half**; rotation and retention stay 24.4.
  2. *AD-21 traces entry (trigger "a real traces consumer, post-19.4")* — **keep deferred**: the records now exist and are readable, but a traces consumer or a vendor must-have has not appeared; re-point to that report.
  3. *20-1 `gen_ai.client.operation_duration` ("joins additively when a producer lands")* — **keep deferred, re-point**: the OTLP exporter reads the event bus, records are not events, and AD-21's interim carries no run id on a metric; the producer is a calls-store read in the exporter or a per-call event, chosen with the first request for it (trigger: a Host or operator asking for latency histograms in OTLP).
  4. *New:* a live tail of records (trigger: a Host asking to follow calls without polling, which also decides an insertion sequence across rotation); a Selector or a subtree filter over calls (trigger: a Host asking for fleet-wide or parent-rollup call views — needs a Run chain or label join the records do not carry, a calls-store step); listing `open_calls` (trigger: 23.4's held-call surface); a tenant-scoped read credential (Ask First O1); writer-side masking of the model text (a note for 23.1's build).
- **Version.** New public types (`CallsQuery`, `CallRecord`, `CallListing`, `CallListingDocument`, `CallError`, the enums), two facade methods and their blocking twins, a calls-store schema step; no state.db schema change and no new `EngineEvent`. hekma-engine **stays 0.12.0** (the unreleased cycle since 21-2's bump; the semver gate's baseline permits it), announced in the Unreleased banners. No new dependency.
- **What 19.4 does NOT do.** No new record field and no change to what the proxy writes (23.1); no hold, release, reroute or reject (23.4); no rotation, retention, dropping or a retention knob (24.4); no reconciliation (19.5); no subscription, tail or event; no OTLP metric; no Selector or subtree expansion over calls; no listing of in-flight calls; no dollar figure on a record; no per-tenant credential.

## Ask First

Each is a public-contract or scope choice; the recommendation is the spec's current text. **O-items are the owner's (Islam's)** — rulings the planning set reserves to him; the numbered items are the orchestrator's.

- **O1. Who may read records: the operator/Host bearer only.** Even a Run Key cannot read its own Run's records, because AD-20's matrix gives it "nothing else" (his ruling). Recommended: keep the matrix as written. If the first production Host needs to give a tenant a credential that reads only that tenant's Runs' records, that is a new credential class with a scope rule, which changes AD-20 and is his call; nothing here prevents adding it.
- **O2. Token ids are shown to the operator/Host bearer as 12-hex labels** (the security review's P12 and 22.1's O5, both still draft for ruling). The record never carries a token or hash and the id is no lookup key here but a filter equality. Recommended: yes, as 22.1 builds on; if P12 is ruled differently (longer id, none in records) this story follows.
1. **Flat routes `/v0/calls` and `/v0/calls/{call_id}`** vs nesting under `/v0/runs/{id}`. Recommended: flat (one query shape; survives a compacted Run).
2. **A single `run` filter; no Selector and no subtree expansion over calls.** A parent's listing returns only calls attributed to the parent; a Host reads a child's calls by the child's id, which it opened. Recommended: as written; the Selector and subtree views need the records to carry a Run chain or labels (a calls-store step) and wait for a Host to ask.
3. **Ordering: call id descending, a keyset on the call id, with records arriving in close order.** vs ordering by close time or an insertion sequence (which cannot survive rotation). Recommended: as written, with the overlap-and-dedup guidance.
4. **The cursor is 21-5's codec, with the id required to be a call id, and the Run listing now refuses a call cursor.** vs a distinct calls codec. Recommended: as written (one codec; closes the cross-kind hole in both directions).
5. **A scan budget of 100,000 rows per page with `scan_limited` and `searched_back_to`** vs unbounded sparse scans or a mandatory time window. Recommended: the budget (bounded reads at any size, honest about partial pages).
6. **`view=all` is the default; `view=problems` is the exception-first view** (vs problems by default as `hekma ps` does for Runs). Recommended: `all` — a Host asking for a Run's calls expects all of them; `problems` is the opt-in.
7. **Time filters apply to the call's start through the id's embedded time, half-open `[from, to)`.** Recommended: as written (index-friendly; verified against 23.1's code at build).
8. **No totals or counts in a calls listing.** A count over a large segment is the O(history) read AD-27 forbids. Recommended: none; paging only.
9. **This story owns the calls-store schema 2 step (two additive indexes), applied by the proxy-owning engine; a read-only engine never migrates and still reads schema 1.** vs asking 23.1's build to create them at schema 1. Recommended: schema 2 here (23.1 is approved text; if its build already shapes `idx_calls_run` as `(run_id, call_id)`, the step skips it).
10. **`hekma calls list|show` ships here** though the story names only the facade and the Control API, because of the CLI-first gate and the verb table's per-call rows. vs facade and API only. Recommended: ship it, thin and read-only.
11. **The reader opens read-only connections itself, takes no Registry lock and tolerates a missing, newer or unreadable segment (counted and surfaced).** Recommended: as written.
12. **`token_id` is `null` for calls that presented no Run Key** (the readiness note's "always present" cannot hold for Run-route, binding and unattributed calls). Recommended: `null`, documented.
13. **`hold_end` and the hold/reroute/reject values are in the shape now, `null`/absent until 23.4; enums are forward-compatible (unknown values render, are not filterable).** Recommended: as written.
14. **No subscription, tail or call event;** Hosts tail the usage event (it carries the call id) and read the record. Recommended: defer with the stated trigger.
15. **No OTLP `operation_duration` here.** Recommended: defer (Design Notes, decision 3).
16. **`model` is masked if it is shaped like a Hekma token and sanitised to visible ASCII; other key shapes are not recognised.** Recommended: yes, plus the writer-side note for 23.1.
17. **A record carries tokens, never dollars.** Recommended: yes.
18. **hekma-engine stays 0.12.0; no new dependency.** Recommended: as written.
19. **Two-pass review (own plus one independent) although the story is read-only,** because Epic 19 applies it to every story and this is the privacy read path. Recommended: yes.

- **2026-11-13, review round 1** (an independent adversarial review: 3 medium, 6 low; all verified real, all fixed):
  - **F1 (medium), records lost or repeated across segments.** The reader walked segments one after another and, once a page had its candidates, took only one row from each later segment. A record lying between two cursors could then sit in no page, and a budget stop in a later-named segment with higher ids could repeat a page's items and give a too-new `searched_back_to`. The segments are now walked together as one merge by call id, so the rows a page has examined are always a prefix of the merged order, whatever the file names say. This also fixes F4, where a replayed id across segments could make a full page look like the last one: copies of the same id are passed over during the walk. It fixes F7 too: the walk stops as soon as the page has its candidates. Tested with interleaved and out-of-name-order segments at five limits and four budgets, a sparse filter, and a replay; the tests fail on the previous reader.

  - **F3 (medium), embedded credentials in `model` unmasked.** The mask now applies the URL scan's rule: any token prefix in any case followed by at least eight credential characters, anywhere in the value.
  - **F5 and F6 (low), unreadable files.** A file with no calls table, or a row that will not decode, is now skipped and named like an unopenable one, instead of failing the whole listing.
