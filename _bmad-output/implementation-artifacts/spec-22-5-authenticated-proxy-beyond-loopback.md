## Intent

**Problem:** The shared Metering Proxy binds `127.0.0.1` only — `ProxyStartError::NonLoopback` is a start error and there is no flag to widen it — so a client on another machine cannot point its base URL at Hekma at all. The `hk_pxy_` proxy-access credentials story 23-1 mints through `hekma binding` are accepted by nothing ("nothing accepts either credential in this release"), which also leaves 23-1's issue output and docs saying so. The port-squatting risk is named in AD-22's Stated limit (another OS user binds the fixed port while no owner holds it) with the socket-activation recommendation explicitly left to this story. 22-2's Host/Origin guard assumes loopback literals and defers the non-loopback case here; a supervised Run's key is refused on the Control API's non-loopback listener but nothing guards the proxy's; and `docs/run-keys.md`'s "An authenticated proxy beyond loopback" section is still a promise.

**Approach:** Widen the one proxy listener — never add a second (AD-26: exactly one per data-path owner). `--metering-listen` grows to accept `IP:PORT` (a bare port keeps today's loopback meaning); a non-loopback bind **requires TLS** (`--proxy-tls-cert`/`--proxy-tls-key`, PEM files permission-checked like the secrets file, loaded before the host takes its lock — exit 2 without them, mirroring `--listen`), and the engine's proxy takes an optional `rustls::ServerConfig` plus the bind address, wrapping its accept loop in tokio-rustls (the host's `TlsListener` pattern; the engine gains the already-in-tree tokio-rustls pair). Each connection records whether its **peer** is loopback (`127.0.0.0/8`, `::1` — R5.9). On a non-loopback bind, **every call authenticates before any body is read or upstream dialed** (R5.6): a valid Run Key — of a non-supervised Run from any peer, of a supervised Run from loopback peers only (P5/R5.5) — or the binding's active `hk_pxy_` presented in the API-key slot, scoped to its own binding's path prefix, swapped for that binding's custodied key under 22-2's swap rules and never forwarded (R5.3). No credential → the new `401 hekma_authentication_required`; a proxy-access credential on another binding's prefix → the new `403 hekma_credential_out_of_scope`; unknown and revoked keep their rows, and the recently-revoked set covers `hk_pxy_`. A proxy-access credential is never a Scent-Check identity (R5.4): proxy-access-authenticated calls are unscented, so `off` serves, `shadow` serves and marks, `enforce` refuses with 22-3's `hekma_unscented_call` — the reserved matrix row lands here. The snapshot publishes the active proxy-access credentials (hash → binding, token id) beside the key index; no schema step, no new event class. Port squatting gets the startup warning (R5.8: warn when the host provably has other interactive users, say so when it cannot tell, never a silent bind) and the docs recommendation (socket activation, a single-user host, or a privileged port where the OS allows). A loopback bind behaves byte-identically to today, and `hk_pxy_` stays unknown there (AD-20's "beyond loopback only").

**Acceptance Criteria:**
- Given `hekma serve --metering-listen 0.0.0.0:8400` with no `--proxy-tls-cert`/`--proxy-tls-key`, then the start is refused with exit 2 before anything binds or opens, naming the address and the remediation (the `--listen` refusal's shape); given the same bind through `EngineOptions` with no TLS config, then the proxy's start fails with the typed non-loopback-without-TLS error; given a loopback bind (a bare port, `127.0.0.1:…`, or unset), then nothing changes and `--proxy-tls-*` on a loopback-only bind is refused exactly as `--tls-*` is without `--listen`.
- Given a group- or world-readable proxy private-key or certificate file on Unix, then the start is refused naming the path and the owner-only remediation (the secrets-file rule); on Windows the check is the documented no-op and the docs say so (R5.2).
- Given a TLS 1.1-only client against the proxy's TLS listener, then the handshake fails and nothing is served (the floor is TLS 1.2 through rustls's safe defaults); given a plain-HTTP request on that listener, then the connection fails the handshake and is closed — never served; the private key's bytes never appear in any log, event, diagnostic or panic path.
- Given `--metering-listen 0.0.0.0:8400` with the TLS pair, then exactly one proxy listener (still one per data-path owner — no second listener) binds `0.0.0.0:8400` over TLS, `control.json`, the started notice and `GET /v0/proxy` name the scheme, bind and port, `hekma binding show` prints `https://<public host>:8400<prefix>`, and a supervised agent's injected base URL still points at `127.0.0.1:8400` — its calls arrive from a loopback peer and keep today's route, custody and scope rules unchanged.
- Given a call on the non-loopback listener with no credential at all, then `401 hekma_authentication_required` (static body, `x-should-retry: false`), the request body is not read past a small bound and no upstream connection is opened — a large-body request is refused without the body being buffered and the upstream fake receives nothing (R5.6); the refusal is counted and surfaces once per minute, and no presented value is ever logged (R5.7).
- Given a supervised Run's Run Key presented by a non-loopback peer on the non-loopback listener, then `401 hekma_unknown_credential` and nothing is forwarded (R5.5); given the same key from a loopback peer on the same listener, then the call is served under today's rules — a dual-homed bind keeps local supervised custody working.
- Given `hekma binding credential issue openai --class proxy-access` and a call presenting the `hk_pxy_` token in the API-key slot (`authorization: Bearer` or `x-api-key`) under `/openai` on the non-loopback listener, then the call is attributed to the binding's Run exactly as a loopback binding call is today, the per-call record carries the credential's token id, and the credential was shown exactly once with only its hash and token id stored (R5.3).
- Given the same call and the binding holds a custodied key, then the credential is stripped and the binding's custodied key inserted toward the binding's pinned origin under 22-2's swap rules (https, verification on, canonical origin equality, path allow-list), and the upstream fake sees no `hk_` token in any header; given the binding holds no custodied key, then the call is forwarded with the credential stripped and no key inserted (the provider's own refusal answers) and the docs say a proxy-access binding wants a custodied key (O4).
- Given the same credential under another binding's prefix, or on a Run route, then `403 hekma_credential_out_of_scope`, nothing forwarded, the upstream fake sees nothing; given any `hk_pxy_` presentation on a loopback-bound listener, or in `x-hekma-run-key` on either listener, then `401 hekma_unknown_credential` (the authority matrix's "beyond loopback only"; a proxy-access credential is not a Run Key) (O8, O2).
- Given `hekma binding credential revoke openai --class proxy-access` and a call presenting the revoked token sent immediately after the command returns — no sleep — then `401 hekma_credential_revoked` (the recently-revoked set covers the class); given a second `issue`, then the first token is revoked in the same job and its next call gets the revoked row; both survive a `kill -9` of the Service Host and a restart.
- Given the mode matrix over a proxy-access-authenticated call (no Run Key, no announce): under `off` it is served; under `shadow` it is served with the `unscented` Anomaly on the binding's Run (once) and the counter; under `enforce` it is refused `401 hekma_unscented_call`, 22-3's body byte for byte — the reserved row lands here (R5.4); given the same call also carrying a valid Run Key in `x-hekma-run-key`, then the Run Key identifies the Run (the call is scented through it) and the proxy-access credential must still be valid and in scope — an invalid or out-of-scope presented credential is never silently ignored (O2).
- Given a loopback-bound proxy (default or explicit), then every request, refusal and response is byte-identical to the 23-1/22-2/22-3 behaviour (the whole existing wire table), no credential is required, and `hk_pxy_` is unknown there.
- Given each bind value: `127.0.0.1:8400` and any `127.0.0.0/8` address are loopback; `0.0.0.0:…`, `[::]:…`, a routable address and any hostname are non-loopback — a hostname input is refused with a remediation to pass an IP literal; a `::1` peer counts as loopback, while a `::1` bind stays deferred with 23-1's entry (R5.9).
- Given a proxy bind on a host where the interactive-user check finds other login-capable users, then the started notice carries the warning naming the risk and the recommendation; given a host where the check cannot tell, then the notice says it cannot tell; the docs carry the recommendation (socket activation through systemd or launchd, a single-user host, or a privileged port where the OS allows) and the warning path is proven with a stubbed user list (R5.8).
- Given a non-loopback bind with `--proxy-allowed-hosts` set, then a `Host` not on the list is `403 hekma_bad_host` before any dial (22-2's row); given the allow-lists empty on a non-loopback bind, then no Host/Origin restriction applies beyond loopback (TLS and the credential carry the boundary) and the docs say so; loopback binds and peers keep the loopback-literal default (O5).
- Given the sentinel scenario (issue → TLS calls → revoke → `kill -9` → restart) with a sentinel `hk_pxy_` token and a sentinel custodied key, then the raw-byte scans (state.db and its `-wal`/`-shm`, the calls store, every log, `control.json`, `serve.log`, before and after a checkpoint) and the no-leak matrix (events, outbox, SSE, every response body, the upstream fake's received headers, OTLP) find neither sentinel anywhere.
- Given `--autostart` with a non-loopback `--metering-listen` or any `--proxy-tls-*`/`--proxy-public-host` flag, then the usage-class refusal mirroring the explicit-listener flags; given an upgrade from a pre-22-5 state directory, then `user_version` is unchanged (no schema step), every loopback behaviour is unchanged, and an older binary accepts the directory as before.
- Given the docs, then `docs/run-keys.md`'s "An authenticated proxy beyond loopback" section ships (TLS + a credential, the credential's shape and show-once rule, not-a-Scent-Check), `docs/metering-proxy.md` carries the beyond-loopback section and the socket-activation recommendation, `docs/hosting.md` extends the recipe, and custody through a non-loopback proxy is called supported only once R5.1-R5.10 pass in CI (§11's verdict); given handoff: fmt, clippy `-D warnings`, the workspace tests, `check_docs.py` (+ `--self-test`), `test_automation.py` pass; changed-line coverage ≥ 95%; the two-pass review (own + one independent adversarial security pass, plus the AI-55 release-surface pass for the new flags and wire rows) done.

## Design Notes

- **What this story owns, and the rulings it builds on.** AD-26 (ruled 2026-10-30) fixes one proxy per data-path owner, "TLS plus a credential required beyond loopback", and the wire contract as a versioned surface; AD-20 fixes the authority matrix's proxy-access row ("the Metering Proxy beyond loopback only, presented in the API-key slot, not a Scent-Check identity, swapped for the binding's custodied key") and the socket-activation note; AD-22's Stated limit names the port-squatting risk. The security review is draft for ruling (AI-58): this spec copies §9's R5.1-R5.10 verbatim into its criteria and builds on P5-A (supervised keys stay local — the proxy half) and P6-A (the `hk_pxy_` format, already built by 23-1). §11's gate is explicit: custody through a non-loopback proxy may be called **supported** only when R5.1-R5.10 pass — the docs gate sentence waits on nothing else.
- **Where the sources disagree, and what this spec does.**
  - **P5's granularity.** The review says "presented by a non-loopback peer"; the built Control API gate is listener-level (`gate(matched, state.loopback, …)`, 22-1). Listener-level on the proxy would break supervised custody on a dual-homed bind — a supervised agent's calls arrive from loopback at a `0.0.0.0` listener and must keep its key. This spec implements the peer-level rule on the proxy (the accepted socket's remote address, available at accept) and leaves the Control API's listener-level gate alone (its non-loopback listener has no supervised callers to preserve).
  - **R5.1's "without TLS and a credential class".** Read as a start check on credentials it deadlocks setup: the first proxy-access credential can only be issued through a running host's Control API, so a host refused at start for having no credentials could never get one. This spec makes **TLS the start check** (typed refusal, mirroring the Control API) and authentication the per-call runtime rule; when zero proxy-access credentials are active the started notice says so (an honest note, never a refusal). Ask First O6.
  - **AD-20's "beyond loopback only"** for `hk_pxy_`: refused (unknown credential) on a loopback-bound listener, accepted on a non-loopback bind from any peer. The matrix says what it says; the alternative (accept anywhere) is O8.
  - **22-2's O4** deferred the guard's non-loopback behaviour here ("22-5 later adds TLS + a credential … where the guard's allow-lists widen") without specifying the widening. Beyond loopback, TLS already breaks DNS rebinding (a rebound hostname fails the certificate check in the browser) and every call needs a credential, so the guard is residual defence: the allow-lists apply when configured, empty means no Host/Origin restriction beyond loopback, and the loopback-literal default stays for loopback binds and peers. O5.
  - **R5.9's `::1`** classification vs 23-1's deferred `::1` **bind**: the classification rule lands (a `::1` peer is loopback; `0.0.0.0`, `::` and hostnames are never loopback), while binding the proxy on `::1` stays deferred with 23-1's entry — the classification and the bind are different questions.
  - **23-1's promise** "nothing accepts either credential in this release — announce (23.2), OTLP intake (23.3) and the proxy beyond loopback (22.5) do — and the docs and the issue output say so": this story retires the proxy-access half (acceptance, docs and issue-output wording); the `hk_ann_` halves stay with their stories and the wording follows whichever has landed when this builds.
  - **The story's "swapped for the binding's custodied key"** presumes 22-2's swap machinery, which is ready-for-dev and **not built** on this branch's base. The build order (22-2 → 22-3 → 23-2 → … → 22-5) puts 22-2 first; this spec rides its swap, eligibility flag and custody cache. If 22-2 has not landed when this story builds, the swap arm degrades to strip-and-forward-with-no-key (the keyless-binding behaviour) and the swap criteria wait — recorded, not silent (AI-18).
- **The identification order beyond loopback** (identify.rs stays pure; the posture and peer scope are inputs): (1) the URL scan, unchanged; (2) a presented `hk_pxy_` in the API-key slot → hash lookup in `proxy_access` → its binding's attribution and custody, or unknown/revoked/out-of-scope; (3) a presented Run Key → today's verdicts, plus the P5 peer rule (`process_owner` && non-loopback peer → unknown); (4) no credential at all → `authentication_required`; then (5) the route/binding resolution, hints and scope checks exactly as 23-1 built them. A Run Key in `x-hekma-run-key` plus a proxy-access credential in the slot is the R5.4 combination: the key identifies (scented), the credential must still be valid and in scope — a presented credential is never silently ignored, the same fail-closed rule as every other presented-but-invalid credential.
- **The credential's carrier (O2).** The PRD Glossary fixes it: "it rides in the API-key slot". So `authorization: Bearer hk_pxy_…` and `x-api-key` (the same slots a Run Key uses under custody — the two classes are distinguished by prefix, never by position), and `x-hekma-run-key` refuses it (that header names Run Keys). A base-URL-only client sets exactly one string — its API key — which is why the slot is the carrier.
- **TLS material (R5.2).** One shared `load_server_config` (the 21-4 implementation) gains the owner-only permission check from `backends` (the secrets-file helper) for **both** listener pairs — the existing Control API surface changes behaviour (a previously-accepted group-readable key now refuses); flagged in Ask First 6. The floor is TLS 1.2 by construction (`with_safe_default_protocol_versions`); the test pins it by forcing a 1.1-only client. Self-signed certificates are accepted mechanically (the server validates nothing about its own cert) and documented exactly as the Control API's are: "use a certificate your clients trust". The key file's path appears in refusals; its bytes never appear anywhere. Mutual TLS stays out of scope (the review's §11).
- **Port squatting (R5.8, the story's "limit").** The concrete shape is the review's: a startup **warning**, never a silent bind and never a refusal — a refusal would break containers and shared CI runners that look multi-user to the password database. `backends::interactive_user_hint()` is the only new OS-conditional code (the allowlisted home): Unix reads the password database for other login-capable users; Windows answers "cannot tell"; the notice says which it did. The docs recommendation is §10's sentence, adapted: socket activation (systemd or launchd), a single-user host, or a privileged port where the OS allows one. The warning fires on every proxy bind (the sticky loopback port is the squattable address, not just a wide one).
- **The advertised URL.** The bind address is not a client-usable hostname (`0.0.0.0` especially), so `--proxy-public-host <name>` sets the display host (`hekma binding show`, `GET /v0/proxy`, `control.json`); without it the surfaces render the bind address and the docs tell the Operator to hand clients the real name. The supervised base URL never uses the public host — it stays `127.0.0.1:<port>` (a supervised agent is local by definition; AD-22's "possession is the binding" needs no network round trip).
- **Snapshot, schema, version.** `binding_credentials` (23-1, v18) already holds the rows; the snapshot index and the recently-revoked extension are publish-side only, so **no schema step** (`user_version` unchanged from whatever 23-1/22-2/22-3/23-2/23-3/23-4/21-8 landed — take the tree as it is). No new event class: issue/rotate/revoke already emit 23-1's `binding` events; the new counters ride the existing once-a-minute note. New public surface: the flags, the two wire rows, `ProxyInfo`'s scheme/bind fields, `MeteringProxyOptions.bind/tls`; hekma-engine **stays 0.12.0** (the cycle rule), announced in the Unreleased banners with the AI-55 release-surface pass.
- **Threats considered** (review ids in brackets; N-ids are this story's):
  - unauthenticated non-loopback serving [T5.1, R5.1] → TLS refused at start (both surfaces); every call authenticates; the zero-credential note;
  - port squatting on the fixed port [T5.2, B9, R5.8] → the warning, the recommendation, the honest "cannot tell";
  - other OS users using a leaked Run Key [T5.3] → unchanged (loopback key + local Run Key use);
  - a supervised key used from the network [T5.4, P5, R5.5] → peer-level refusal, the typed unknown row;
  - the proxy-access credential as a shared long-lived virtual key [T5.5, R5.3] → per binding, shown once, hashed, revocable and rotatable through the 23-1 surface, scoped to its prefix and origin, published to the snapshot so revocation binds on the next call;
  - credential guessing and log flooding [T5.6, R5.7] → 256-bit tokens; counters; one diagnostic per minute; no presented value;
  - `0.0.0.0`/`::`/hostname read as loopback [T5.7, R5.9] → the classification rule, tested per bind value; hostname inputs refused;
  - TLS material on disk [T5.8, R5.2] → owner-only permission check on both pairs; the key never logged; TLS 1.2 floor;
  - slow or hostile TLS handshakes [N1] → per-connection handshake tasks with a 10 s bound (the `control/tls.rs` pattern; one stalled client never blocks accepts);
  - an expired or wrong certificate [N2] → the handshake fails loudly; the docs say to monitor expiry; no in-process rotation in v1 (deferred);
  - a restart without the flags silently narrowing the bind [N3] → the bind is never persisted (an operator flag, like `--listen`); the notice and `/v0/proxy` always state the current bind; the docs say to pin the flags in the service unit;
  - rebinding or CSRF beyond loopback [N4] → TLS breaks the rebound hostname, the credential gates spend (P4), the guard applies when configured;
  - a proxy-access credential replayed from a captured TLS session [N5] → TLS 1.2+ only, no session resumption across revocation (the snapshot read is per call); rotation is one command.
  Out of scope, with the review: mutual TLS (§11), containing a hostile same-user agent (NFR-6), the Hub/Node surfaces (AD-24), socket-activation **implementation** (the recommendation is docs; the socket handoff across restarts is 24-x's socket work), ACME or any certificate provisioning.

## Ask First

Each is a public-contract or scope choice; the recommendation is the spec's current text. **O-items are the owner's (Islam's) rulings** — the security review's readings (AI-58), the PRD-level wording and every product call this story makes on his behalf; the numbered items are the orchestrator's. Until ruled, the build proceeds on the recommended option and the PR stays unmerged past review.

- **O1. The proxy's TLS certificate and key: separate `--proxy-tls-cert`/`--proxy-tls-key` flags, or reuse of the Control API's `--tls-cert`/`--tls-key`; and whether self-signed is allowed.** Options: (a) separate flags, one pair per listener (recommended — the two listeners answer different names with different client populations and certificate lifetimes, and the proxy can go beyond loopback while the Control API stays loopback; one pair would force both listeners to move together); (b) one shared pair for both listeners (simpler, one flag fewer, but one hostname-shaped cert must cover both surfaces or carry SANs, and rotating one rotates both); (c) the proxy reuses `--tls-*` and gains none of its own (same coupling, worse ergonomics beyond loopback). Self-signed: allowed under every option — the server validates nothing about its own cert, and the docs say "use a certificate your clients trust" (exactly the Control API's wording); Hekma adds no CA, no provisioning, no mTLS. Meanwhile: (a) with self-signed allowed and documented.
- **O2. The proxy-access credential's wire carrier, and how it combines with a Run Key on the same call.** The PRD Glossary fixes the carrier ("it rides in the API-key slot"); confirm the reading: `authorization: Bearer hk_pxy_…` or `x-api-key`, accepted **only** on a non-loopback bind; `x-hekma-run-key` refuses it (that header names Run Keys). Combination: a call may carry both (a base-URL-only client sets one string, but a framework client can set two) — the Run Key identifies the Run (the call is scented through it, R5.4's escape), and the presented proxy-access credential must still be **valid and in scope** (fail closed; a presented-but-invalid credential is never silently ignored, the house rule for every credential). Alternative: let a valid Run Key satisfy authentication while an invalid proxy-access credential is ignored (more forgiving, silently masks client misconfiguration — rejected). Public contract — confirm. Meanwhile: as written.
- **O3. What "port-squatting limit" means concretely, and the recommendation's wording.** Options: (a) a startup **warning** plus the docs recommendation (R5.8 as written: warn when the host provably has other interactive users, say "cannot tell" where the OS gives no answer, never a silent bind) — recommended: a refusal would break containers and shared runners that look multi-user to the password database, and the warning is the honest AI-18 surfacing; (b) a bind-time refusal on detected multi-user hosts (stronger, but it refuses legitimate container deployments and the detection is heuristic); (c) docs only, no runtime signal (loses the visible warning on exactly the hosts that need it). The recommendation's wording is §10's sentence adapted (see Build Conventions): socket activation through systemd or launchd, a single-user host, or a privileged port where the OS allows one. Meanwhile: (a).
- **O4. May a non-loopback proxy serve Runs without custody — bindings that hold no custodied key — or only custodied bindings?** Options: (a) any binding may serve; a proxy-access-authenticated call on a keyless binding is forwarded with the credential stripped and no key inserted (the provider's own refusal answers), with docs saying a proxy-access binding wants a custodied key (recommended — TLS protects both legs, the binding's shape is the Operator's choice, and nothing is silently synthesized); (b) refuse a keyless binding's calls beyond loopback (stricter, but it forbids a legitimate pass-through shape and invents a refusal the loopback proxy does not have). Meanwhile: (a).
- **O5. The Host/Origin guard on a non-loopback bind (22-2 deferred it here).** Options: (a) the allow-lists (`--proxy-allowed-hosts`/`--proxy-allowed-origins`) apply when configured; empty means no Host/Origin restriction beyond loopback, with TLS and the credential carrying the boundary; loopback binds and peers keep the loopback-literal default (recommended — beyond loopback TLS already breaks DNS rebinding in the browser and every call needs a credential, so the guard is residual defence, and an empty-but-required list would refuse starts until Operators invent hostnames); (b) require a non-empty `--proxy-allowed-hosts` on a non-loopback bind (stronger posture, but it adds a mandatory flag whose only threat is already dead under TLS + credentials); (c) keep the loopback-literal rule verbatim (refuses every legitimate client — rejected). Public contract — confirm. Meanwhile: (a).
- **O6. What "refused at start" checks (R5.1's "without TLS and a credential class" vs FR-51's wording).** Options: (a) TLS is the start check (exit 2 without the pair); authentication is the per-call runtime rule; a started-notice note when zero proxy-access credentials are active (recommended — a start check on credentials deadlocks setup: the first credential can only be issued through a running host, and announced Run Keys are equally dynamic); (b) also refuse the start until one binding holds an active proxy-access credential (a literal reading; it cannot bootstrap — the host that would issue the credential is the host being refused). Meanwhile: (a).
- **O7. Two new public `proxy-wire v1` rows** — `401 hekma_authentication_required` and `403 hekma_credential_out_of_scope` (names, statuses, static bodies in the tasks). Alternatives: reuse `hekma_unknown_credential` for the no-credential case (misleading — nothing was presented, and the remediation differs) and `hekma_run_out_of_scope` for scope (its body is about Run subtrees, not bindings). Public contract — confirm. Meanwhile: the two new rows.
- **O8. `hk_pxy_` on a loopback-bound listener: refused (AD-20's "the Metering Proxy beyond loopback only") or accepted wherever valid.** Options: (a) refused with `401 hekma_unknown_credential` on a loopback bind, documented (recommended — the authority matrix says what it says, a credential class on a surface its class does not allow is refused, and no loopback client needs one); (b) accept it on loopback too (harmless — still scoped to its binding — and friendlier to a client whose configuration points at loopback, but it amends the matrix). Meanwhile: (a).
